## 外部凭据统一保管层(`services/credentials.py`,v3.26 凭据整合波)

我方持有、用于访问外部系统的机密及其伴生配置(LLM api_key、X bearer_token、远程同步登录密码,未来的内网 SSO 工号密码/微信微博等平台会话凭据)统一走本层的**保管契约**——声明式 `CredentialNamespace` 注册(字段清单 + env/ini/KV 三层映射),四能力:`resolve_values`(解析序 runtime_kv > env > ini > default)/`field_sources`(逐字段来源标注,因为凭据可能来自环境变量、此时运行时值不生效)/`save_updates`(只写不回显的写入半边:secret 空值=保留既有、普通字段空串=清 KV 覆盖回落基线)/`sanitize_values`(`{field}_set` 布尔 + `mask_tail` ••••尾四位预览,绝不回明文)。KV key 沿用各域既有存量(**零迁移**,test_credentials 有守卫);`x_api_config`/`daily_brief.resolve_llm_config` 保持公开签名、内部委托本层;remote_sync 定时凭据的单 JSON blob 是历史形态,只复用 `apply_secret_update` 合并语义,新命名空间一律一字段一 key。**边界(勿误并)**:本系统自签发令牌(dsub_/dfeed_ 存 hash、dshr_ 明文)与账号登录密码(accounts.py PBKDF2)不属本层;连通性探针(LLM ping/X 最省钱探针/remote-sync 登录探测)与字段取值校验留在各域 router;凭据的**使用**(client 构造)也留在各域。会话类凭据(cookie,会过期)未来接入:凭据入本层保管,续期流程各平台特质化,健康度走普通字段(last_verified_at/status)约定。前端 `SecretField.jsx` 是契约的表单半边(掩码预览即占位——`••••97c0` 本身就是「已有凭据」的信号,不赘述文字;输入框空值起步,留空=保留、输入=覆盖,语义细节挂 title)。**编辑单点在设置柜 → 管理 → 凭据(v3.27 凭据整合台,拍板 B)**:`settings/CredentialsSection.jsx` 承载 LLM/X 两张编辑卡(来源徽记+stamp+测试/保存)与「其它凭据」只读回指行(定时同步凭据与 cron 同工作流故编辑留数据同步区[柜内一跳];GitHub Token 部署级 env-only,存在性经 `GET /api/admin/credentials`);消费页只留 model-chip 状态签深链至此(日报页头/运维 AI 开关板「模型」、运维内容页 X 区头「凭据」),用量/配额观测面留在运维管理——**设置=写入口,运维=观测面**。**新增一类外部凭据 = 在 REGISTRY 登记命名空间 + 凭据区加一张卡**,即获整套存取/脱敏/来源标注契约。

## Accounts are database-managed（多管理员,v3.19 平权波）

Login accounts live in the `users` ORM table (`UserRecord`), passwords stored as PBKDF2-HMAC-SHA256 hashes. `src/services/accounts.py` centralizes hashing/verify, user CRUD, the **last-active-admin guard**, and `seed_root_admin_if_empty`. `[auth]` no longer seeds accounts: **on first boot (empty `users` table) the system auto-creates a root admin `admin`/`admin`** (log in and change the password immediately); **v3.55(issue #31)起根管理员是平权之上唯一的例外**:用户级明细(账户名单、逐账户设置/启停/改角色、单用户活动抽屉、活跃榜、AI 用量按用户维度)只有根管理员可见可操作,其它 admin 只见聚合数字——判据 `accounts.root_admin_username`(活跃管理员里名为 `admin` 者,缺则回落创建最早的活跃管理员,任何库恒有一名),门控 `app.root_admin_required`(`/api/accounts`、`/api/admin/accounts` 前缀 403「仅限根管理员」;`ai-usage`/`overview` 按会话剥用户维度),能力位 `runtime.root_admin`;根管理员不可降级/停用/删除(`_guard_root_admin`,先于末位保护);反馈收件箱/自定源创建者列/非账户类操作审计有意保留给全体管理员,账户操作审计行与自定源含凭证地址对非根遮蔽(见 `docs/archive/admin-root-admin-and-account-growth.md`)。**Admins are otherwise unlimited**: the root admin can create accounts of either role, promote a reader to admin, or demote/disable/delete another admin. The second guard is last-active-admin protection (`_guard_last_active_admin`): the last remaining *active* admin cannot be demoted/disabled/deleted (an inactive admin doesn't count and can be deleted). Self-demotion/self-disable follows the same rule — the acting admin's own cookie is then revoked on the next request (by design; the frontend confirm dialog warns first). Admin manages all accounts under `/api/accounts` (list/create[role]/update role|active|per-account AI toggle/reset-password/delete — admin-only via `account_admin_required()`, independent of the runtime axis); `/api/admin/accounts` lists **all accounts including admins** (rows carry `role`; frontend shows a role column + promote/demote actions). Any logged-in user self-changes password via `POST /api/auth/change-password`; `POST /api/auth/preferences` stores per-account preferences (currently `default_surface`, see *Admin dual-surface*). `login_admin` and `read_auth_token` validate against the DB (account must exist, be `is_active`, role must match the token), so disabling/deleting/role-changing a user revokes their existing cookie on the next request. `username` is the immutable identity (it keys `owner_username` on subscriptions/feed tokens — no rename; deleting a user cascades their subscriptions + feed token). The account-management UI lives in the **运维管理 Tab** (`AdminOpsTab`, see [Admin Ops console](admin-ops.md)); the 设置柜's 账户 section holds the self password-change/avatar/logout available to every account (+ the admin-only default-surface picker). **密码登录能力位(issue #130)**:`services/auth_policy.password_login_enabled(record)` 是下游外部身份源(内网 SSO)的唯一覆盖点,main 上恒 True;`runtime.password_login_enabled` 与 `GET /api/auth/session` 透出,`false` 时 `/api/auth/login` 与 `change-password` 403、设置柜账户区隐藏改密表单——下游不得再把该信号当 prop 穿过 `App.jsx` / `SettingsModal.jsx` 签名。

## Admin audit log（管理操作审计,v3.19）

with multiple admins, every management write is recorded so admins can audit each other. `src/services/admin_audit.py` hooks into the tail of the `require_admin_session` middleware: any non-GET request by an admin session hitting the management prefixes (`AUDIT_PATH_PREFIXES`: `/api/accounts`, `/api/admin`, `/api/x-api`, `/api/source-configs`, `/api/collection-jobs`, `/api/llm`, `/api/daily-brief`) writes one `AdminAuditRecord` row (operator/method/path/status_code/semantic `summary`/`target`/timestamp) — reader-surface actions (`/api/reader/*`, `/api/auth/*`) are deliberately exempt (an admin reading/subscribing is not a management operation). Requests rejected by the middleware itself (401/403) are not recorded; handler-level 400s (e.g. last-admin guard refusals) **are** — "who tried to delete the last admin" is part of the audit's job. A small path-pattern registry renders semantic summaries for account ops (never reading password fields); `record_audit` swallows all exceptions (same pattern as the AI-usage recorder). Read back via `GET /api/admin/audit-log?days=&limit=` (admin-only); surfaced in 运维管理 → 用户 → 操作审计 (`AdminAuditPanel.jsx`). No retention/cleanup yet.

## Admin dual-surface（管理员双界面,v3.19）

an admin is also a reader. The backend reader gate already admits admins (`reader_role_enabled`); the frontend gives admins a **hidden surface switch**: a `BookOpen` button at the bottom of the app rail enters the 阅读器 in its standalone full-page form (subscribe/read/favorite like any reader), and a symmetric `LayoutDashboard` button in the reader vrail bottom (rendered only when `onExitReader` is passed) returns to the console. `App.jsx` keeps two orthogonal notions: `isReaderRole` (account semantics — tabs/redirects/copy) vs `readerView` (layout fork — rail hidden, ReaderTab shown); admin's `surfaceMode` (`console`|`reader`) lives in sessionStorage (`dorami-surface`, cleared on logout) and doesn't touch tabs/activeTab/hash, so exiting returns to the original tab. The per-account `UserRecord.default_surface` (`console`|`reader`, exposed via `/api/runtime`, edited in 设置柜 → 账户) decides the landing surface at login when the session has no prior switch.

## Access control — login account role (primary axis)

In the default single-node `all` deployment the only axis that matters is the **login account role** (`admin` | `user`, stored per-account in the `users` table). **`admin` is a superuser** — collector surfaces (节点管理/任务运行, article CRUD) plus every reader surface; **a `user` is a restricted reader** — reader surfaces only (subscription delivery, full-text search, MCP/接入集成, surfaced as the full-page 阅读器 + the 设置柜's 接入集成 group), open to any logged-in account except archive import (admin-only, it mutates the whole archive). `disabled_runtime_surface()` enforces this per request via `COLLECTOR_API_PREFIXES` / `READER_API_PREFIXES` (reader-prefix matches short-circuit, allowing reader/collector prefix overlap). The frontend mirrors it through `runtime_capabilities()` → `collector_enabled` / `reader_enabled` / `account_role` per session.

## Optional second axis — deployment runtime role

(`[runtime] role`, default `all`): only relevant for a *split deployment* where collection and distribution live on separate hosts (`collector` = collect/archive only, external network; `reader` = distribution only, intranet; they exchange data via *Archive Sync*). It ANDs with the account role (`collector_enabled = runtime allows collector AND account is admin`). For the default `all` single-node setup this axis is inert and `collector_enabled`/`reader_enabled` reduce to the account role above — you can ignore it unless you actually split the deployment.

## 游客(guest,issue #213)

第三种会话角色 `guest`:收到站内链接的人不登录也能逛读者面。**会话按访客,三件事落到共享保留账号**:

- **访客身份** `guest:v:<vid>`(vid 随机 16 字节,签名长效 Cookie `{AUTH_COOKIE_NAME}_vid` 记住,365 天,同一浏览器回来沿用);会话令牌沿用登录 Cookie,载荷 `{"sub": "guest:v:<vid>", "role": "guest", "gen": <保留账号会话世代>}`,有效期同账号会话。已读、AI 计次与用量、阅读计量、长文翻译任务、公告关闭都按访客身份记,天然各自独立;访客 30 天无访问,其已读与公告关闭行随留存清理回收。
- **共享保留账号** `guest:shared`(`users` 一行,`role = "guest"`,不可登录的密码哈希,免兴趣引导):订阅范围(镜像新账号默认名单)、共享游客早报、AI 授权(`ai_beta_enabled` = 运维「游客 AI」开关)落到它;`accounts.account_username_for` / `get_account_for` 做映射,`accounts.is_guest_username` 是唯一判定(保留账号与 `guest:v:*` 都算)。冒号是系统保留身份的命名空间(用户名禁冒号,同 `deleted:` 墓碑)。
- **总闸** KV `guest_access_enabled`(`services/guest_access.py`,缺省开):关 = 保留账号停用 + 轮换会话世代,在线游客下一次请求即 401;开总闸 / 改默认名单 / 启动时 `ensure_guest_identity` 同步订阅镜像,名单变化时重编当日游客早报。
- **门控 fail-closed**:`src/api/guest_policy.py` 的 `GUEST_ALLOWED_ROUTES` 按 (方法, 路由模板) 登记游客可达端点(用 Starlette 路由匹配,与框架分发同序取首个完全匹配,不会因前缀相同误放写端点);其余一律 **403 `{"code": "login_required"}`**——不回 401,因为前端 401 即踢回登录页;`/mcp` 与全部管理 / 采集面同样拒绝。守卫 `tests/test_route_authz_audit.py`:登记项必须真实存在、其余路由对游客一律 403。**新端点默认不对游客开放**,要开放须显式登记。
- **会话端点**:公开的 `POST /api/auth/guest {entry}`(总闸关 403 `guest_disabled`;已登录账号 409,不降级);`GET /api/auth/session` 匿名载荷带 `guest_access_enabled`,游客会话 `user.role = "guest"`、展示名「游客」;`/api/runtime` 对游客给 `account_role: "guest"`,对所有会话给 `guest_access_enabled`。
- **账户面排除**:保留账号不进账户名单,批量 / 改角色 / 启停 / 删号 / 重置密码一律拒绝;`seed_root_admin_if_empty` 的空表判定、账户增长、读者数、发现页「N 人订阅」、运维订阅数都不计;登录接口拒绝保留账号名。游客在本浏览器登录成功时记一次转化(运维游客区)。
- **媒体代理**:游客会话的 `/api/media/proxy` 只回已缓存图片,未命中 302 回源站,不在服务端代为下载(免得成了公网取图代理)。
- **前端**:游客是读者面的只读角色(`App.jsx` 的 `isGuest`,布局同读者)。需要账号的操作不隐藏入口,点了走 `utils/loginPrompt.requestLogin` 弹 `LoginPrompt`(不发请求),后端 403 `login_required` / 429 `guest_quota_exhausted` 由 `api.js` 派发同一事件兜底;「登录」把登录页叠在阅读器之上(「返回继续逛逛」原样回来);回跳目标 = 打开登录页那一刻眼前正在看的那篇(阅读器外壳经 `onVisibleArticleChange` 上报),没有就落早报;登录完成时主界面先卸载、拉到新账号的 runtime 后重新挂载,回跳只由新身份的阅读器消费,管理员这次也落阅读器。改认证 Cookie 的请求(登录、游客进入与续期、退出)经 `utils/authSession.authQueue` 串行,会话代次(`api.js` 的 `authGeneration`)在 Cookie 换身份时推进,401 事件带发出时的代次,旧代次的 401 一律忽略;游客会话失效时同批并发的 401 只续期一次。未登录打开站内链接且总闸开时直接以游客进入并打开那一篇;登录页总闸开时登录按钮下方多一行小字「游客登录」。
