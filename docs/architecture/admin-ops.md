## Admin Ops console (运维管理 Tab)

An **admin-only** top-level Tab (`AdminOpsTab.jsx`, gated by `account_role === 'admin'`) is the operational hub, laid out as a **Grafana-style monitoring 看板** (charts via `recharts`, themed through dorami tokens in `components/charts/DashboardCharts.jsx` + `chartUtils.js`; numbers hidden until hover-tooltip). It is split by a `.segmented-control` into three sub-pages (`sub` state: `ai` | `user` | `content`): **① AI** — the AI Beta master switch as a compact status-light + toggle in the panel header (`/api/admin/ai-beta/global`), a read-only **model-status chip** (the LLM editor lived here v3.9–v3.26; v3.27 凭据整合台 moved editing to 设置柜 → 凭据, the chip deep-links there via `openSettings('credentials')` — same pattern as the Daily Brief panel's chip), and an **AI usage dashboard** charted from `/api/admin/ai-usage` — a time-range dropdown (近 7/14/30/90 天) drives two daily multi-series **stacked bar charts** (每日调用次数 / 每日 tokens;issue #184 起离散柱,没有数据的日子画刻度点), each with an in-header 按用途/按用户 segmented toggle that re-pivots the series from `summarize.by_day_purpose` / `by_day_user`; series use a categorical palette (not just the brand token) for distinguishability; **② 用户** — a **windowed** reader-OPS board (migrated out of `SettingsModal`): a 近 7/14/30/90 天 time-range dropdown drives the whole sub-page (default 30) — top KPI tiles (读者数 / 窗口内登录过 / 窗口阅读 / 窗口 AI 调用) + **账户增长**(v3.55 issue #31,`admin/AccountGrowth.jsx`:`GET /api/admin/account-growth` 按创建日新增序列 → 随页头时间窗逐日折桶,一条从存量起步的阶梯线、抬阶处标「+N」(issue #184;此前柱 + 折线双轴),现存账户口径,全体管理员可见;非根管理员的用户子页只有四格聚合 KPI + 增长 + 审计,账户表/活跃榜/抽屉不渲染、AI 用量图只留按用途) + an 活跃用户 Top rank bar with an **阅读 / 登录 segmented toggle** (re-ranks by the chosen activity dimension), then a list where **each row shows window metrics, not lifetime counters** (最近登录 + 窗口登录次数 + 窗口阅读次数 + 窗口 AI 调用 + 订阅数). The window fields (`reads` from `reader_activity.reads_by_user`, `logins` from `accounts.logins_by_user`, `ai_calls`/`ai_tokens` from `ai_usage.usage_by_user`, `logged_in_window` derived from `last_login_at`) come from `GET /api/admin/accounts?days=`. **Clicking a row opens a read-only per-user activity drawer** (`GET /api/admin/accounts/{username}/activity?days=`, powered by `ai_usage.summarize_user` + `reader_activity.summarize_user_reads` + `accounts.summarize_user_logins` + a per-user favorites-by-source join): an **expandable 登录 card** (count + click-to-reveal 最近 N 次登录时间 list) alongside 阅读/AI/订阅 snapshot tiles + a 各源 · 阅读/收藏 grouped-bar chart (`source_engagement` = reads ∪ favorites per source) + a 每日 AI 用量 stacked-bar chart (调用/tokens toggle, purpose-stacked). Row-level management (create-account[role picker]/promote-demote admin/active/per-account AI toggle/reset-password/delete) stays inline (`stopPropagation` so it doesn't open the drawer); the account list includes admins with a role column (v3.19 多管理员), and an 操作审计 panel (`AdminAuditPanel.jsx`, `GET /api/admin/audit-log`) sits below it. Windowed richness derives from `AiUsageRecord` + `ReaderReadRecord` + `LoginEventRecord`. (`ChartPanel` flex-centers its chart so a short rank chart sits vertically centered when a taller sibling stretches the row; `RankBars` takes an optional `bars` prop for grouped multi-series.) **③ 内容** — a charted content board (`/api/admin/content` → 各源收藏/订阅 rank bars + 收藏文章榜). (The old overview KPI stat board was removed as low-signal; `/api/admin/overview` still exists but the UI no longer calls it.) New admin endpoints live under the `/api/admin/*` prefix (`overview`, `accounts`, `accounts/{username}/activity`, `ai-usage`, `content`, `ai-beta/global`), all forced to admin via `account_admin_required()` (which matches `/api/accounts` **and** `/api/admin`). The shared recharts wrapper `MultiSeriesBars` (issue #184: discrete stacked bars + empty-day ticks, formerly the monotone `MultiSeriesArea`) takes a `dims` prop so the same stacked-bar component serves both the AI-usage 按用途/按用户 toggle and the per-user 调用/tokens toggle.

## 运维面播客与分析标签(issue #76)

运维管理五段 seg 不变,「标签」改名**「分析与标签」**——「分析链路」(4 枚 ledger-switch 开关板 / 指标 KPI / 分数分布 / 历史文章完整分析,回填默认档 `missing_or_outdated`)与「标签治理」(目录版本 KPI / `GET /api/admin/taxonomy/ledger` 规范标签 ∪ 候选统一总账,整行开标签或候选抽屉,新建标签 form-sheet);早报重大事件 / 订阅外兴趣 / 兴趣目录 Top N 归「内容」子页「早报与兴趣」区(它们是 `personal_digest_*` 分发策略,不是分析 worker 或目录的生产状态);「内容」子页「播客」分区 = KPI 六格 → 处理参数开关板(优质门槛可调 / 简介处理线 5.0 固定 / ASR 配额 chip 深链设置)→ 单集处理表(节目搜索、阶段 / 判定 / TTS 三轴筛选、评分 / 更新排序,阶段章 + 原因行,判定章只表优质线)→ 中文精简音频表(发布 / 下架 / 删除 / 安全回收),三处整行开同一个单集抽屉(评分与判定 / 六步处理时间线 / 产物 / 逐字稿 / 强制全文·强制 TTS)。播客处理状态的展示与命令组装只经 `frontend/src/utils/podcastProcessing.js`(阶段 / 判定 / TTS 谓词 + 章文案 + 动作 + 审计 reason + toast,面板 / 台账 / 抽屉同源;`stage_code="reconciliation"` 独立于 failed);标签枚举经 `utils/taxonomyLabels.js`。管理面 loader 纪律:实例级代次守卫、保留旧快照并经 `admin/StaleNotice.jsx` 就地提示「刷新失败 / 未接入(404)」、内容 KPI 失败不挡同页分区、`refreshTick` 透传各分区;内容子页不渲染页头时间窗。

## AI usage metering (token tracking)

`src/llm/client.py` keeps `chat_completion()` returning a `str` but optionally surfaces the response `usage` (prompt/completion/total tokens): pass a `UsageMeta(purpose, username)` and the client hands token usage to a registered recorder callback (`set_usage_recorder`, wired in `app.py` to write the DB) — **metering never blocks the main flow** (recorder exceptions are swallowed; `ping()` passes no meta so connectivity tests aren't counted). `src/services/ai_usage.py` aggregates one row per `(day × username × purpose × model)` into the `AiUsageRecord` table (`record_usage` upserts/accumulates; `summarize` powers `GET /api/admin/ai-usage`). Purposes: `translate`/`ask` (attributed to the logged-in reader), `daily_brief_map|dedup|reduce` (attributed to the **admin who manually triggered** the run via `generate_daily_brief(triggered_by=...)`, else `"system"` for scheduled runs), `source_config`/`detail_profile`. Lightweight per-account counters (`UserRecord.ai_translate_count`/`ai_ask_count`/`last_login_at`) remain a separate cheap snapshot for the account row; `AiUsageRecord` is the token dashboard's source of truth.

## Reading metering (阅读计量)

parallel to AI metering but for plain reads — `src/services/reader_activity.py` aggregates one row per `(day × username × source_id)` into `ReaderReadRecord` (`record_read` upserts/accumulates). A read is recorded when a reader **deliberately opens an article** in the 阅读器: `POST /api/reader/articles/{id}/read` (reader-gated, fire-and-forget, dedup'd frontend-side against consecutive re-clicks, silently ignores missing articles) resolves the article's `source_id` and bumps the aggregate. To keep the signal clean the reader **no longer auto-opens a default article** (auto-opens would be passive, not deliberate). `reads_by_user` (windowed per-user totals) feeds the admin account list / 活跃用户 Top; `summarize_user_reads` (total + by_source + by_day) feeds the per-user activity drawer's 各源阅读/收藏 board. The same `/read` call also bumps a per-article lifetime counter `ArticleRecord.read_count` (migration `263e8e8b6c3d`) and returns it — the 阅读窗 meta line shows「阅读量 N」(article/bulletin panes; social flow has no open action), and `serialize_article_list_item` exposes `read_count`.

## Login metering (登录计量)

`accounts.touch_login` writes a `LoginEventRecord` (raw event with precise timestamp) on every successful login **in addition to** updating the `UserRecord.last_login_at` snapshot — the event stream backs windowed login counts and the "最近若干次登录时间" list (logins are low-frequency, so raw retention is fine). `accounts.logins_by_user` (windowed per-user count) enriches the account list / 活跃用户 Top's 登录 dimension; `accounts.summarize_user_logins` (count + by_day + recent N timestamps) feeds the per-user drawer's expandable 最近登录 list.

## 游客区与游客计量(issue #213)

运维「用户」子页账户增长之下的「游客」区(`components/admin/GuestZone.jsx`,全体管理员可见、聚合口径,吃页头近 N 天时间窗):总闸 +「游客 AI」两枚开关、五格 KPI(访客 / 新访客、访问 / 日均、阅读 / 人均、AI 调用 / tokens、转化 / 转化率)、每日走势(访客柱 + 当日转化点)、入口分布条;区头齿轮开「游客设置」抽屉(四类用途每位游客的日额度,默认订阅名单只读展示、回指「内容」子页)。端点 `GET /api/admin/guest?days=`、`PUT /api/admin/guest/settings`(`/api/admin` 前缀,自动入审计)。

计量:新表 `guest_visits`(`(day, visitor_id)` 唯一;`entry` = 当天首个入口 `deep_link` / `share_page` / `login_page` / `return`;`visits` 由游客打开应用拉 `/api/runtime` 累加;游客在本浏览器登录成功时在其 30 天内最近一行记 `converted_username` / `converted_at`),留存 365 天(同登录事件)。统计口径:访问、入口、逐日访客按访问行的 `day`;**转化按事件时间**(`converted_at` 落在窗口内,不管记在哪天的行上);窗口「访客」= 有访问行的访客 ∪ 窗口内转化的访客,转化率因此不超过 100%,访客为 0 时显示「—」。刷新失败而旧快照还在时区头挂 `StaleNotice`,派生数字一律按快照自带的 `stats.days`;阅读与 AI 用量直接复用 `ReaderReadRecord` / `AiUsageRecord` 里 `guest:v:*` 的行。现有口径排除游客:用户子页的账户 / 活跃 / 登录 / 阅读 / AI 五格、活跃榜、账户增长、账户名单与单用户抽屉(访客活动 404);「AI」子页按用途的总量照常含游客(成本真实),按用户视图里全体访客合成一条「游客」(哨兵 `guest:`,同 `other:` 写法,前端映射显示名);「分析 → 指标」的早报版面数排除游客版。
