① 「来自上游」为什么按源看

每篇文章上确实有一列记着「这篇归谁」。但这一列是写入时盖上去的章,决定它的是源:谁采集一个源,谁就是这个源下所有文章的写者。

所以标记放在源管理页。决定在源上发生,管理员能拨的开关也全在源上。文章面上没有需要「远端」来门控的按钮:删除与重新分析对上游文章今天已经拒绝。

② 源管理页:今天 vs #263 之后

今天内网的整机开关一开,所有公共源一起停,页面不用区分。去掉整机开关后,同一张表里有两种行:归上游的冻结,本机的照常。表上必须看得出来。

③ 去掉整机开关:节点不再有「模式」

今天是整台机器一个开关,拉一次就切过去、撤不回来。之后没有节点级的状态,只剩每个源各自的归属。

这条按源归属的约束今天就存在(collection_authority_id 非空即不准本机采析),和整机开关无关。整机开关只多管了两件事:上游没有的源也不准采,以及首次全量到达前的空窗。去掉它,16 处调用点的语义自动收窄成按源判定,调用处不用改。

④ 转发:拉来的也导出

今天每台节点只导出自己产生的数据。之后导出本机持有的全部公开数据,每行带上原产地。

画这张图时修正了方案稿的一处漏洞。方案稿让 B 用「本机记的 taxonomy 来源」充当原产地,但 C 记的来源是上一跳 B,传到第二跳就丢了树根。改为接收端另存一份 taxonomy 原产地,每跳原样往下传。方案 §3.3、§3.4 已同步修改。
本波最大的数据风险在这里。下游整流全量收尾时会问上游「这批还在吗」,上游答「不在」的就删。这个存在性核对的口径必须和导出一起扩大,否则 C 会把 A 原产的行当成「B 没有」全部删掉。方案要求两处共用一个判定函数,并加一条守卫测试。

⑤ 本机时钟:为什么加两列而不是改一列

导出按「事务修订号」翻页。今天这张记账表里本就混着两种时钟,转发要求再加一种用法。

选:加新列。旧代码完全不认识 local_revision 与 origin。新版本回滚到旧版本时,新列被无视,旧逻辑照旧工作。
不选:把 revision 改成本机时钟、另存上游值。改动更少,但回滚到旧代码后,旧代码会拿本机时钟和上游 revision 比大小,可能把真正的上游更新当成「已应用」跳过,数据静默过期。

⑥ 为什么不做互拉(A↔B)

互拉是一个 2 环,和「单一上游 → 树」矛盾。即使靠防环跳过本机行,两边同时首拉时有一个接收端无法察觉的竞态。

⑦ 上线顺序与混版本

外网按 tag 先上,内网经 master 晚几天,外网也可能回滚。两个窗口都安全,出网请求零变化。
