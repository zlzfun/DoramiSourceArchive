# issue #261 节点同步控制台 · 样页(三个方向)

> 目的:把 Archive Sync 从「设置 → 数据同步」迁到运维管理,新增一页「节点同步」,让管理员看清**同步了什么、每条流到哪了、这一轮跑到哪、失败在哪一页**。
> 本稿出三个方向(A 流水线 / B 台账 / C 两端对照),每个方向都能切五种状态(空闲 / 运行中 / 失败 / 未配置 / 生产端),外加首页目录的小磁贴。**所有数字为示意**(量级参考本机 09-17 开发副本,按外网生产规模放大),实装以接口为准。
> 视觉沿用 #114 已落地的「A 精修」:样页内联的产品 CSS 是 `frontend/src/index.css` 当前编译产物按本页用到的类名抽取的(token、`.acct-table` / `.ledger-drawer` / `.stamp` / `.ops-tile` 等 1:1),本稿新增的类全部只用 token。没有新增字体或依赖,图标是 lucide-react 1.14 原形。

## 三个方向

| | A 流水线 | B 台账 | C 两端对照 |
|---|---|---|---|
| 一句话主张 | 同步是一条按顺序跑的线:先看这一轮跑到哪、卡在哪 | 同步是一本账:先看每类内容本机有多少、上次动了多少 | 同步是两端对账:先看外网有的,本机是不是都到了 |
| 主体 | 9 条流 + 反向回传画成分组的阶段线(目录 → 原文 → AI 派生 → 媒体 → 播客 → 就绪 ‖ 回传);每站一个状态标记 + 一个关键数 + 装了什么 + 用时;站点下方一条「当前流」进度 / 失败条;卡底常驻「不同步」 | 一张密表:行 = 产品名内容(按 原文 / AI 派生 / 治理 / 媒体 / 反向 分组,AI 分析拆 评分 / 速读 / AI 标签,播客文本拆三类),列 = 本机 · 新增 · 更新 · 删除 · 下载 · 完成于 · 状态;运行中当前行内嵌进度;「不同步」是表尾折叠组 | 左外网、右本机,逐类内容镜像对齐(外网数右对齐、本机数左对齐),中间一列是带箭头的「同步关系」:已到齐 / 待同步 N / 进行中 / 第 37 页失败 / 未跑 / 未协商;回传证据用反向箭头;表头上方一行两端身份 + 中间的合计结论 |
| 回答得最好的问题 | 跑到哪了、多久、失败在哪条流哪一页(issue 目标 3、4) | 同步了什么、各有多少(目标 2、6) | 是不是都到了、差多少(目标 2 的「落后」) |
| 优点 | 阶段顺序与「就绪围栏永远最后」一眼可见;失败定位最直观;只依赖少量需新增(分母、失败页码);形态是自己的(地铁线式时间线,不是竞品看板) | 与运维其它页同一套表格语言(列头即操作、抽屉),实现最省、最好扩展;内容盘点最完整 | 最贴近「对账」直觉;反向证据、「本机多(删除不传播)」这类边界一眼能看懂;采集就绪「条数相同但待同步 7」能讲清「待同步 ≠ 条数差」 |
| 代价 | 每站信息密,1280 下部分站点的小字要折两行(subgrid 保证各站同一行对齐);内容条数下沉到抽屉 | 流的先后顺序没了(按类别排),进度只在一行里;表很长(18 行 + 折叠组) | **最依赖需新增**:外网条数、待同步、合计结论都要生产端加计数探针(协议扩展);没有探针时左列与中列基本空白,退化成 B |
| 生产端状态 | 站点改成「可导出 N · 修订 r…」,反向站显示收到的证据 | 表改成 可导出 · tombstone · 最新修订 · 最近变更 | 左右互换:左是本机(生产端),右是接收端(多为需新增) |

三者共有:

- **页头**(左右各两行,顶对齐):左 = 面包屑「运维管理 › 节点同步 ▾」+ 对端身份一行(角色章「接收端 / 生产端 / 未接入」· 拉取自 `dorami.cloud` · authority `7c1e9a2b` · 远端 v3.67.4 · 协议 v3 · 9 / 9 流,悬停看完整 URL / UUID / 能力清单);右 = 测试连接(图标)· `⋯` 高危(图标)· **立即同步**(本页唯一主按钮,运行中变成「同步中 6 / 9」)+ 定时胶囊「定时 每 6 小时 · 下次 18:00」(点开弹层)。零说明句。
- **运行记录**:最近 10 次;列 = 开始 · 触发 · 结果 · 逐流(9 + 1 格小条,失败格红、未跑空心、未协商虚线)· 条数 · 新增 · 更新 · 删除 · 下载 · 用时;失败行下贴一行错误(定位到流与页)。整行开运行抽屉。
- **连接与定时**:两栏 KV(远端 / 账号 / 协议 / 能力 / authority / 接收端围栏;状态 / 频率 / cron / 下次 / 上次保存),编辑入口是小图标(定时 → 弹层,更换远端 → 高危抽屉)。
- **逐流抽屉**:装了什么(产品名 + 接收端语义)· 本机条数 · checkpoint(authority / snapshot / 完成于)· 本次或上次统计(页 / 条数 / 新增 / 更新 / 删除 / 清理 / 跳过 / 延后,媒体与音频另有下载 / 复用 / 字节,文章另有事件成员补回)· 历次结果;脚部一个「重置本流 checkpoint」小图标(跳到高危抽屉并预选该流)。
- **运行抽屉**:概要 · 逐流表(结果 / 条数 / 新增 / 更新 / 删除 / 用时,失败流写「第 37 页 · 已处理 36,000」)· 错误原文 · 重试同步。
- **高危抽屉**(`⋯`):重置某条流的 checkpoint(九宫格选流)· 重放分析流 · 更换远端并重新基线 · v1 JSONL 兼容导出 / 导入(v2 接收端上导入按钮禁用,因为后端会 409)。每个高危按钮都过确认框。
- **未配置**:页顶一张「接入生产端」卡(地址 / 账号 / 密码 / 协议 v2 全流 · v1 兼容 + 测试连接 + 开始首次同步),测试结果一行(远端版本 / 协议 / authority / 能力 / Taxonomy / 文章总量)+ 前置条件勾选(必需能力、远端 Taxonomy 已发布、本机媒体库、本机播客产物库、首次整流全量);下面是本方向的空态(变淡)。
- **生产端**:没有运行记录,换成「接收端」板块(谁拉过、拉到哪、落后多少;整块需新增,只有「最近回传证据」「同步账号登录」两列能从库里聚合出来)。

## 内容盘点(样页的核心;与协议常量同源,实装时从 `V2_STREAM_ORDER` 与能力常量生成,不手抄)

| 类别 | 内容(产品名) | 流 | 接收端语义 |
|---|---|---|---|
| 原文 | 文章正文与元数据 | `articles` | 外网权威,authority 围栏,本机不重抓 |
| 原文 | 公共日报 | `articles` | 以文章形式到达,本机不生成 |
| AI 派生 | 评分(新闻价值 + 内容价值)、速读摘要、AI 标签 | `analyses` | 不重算不覆盖;原文变了的分析以 tombstone 撤回;AI 标签只替换 AI 打标,人工 / 规则标签保留 |
| AI 派生 | 翻译(译文缓存) | 随 `articles` 的扩展字段 | 本机已核验的终稿译文保留(#218) |
| AI 派生 | 事件(成员与合并) | `events`(能力 `events_v1`) | 本机不往外网事件里加成员;旧事件号经重定向仍可解析 |
| AI 派生 | 播客逐字稿 / 中文博客 / 讲稿 | `podcast_texts`(能力协商) | 只同步已发布的 |
| AI 派生 | 中文精简音频 | `podcast_audio`(能力协商) | 元数据 + 二进制校验后入库;下架以 tombstone 撤回 |
| 治理 | 来源目录 / 启停 / 删除 | `sources` | 删除以 tombstone 传播 |
| 治理 | 标签目录 Taxonomy | `taxonomy` | 本机只读;版本号单独计 |
| 治理 | 采集就绪 | `source_states` | 永远最后一条(就绪围栏) |
| 媒体 | 正文 / 社交 / 播客封面图 | `media` | 不含原播客音频;删除不传播,本机 7 天宽限后回收 |
| 反向 | 自定源标签候选证据 | 内网 → 外网 `candidate-evidence.jsonl` | 每次运行末尾整份替换;最小化(无正文 / 摘要 / 链接) |
| 不同步 | 账户、订阅、兴趣、个人早报、隐藏源、人工 / 规则标签、论文全文任务、本机自定源正文、公告 | — | 本机自有 |
| 不同步 | 榜单快照(阅读榜单 / 事件热度榜) | — | 本机按可见性重建 |

(issue 里「公共日报 / 榜单快照 / 公告的口径」本稿补了:日报随文章到达;两种榜单快照本机重建;公告本机自有。)

## 数据来源表

**现有**(已有接口直接给,样页不标角标):

| 元素 | 来源 |
|---|---|
| 远端地址、账号、上次同步时间 | `GET /api/admin/remote-sync/status` → `state.targets[<url>]`(`username` / `last_synced_at`) |
| authority、协议、能力、协商流数 | 同上 → `v2_authority_id` / `v2_schema_version` / `v2_capabilities`(流数由能力按 `negotiated_v2_stream_order` 推出) |
| 每流 checkpoint(snapshot、完成于)与上次完成那次的统计 | 同上 → `v2_streams.<stream>`:`snapshot` / `completed_at` / `pages` / `count` / `inserted` / `updated` / `deleted` / `pruned` / `skipped` / `deferred` / `media_*` / `podcast_audio_*` / `reused_bytes` / `downloaded_bytes`,articles 另有 `backlog_replay` |
| 运行记录(状态、时间、用时、逐流统计、回传证据、错误) | 同上 → `jobs`(最近 10 个):`status` / `created_at` / `started_at` / `ended_at` / `result.streams` / `result.candidate_evidence` / `error` |
| 逐流小条、失败停在哪条流 | 成功 = `result.streams` 有哪些流;失败 = `progress.stream`(失败时 result 为空)+ 协商顺序 |
| 运行中:当前流、累计与本流已处理、复用 / 下载个数与字节 | `GET /api/jobs/{id}` → `progress` |
| 测试连接结果(远端版本、协议、能力、authority、Taxonomy 版本、文章总量) | `POST /api/admin/remote-sync/test`(`version` / `schema_version` / `capabilities` / `authority_id` / `taxonomy_version` / `article_total`) |
| 定时:开关、频率 / cron、账号、密码已保存、上次保存;下次时间 | `GET/POST /api/admin/remote-sync/schedule`;下次时间前端按 cron 推算 |
| v1 导出 / 导入;v2 接收端禁用 v1 导入 | `GET /api/archive/export/articles.jsonl` / `POST /api/archive/import/articles.jsonl`(进入 v2 后 409) |
| 生产端:authority、当前修订、Taxonomy 版本、本机版本 | 本机 `GET /api/archive/v2/export/sources.jsonl?limit=1` 的 manifest(`authority_id` / `snapshot`)、`taxonomy` 流 manifest 的 `taxonomy_version`、`/api/runtime` |

| 元素 | 怎么聚合 |

## 我的推荐

**首选 A(流水线)**,并吸收两点:B 的「不同步」折叠组与本机条数已放进 A 的站点抽屉与卡底;计数探针批了之后,在 A 每站多一行「待同步 N」——拿到 C 的价值而不必整页换成对照表。理由:

1. issue 最痛的三条(看不到进度、看不到阶段、失败定位不到)A 回答得最直接:顺序、当前流、已用时、失败停在哪条流哪一页,一屏可见;「采集就绪永远最后」这种不变量自己就画出来了。
2. A 主体只用现有数据就成立(需新增只有分母和失败页码,都是小改);C 离开计数探针就塌成 B。
3. 形态是自己的:不是又一张 SaaS 看板,也和其它运维页的表格分得开;运行记录、抽屉、列头即操作仍是同一套语言。

B 是最稳的备选(实现最省、与其它运维页最一致);如果更在意「内容盘点表」完整常驻,可以是「A 的流水线卡 + B 的台账作为第二板块(只留本机条数与语义两列)」。

## 不确定的地方

- 流水线各站用 CSS `subgrid` 对齐行(Chrome / Edge ≥ 117、Safari ≥ 16)。内网若还有更老的 Chromium 内核浏览器,退化是各站自己排、行不对齐(不坏),要不要做 flex 兜底待定。
- 计数探针的成本与口径:`(stream, authority_id, revision)` 有索引,按区间计数应该便宜;但「待同步」数的是**修订晚于 checkpoint 的实体**(含更新),和两端条数差不是一回事(样页里采集就绪「128 = 128 但待同步 7」就是这个),文案要能讲清。
- 「重放分析流」现在只能靠改常量触发;做成按钮要想清楚与 `v2_analysis_payload_generation` 记账的关系。
- 生产端从回传证据「认出」接收端只对挂了自定源的接收端有效;没有自定源的接收端不回传证据,就完全看不见。
- 运行记录的「触发」(定时 / admin)和逐流用时都依赖小接口改动;运行中「剩余 237」依赖计数探针。
