# IM 机器人后端架构设计（给内网编码助理的开工指示）

与 [`contracts/im_bot_integration.md`](./contracts/im_bot_integration.md) 配套：
契约册讲「哆啦美侧承诺什么」，本册讲「机器人侧怎么长」——如何从当前的纯收发系统
演进出单聊/群聊问答与日报订阅推送，且后续功能能以解耦形式持续补充。
设计已经用户拍板（2026-08-13），实现中的取舍偏离本册时请先回来对齐。

**核心思想一句话**：系统拆成「入站管道 → 按会话串行的调度器 → 处理器 → 出站管道」
四段；**会话是内存态、订阅是持久态、网关是哑管道**。

## 0. 总体分层

```
[IM SDK DLL]
   ↕ (32 位网关：只做收发，永远别长业务)
[主应用（asyncio 单进程）]
   入站管道  normalize → dedup → 自消息过滤 → 群聊@门控
      ↓
   路由器    命令注册表（订阅/退订/帮助/新话题）→ 命中即命令处理器
      ↓                                          未命中 → 问答处理器
   会话调度  per-chat 串行 × 跨 chat 并发 × 全局信号量
      ↓
   出站管道  渲染（md 降级/脚注/分片）→ 出站队列（限速、串行过网关）
```

## 1. 网关纪律（先钉死）

32 位 py3.8 + IM SDK 32 位 DLL 是全系统最脆、最难升级的一环，**只保留两个能力**：
收到消息就 POST 给主应用；收到发送指令就调 DLL。任何业务逻辑不得进入网关。

- **发送必须串行**：32 位 SDK DLL 十有八九不是线程安全的。网关内部用单线程
  队列消化发送请求；主应用侧也不并发调网关。
- **上报要快回 ACK**：网关 POST 主应用 webhook 时，主应用收到即入队、立刻 200。
  任何慢活（问哆啦美要 10–30 秒）都不能发生在这个请求的生命周期里，
  否则网关积压甚至丢消息。

## 2. 统一消息模型 + 中间件式入站管道

主应用入口先把平台原始事件**规范化**，下游永远不碰 SDK 原始形状
（与哆啦美的跨平台抽象层同一哲学——将来换 IM 或加第二个 IM，只重写 Normalizer）：

```python
InboundMessage:
  msg_id        # 平台消息 ID（去重键）
  chat          # ChatRef(kind: private|group, id)
  sender        # 用户 ID / 显示名
  text          # 已剥离 @机器人 后的纯文本
  mentioned_me  # 群聊里是否 @了机器人
  ts
```

入站管道是一条**中间件链**（web 框架 middleware 模式），每环节可放行/吞掉/注记：

1. **去重**：`msg_id` 的 TTL-LRU 集合。IM SDK 断线重连重放回调是常态，
   没有这层每个功能都要自己防重。
2. **自消息过滤**：机器人自己发的消息回环上报时直接吞
   （不吞会自问自答死循环——IM 机器人的经典事故）。
3. **群聊门控**：`kind=group 且 not mentioned_me` → 吞。剥 @ 在 Normalizer 做完。

**新功能 = 注册一个新 handler 或插一个新中间件**，不动既有代码——解耦的落点在此。

## 3. 会话（Session）与生命周期

```python
Session:
  key          = chat.id      # 单聊=对方ID，群聊=群ID（群共享，已拍板）
  history      # 有界 deque，保最近 6–8 轮（哆啦美服务端反正截尾到 8 条）
  last_active  # 时间戳
  busy         # 在途 ask 标记
```

生命周期 =「**懒创建 + 双重回收 + 手动清场**」：

- **创建**：首条消息到达时才建，无注册流程。
- **消亡**（两条正交机制叠加，各只有几行代码）：
  - *访问时懒检查*：取会话时发现 `now - last_active > TTL`（建议 30 分钟）
    就地重置历史——保证**语义正确**（隔夜追问不接昨天上下文）；
  - *定时清扫*：每几分钟一轮删过期会话 + LRU 上限（如 500 个）兜底——
    保证**内存有界**。只做懒检查会漏内存，只做清扫会有语义窗口期，两个都要。
- **手动**：`新话题` 命令清空 history。
- **不持久化，就放内存**（明确的反直觉决策）：对话历史是可抛弃的 UX 状态，
  进程重启 = 大家重新开始话题，代价几乎为零；为它上 SQLite 换来的是序列化/
  并发写/脏数据清理一堆麻烦。**需要持久化的只有订阅名单和日报推送水位**
  （SQLite 一张表），两类状态不混存。

## 4. 并发模型

工作负载纯 IO（等哆啦美、等网关），**asyncio 单进程**是正解，
不上多线程/多进程。三层并发控制各管一件事：

1. **per-chat 串行**：同一会话内消息顺序处理（否则 history 错乱、回复乱序）。
   实现：每 Session 一把 `asyncio.Lock`，或更干净的「每 chat 一条 mini 队列」。
   跨 chat 天然并发。
2. **在途拒绝而非排队**：会话已有 ask 在途时，新问题**礼貌拒绝**
   （「上一个问题还在思考，请稍候～」）而不是排队——聊天场景里排队意味着
   用户 30 秒后收到一个早已不想要的答案；拒绝更诚实，实现只是查 `busy` 位。
3. **全局信号量**：`asyncio.Semaphore(4)` 罩住所有哆啦美 ask 调用，
   保护内网 LLM 端点；叠加契约册约定的每用户/每群冷却窗口防刷。

**出站也是管道**：渲染（markdown 降级 → `[n]` 引用脚注 → 段落边界分片）
全是纯函数、可单测；之后进单一出站队列，限速（如 2 条/秒）串行发网关——
限速既是对 IM 风控的敬畏，也是网关串行纪律的落实。占位消息
（「正在查阅资料…」）与最终答案走同一条队列，per-chat 串行保证顺序不倒。

## 5. 模块骨架

```
bot/
├─ transport/
│   ├─ inbound_server.py   # webhook：收网关上报，秒回 ACK，入队
│   └─ gateway_client.py   # 出站队列 + 限速 + 失败重试
├─ core/
│   ├─ models.py           # InboundMessage / ChatRef / Turn
│   ├─ pipeline.py         # 中间件链：dedup → 自消息 → 群聊门控
│   └─ dispatcher.py       # per-chat 串行调度 + 全局信号量
├─ sessions/manager.py     # 懒创建 / TTL / 清扫 / LRU / 新话题重置
├─ handlers/
│   ├─ commands.py         # 订阅/退订/帮助/新话题（快路径，同步完成）
│   └─ chat.py             # 慢路径：占位 → ask → 渲染 → 分片发送
├─ dorami/client.py        # 程序化登录（Cookie 显式头）+ 401 重登重放 + ask + feed 拉取
├─ render/text.py          # md 降级 / [n] 脚注 / 分片（纯函数，重点单测对象）
├─ subs/store.py           # SQLite：订阅表 + 日报推送水位
└─ push/daily_brief.py     # 定时拉 dfeed → 水位判新 → 限速 fan-out 逐订阅者投递
```

三个预期功能在此骨架下的落点：功能 1/2（单聊/群聊问答）= `handlers/chat.py`
一个处理器（单聊群聊同路，差异已在管道消化）；功能 3（订阅+日报）=
`handlers/commands.py` 两条命令 + `push/daily_brief.py` 一个定时任务。
后续新功能（如「查某源最新几条」）都是再注册一个 handler，
管道/会话/并发设施全部复用。

## 6. 运维性要求

- **降级话术进代码**：哆啦美 403（AI 未开）→「AI 功能暂不可用」；
  502/超时 →「稍后再试」。异常栈与 HTTP 细节不得漏进聊天窗口。
- **Windows 进程监管**：主应用与网关各注册成服务（NSSM 或计划任务拉活），
  互相加健康探针——网关挂了主应用要能发现并告警，而非静默失联。
- **测试手法**：网关与哆啦美都是 HTTP 边界，主应用用假网关 + 假哆啦美
  （httpx MockTransport 风格）做全链路测试，不碰真 IM、不碰真 LLM。

## 7. 已拍板取舍一览（偏离前先对齐）

| 取舍 | 决定 | 理由速记 |
|---|---|---|
| 主应用并发模型 | asyncio 单进程 | 纯 IO 负载；线程/多进程徒增复杂度 |
| 会话持久化 | 不持久化（内存） | 历史是可抛弃 UX 态；持久化只留给订阅与水位 |
| 在途新问题 | 拒绝并提示 | 排队的答案送达时已过时；拒绝更诚实 |
| 群聊历史 | 群共享一份 | 契约册拍板；符合「群里讨论一件事」直觉 |
| 网关角色 | 哑管道 + 发送串行 | 最脆一环越薄越好；DLL 线程安全存疑 |
| webhook 处理 | 秒回 ACK 再干活 | 慢活占住上报通道会让网关积压丢消息 |
