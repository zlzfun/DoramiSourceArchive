# IM 机器人接入契约（哆啦美 × 内网聊天软件机器人）

内网聊天软件的「哆啦美」公共账号机器人以**读者客户端**身份消费本平台既有 HTTP API，
提供单聊/群聊问答与日报订阅推送。本册是哆啦美侧对机器人侧的**唯一接口承诺**：
机器人开发（独立仓、由内网编码助理负责）只依赖本册所述端点与语义；
哆啦美侧改动这些契约时必须同步更新本册。

**哆啦美侧零代码改动**：本契约完全建立在现役端点之上（v3.32 ask 四档 scope、
`dfeed_` 聚合 feed、程序化登录先例见 `services/remote_sync.py`）。

## 责任分界

| 归属 | 内容 |
|---|---|
| 哆啦美侧 | 内容归档、FTS5 检索、LLM 问答（规划→召回→选篇→作答全链路）、日报生成、本册契约的稳定性 |
| 机器人侧 | IM 消息收发（32 位网关保持哑管道）、单聊/群聊@路由、命令解析（订阅/退订/帮助/新话题）、会话历史管理、订阅名单存储（IM 侧本地表）、日报拉取与推送调度、markdown→IM 文本降级与分片、节流防刷 |

**已拍板决策**（2026-08-13）：

- 问答检索域 **scope=all**（2026-08-14 改判，原拍板 subscription）：检索域=全库
  可见源（隐藏源照旧排除）。改判理由：subscription 的「策展旋钮」从未被使用，
  且有诚实性缺陷——平台里有、但 dorami-bot 订阅之外的内容会被答成「没有资料」；
  IM 用户的心智模型里哆啦美=整个平台。all 本就是 v3.32 给代答场景的预留原语。
  若将来实测回答被高噪源污染，再回到 subscription+视角参数方案重新评估。
- 群聊会话历史**群共享**（一个群一份上下文，而非按提问者隔离）。
- IM 订阅日报是**纯机器人侧状态**（IM 用户/群 ID → 是否订阅，存机器人本地），
  **不映射**成哆啦美账号；哆啦美只对 `dorami-bot` 这一个服务账号可见。

## 前置条件（哆啦美侧运行时准备，非代码）

1. 内网 reader 实例 `[llm]` 配置可用的 OpenAI 兼容端点——ask 全链路
   （规划/选篇/作答）三处调 LLM，未配置时端点直接 403，这是硬前提。
2. 管理员创建读者账号 **`dorami-bot`**（role=user），开启该账号的 AI Beta。
3. 用 `dorami-bot` 登录阅读器，**订阅日报源 `dorami_daily_brief`**——scope=all
   之后订阅名单对问答无影响，但 `dfeed_` 日报拉取的范围=该账号订阅的源，
   **日报源必须保持订阅**（其余订阅可留可清）；将来清理订阅时勿动日报源，
   否则日报推送静默断供。
4. 在设置柜 → 接入集成取得该账号的 `dfeed_` 聚合令牌，交付给机器人配置。

附带可观测性：机器人的全部 AI 调用以 `dorami-bot` 计入 `AiUsageRecord`，
运维管理 → AI 用量看板天然可见其调用次数与 token 消耗，无需另建监控。

## 一、鉴权：程序化登录（会话 cookie）

问答端点走登录会话门控（无 token 通路，日后如需再议专用 bot token 端点）。

```http
POST /api/auth/login
Content-Type: application/json

{"username": "dorami-bot", "password": "***"}
```

成功 `200 {"authenticated": true, "user": {...}}`，会话经 `Set-Cookie` 下发。

**Secure cookie 陷阱（必读）**：远端若为生产姿态（`cookie_secure=true`）而机器人
经 http 访问，httpx 等客户端的 cookiejar 会因 Secure 属性**拒绝回发该 cookie**。
正确做法与 `services/remote_sync.py` 相同：从登录响应的 `Set-Cookie` 头手工抽取
`name=value`，之后每个请求**显式带 `Cookie` 头**，不依赖 cookiejar。

会话过期/账号变更后任何请求返回 401 → 重新登录一次并重放请求即可。
密码存机器人侧配置（环境变量/本地凭据文件），不入仓不打日志。

## 二、问答：`POST /api/reader/ai/ask`

单聊与群聊@共用同一契约（群聊侧先剥离 `@哆啦美` 再提交）。

```http
POST /api/reader/ai/ask
Cookie: <session>
Content-Type: application/json

{
  "question": "最近一周有哪些模型发布？",
  "scope": "all",
  "history": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ],
  "ask_id": "<客户端生成的随机 ID，可选>"
}
```

响应：

```json
{
  "status": "success",
  "answer": "……markdown，行内含 [n] 引用标记……",
  "scope": "all",
  "sources": [
    {"id": "...", "title": "...", "source_id": "...",
     "source_name": "...", "source_url": "https://原文链接", "publish_date": "2026-08-12"}
  ]
}
```

要点：

- **history 契约**：`role` 取 `user | assistant`，纯文本问答内容（不含参考资料）。
  服务端自动截尾——只保留**最近 8 条**、单条超 2000 字符截断，机器人侧无须
  精确控制长度，但传更长也不会被利用，建议客户端同样只保留最近若干轮。
- **多轮语义**：会话历史由机器人维护并整体回传（服务端无会话状态）。
  群聊 = 一个群一份历史（群共享）；建议空闲 TTL 自动清场 + `新话题` 指令手动清场。
- **引用渲染**：`answer` 行内的 `[n]` 与 `sources` 数组**同序对应**（编号即引用锚）。
  IM 端渲染为纯文本脚注：正文保留 `[n]`，末尾按序列出
  `[n] 标题（来源名 · 日期）原文链接`——链接用 `source_url`（原文），
  **不要**用 `id` 拼站内深链（IM 用户无哆啦美账号，深链打不开）。
- **等待态**：检索型问题耗时 10–30 秒量级。建议收到问题先回「正在查阅资料…」
  占位；可选进阶：轮询 `GET /api/reader/ai/ask/progress?ask_id=`（阶段
  plan→search→select→answer，完成即清）做阶段播报。客户端超时预算建议 ≥180 秒。
- **错误语义**：401=会话失效（重登重放）；403=AI 功能未开
  （总闸关/账号未开 AI/LLM 未配置——机器人应回「AI 功能暂不可用」而非重试）；
  502=LLM 上游失败（可提示稍后再试）；其余 4xx 原样转述 `detail`。

## 三、日报拉取：`dfeed_` 聚合 feed（免会话）

```http
GET /api/public/feed/articles?source_ids=dorami_daily_brief&include_content=true&limit=3
Authorization: Bearer dfeed_xxx
```

（令牌也可走 `?token=` 查询参数；响应 `items[]` 含标题/发布时间/markdown 正文。）

推送流程约定：

- 机器人定时轮询（建议挂在日报生成 cron 之后留出余量，每 10–30 分钟一次即可）。
- **幂等水位**：机器人记录 last_pushed_article_id（或最大 publish_date），
  发现新条目才推送，逐订阅者（单聊/群）投递，失败重试。
- 日报正文是 markdown，同样过机器人侧的降级转换 + 超长分片。
- 令牌在设置柜可轮换（rotate 即旧牌作废），轮换后需同步机器人配置——
  建议机器人在 401 时告警而非静默空跑。

## 四、机器人侧行为约定（建议，非强制）

- **节流**：每用户/每群冷却窗口 + 全局并发上限。ask 端点当前无服务端限流，
  群聊连环 @ 的防刷责任在机器人侧（哆啦美侧限流列为后续可选项）。
- **markdown 降级**：加粗/标题/列表降为纯文本约定俗成的形式，链接保留裸 URL；
  超长消息按 IM 单条上限分片，分片点优先落在段落边界。
- **命令保留字**：`订阅`/`退订`/`帮助`/`新话题`（可扩展）先于自由问答匹配；
  未匹配任何命令的消息一律进问答通路。

## 五、后续可选演进（触发再做，均属哆啦美侧）

- 专用 bot token 鉴权的 ask 端点（若会话维持在实践中确实繁琐）。
- ask 服务端速率限制（若机器人侧节流不够用）。
- 日报推送改事件通知（当前轮询在日报一天一更的频率下完全够用）。
