## 1. 现状与目标

#288 让只动前端 / 文档的 PR 不再等后端;动到后端的 PR 仍要等约 10.5 分钟,由 `backend-unit` 一个 job 决定:约 3470 个用例,runner 上 `-n 4` 要 10 分 12 秒(本机同一条命令 3 分 27 秒),`backend-deploy` 4–6 分钟。

本机插桩(一次 unit 全量,worker 时间合计 801 s)看时间花在哪:

| 开销 | 次数 | 单次 | 占 worker 时间 |
|---|---|---|---|
| `SQLModel.metadata.create_all`(77 张表、253 个索引、78 个触发器,一次 625 条语句) | 2203 | 76 ms | 21% |
| PBKDF2 20 万轮(播种账号 + 登录校验) | 2401 | 23 ms | 7% |
| TestClient 启动(lifespan) | 749 | 72 ms | 7% |
| Alembic `upgrade` | 75 | 631 ms | 6% |

没有哪一项占多数,剩下的六成散在三千多个用例里——所以主手段是**并行**(把一个 job 拆成几片各占一台 runner,公共仓库分钟数免费),用例本身的开销按「收益 ÷ 风险」挑着做。目标:动到后端的 PR 等待降到 5 分钟以内。

## 2. 分片

### 2.1 `--shard I/N`

`tests/conftest.py` 加一个 pytest 选项:`--shard I/N` 只保留落在第 I 片的用例(`pytest_collection_modifyitems` 里 deselect)。

- 片号 = `crc32(用例函数的 nodeid) % N + 1`。纯函数:不依赖收集顺序、不依赖别的片跑了什么,所以「每条用例恰好落在一片里」是构造出来的,不是靠各片互相配合。
- **参数 id 不参与哈希**(取 nodeid 的 `[` 之前):同一个测试函数的全部参数化落在同一片。个别参数 id 来自对象 `repr`,不能指望它跨进程稳定;按函数哈希则只依赖文件路径、类名、函数名。
- 按用例而不是按文件分:deploy 侧只有 6 个文件、单文件上百条慢用例,按文件分不匀。代价是每片都要收集全部文件(本机 4–5 秒)。
- 形状不对(`0/3`、`4/3`、`1`、`a/b`)直接是用法错误(退出码 4),不默默退回全量或空集;某一片为空时 pytest 自己以退出码 5 报红。
- xdist 下每个 worker 各自收集、各自按同一函数筛,结果一致。

均衡性(本机):unit 3 片 1198 / 1226 / 1144 条,耗时 85 / 72 / 73 秒(不分片 210 秒);deploy 2 片 109 / 114 条。

### 2.2 `ci.yml`

`backend-unit` 用矩阵 `shard: [1, 2, 3]`,`backend-deploy` 用 `shard: [1, 2]`,命令各加 `--shard ${{matrix.shard}}/N`,每片仍是 `-n 4 --dist worksteal`。`fail-fast: false`:一片红了别的片照样跑完,一次看全。

汇总门对这两个 job 的读法不用改:`needs.<job>.result` 对矩阵 job 是各片的汇总——按官方文档,任一片失败即 `failure`,job 级 `if` 在矩阵展开之前判断、为假时整体 `skipped`,`fail-fast: false` 不会因一片失败取消其余片。#288 的两条放行路径原样成立(只多要求一个 `backend-guards`,见 §2.3)。

实测(PR #294,运行 43841904357):整条 CI **4.0 分钟**(此前 8.7–10.5 分钟)。unit 三片 3.7 / 3.0 / 2.9 分钟(测试步骤 152 / 150 / 128 秒),deploy 两片 2.1 / 2.4 分钟(113 / 133 秒)。

### 2.3 少一片的后果与守卫

少一片(矩阵写成 `[1, 2]` 而分母是 3、分母漂成 4、命令里把矩阵变量写死成 `1/3`、矩阵被 `exclude` 掉一个取值)的后果是:那一片的用例哪个 job 都不跑,而 CI 照样是绿的。三层守卫:

1. **结构**(`_assert_shards`):`strategy` 块只认恰好三行受控格式——`fail-fast: false` / `matrix:` / `shard: [1, …, N]`,多出任何一行都拒(`include` / `exclude` 带不带引号、前面隔不隔空行,第二个维度,`max-parallel`,多行列表,带引号的 `"strategy"`);矩阵取值恰是 `1..N`;命令里 `--shard` 恰好出现一次,值恰是 `${{matrix.shard}}/N`。看不懂的写法不放行,而不是尽量去解析。
2. **端到端**(`_assert_shards_partition`):把矩阵的每个取值代入**真实命令里的全部分片参数**,真跑 `--collect-only`,各片互不相交、并集等于不分片时的全集,同一函数的参数化不跨片。只读矩阵长度再自己拼 `--shard I/N` 是不够的——命令末尾多一个写死的 `--shard 1/3` 把矩阵值盖掉时,那样的检查照样通过。
3. **守卫自己不在被分片的 job 里**:分片配置一旦写错,检查分片的用例可能正好落在没人跑的那一片(首轮检视的现场:追加 `--shard 1/3` 后三个 job 全跑第一片,而结构检查在第三片、突变用例在第二片)。所以另起一个**不分片**的 `backend-guards` job,单独跑 `tests/test_ci_workflow.py` 与 `tests/test_ci_scope.py`(清单 = `ci_scope.GUARD_TESTS`,命令不带 `--shard`),汇总门的全量路径要求它成功。这两份守卫同时仍留在 unit 的划分里:两边互为对照——unit 的命令被改坏了 guards 会红,guards 的命令被改坏了 unit 那边会红。只动前端 / 文档的 PR 改不到工作流与测试,不跑它,轻量路径仍是约 1 分钟。

汇总门因此是六个变量:`changes` 结果、`backend` 取值、unit / deploy / light / guards 四个结果,真值表 4096 种组合仍只放行 5 种(全量:unit、deploy、guards 都 `success`;轻量:三者都 `skipped` 且 light `success`)。

调整片数只改 `ci.yml` 的两处(矩阵与命令分母),守卫与突变都按当前片数生成,测试不用跟着改——模拟过 unit 4 片 / deploy 3 片:全部守卫通过、91 条突变照样全部被拒。

## 3. 用例开销

### 3.1 测试里的密码哈希:做

生产是 PBKDF2-HMAC-SHA256 20 万轮,本机单次 22.6 ms;unit 一轮要哈希 / 校验约 2400 次,占 worker 时间约 7%。测试只关心「能登录、口令对不对」,不关心轮数。

- `services/accounts.hash_password` 的缺省轮数从「默认参数」改为**调用期**读 `_PBKDF2_ITERATIONS`(默认参数在函数定义时就绑死,改常量不生效)。生产行为不变:常量仍是 20 万,校验按编码串里记的轮数算。
- `tests/conftest.py` 加会话级 autouse 夹具 `fast_password_hashing`:整个测试会话把缺省轮数调到 1000(单次 0.14 ms),会话结束还原;夹具顺带断言生产常量不低于 20 万——快哈希只该来自这个夹具。
- 需要真轮数的用例显式传 `iterations=`;`tests/test_accounts.py` 补一条钉住这三件事。

### 3.2 临时目录放 tmpfs:看 CI 实测

同一条 unit 命令本机 3.5 分钟、runner 上 10 分钟。一个假设是 SQLite 的 fsync:macOS 的 `fsync` 不真正落盘,runner 的 ext4 会,而几千个用例各自提交多次。把 pytest 的临时目录(`tmp_path` 与 conftest 沙箱都跟 `TMPDIR` 走)指到 `/dev/shm` 是一行的改动,但它只在 runner 上有意义,本机量不出来——所以在本 PR 里放一个**临时工作流**(`ci-exp-289.yml`,合入前删除),用与 `ci.yml` 第 1 片逐字相同的命令、只多一个 `TMPDIR=/dev/shm`,和同一次运行里 `ci.yml` 的第 1 片比耗时。

实测(PR #294 的第一次推送,`ci.yml` 运行 43841904357 与实验运行 43841904730;同一片用例、同一条命令):

| 测试步骤耗时 | 磁盘(`ci.yml` 的那一片) | tmpfs(`TMPDIR=/dev/shm`) |
|---|---|---|
| unit 第 1 片 | 152 s | 124 s |
| deploy 第 1 片 | 113 s | 121 s |

**不采用。** unit 快了 28 秒(18%),deploy 没有变快;这是单次样本,而同一次运行里用例数相近的 unit 第 2、3 片之间就差 22 秒(150 s / 128 s),差距落在 runner 之间的自然波动里。结论只能是:fsync 不是「runner 比本机慢 3 倍」的主因(否则不会只差这么点),更像是 runner 的 vCPU 本身慢。另一头是风险:pytest 默认保留整个会话的 `tmp_path`,一片一千多条用例各建约 2 MB 的库,全压在内存盘上(`/dev/shm` 上限是内存的一半)。收益不确定、失败方式难看。实验工作流已从本 PR 删除。

### 3.3 建库模板:试验可行,这一波不做

`DatabaseStorage()` 初始化一次 152 ms,其中 `create_all` 71 ms(77 张表、253 个索引、78 个触发器,625 条语句),其余是 FTS、标题翻译初始化等;unit 一轮要建约 2200 个库,是 worker 时间里最大的一项。试验:建一个模板库,之后用 `sqlite3` 的 backup 拷进新连接只要 1.9 ms,直接拷文件 0.2 ms。

不在这一波做,原因是「什么时候模板算陈旧」说不干净:

- 触发器、FTS 等是挂在 `after_create` 上的监听器,分散在不同模块里按导入顺序注册;模板建得早于某个模块的导入,之后的库就悄悄少一批对象。要防这个,指纹得把监听器状态也算进去。
- 最大的调用点是 `DatabaseStorage.__init__`,`create_all` 之后还有四步初始化;只替换 `create_all` 拿不到一半收益,要拿全就得在生产类上开一个只给测试用的口子。
- 分片之后它对 PR 等待的边际收益不到 1 分钟(unit 片从约 4 分钟降到约 3 分钟,届时 deploy 片成为决定项)。

记入 backlog,触发条件:分片后 unit 片仍是 PR 等待的决定项、且用例数再涨一截。

## 4. 守卫与自测

- `tests/test_ci_workflow.py`(123 例,97 条突变):§2.3 的三层;畸形 `--shard` 七种写法都是用法错误;分片突变按当前片数生成,两个 job 各 15 种(矩阵缺片 / 从 0 起 / 重复 / `exclude` 三种写法 / `include` / 多一维 / `max-parallel` / 多行列表 / 带引号的 `strategy` / 整块删掉,分母漂移,分子写死,选项丢失),外加「后一个 `--shard` 覆盖」的结构与端到端两条、轻量 job 被加矩阵、job 层带引号的键;`backend-guards` 七条(汇总门不要求它 / 不 `needs` 它,被分片、被筛选、清单少一份、只在轻量模式跑、吞失败)。汇总门真值表 4096 种组合真跑 shell。job 层的键改为严格读取(四空格缩进的有效行必须是不带引号的 `key:`)。
- `tests/test_accounts.py`:缺省轮数在调用期读取、显式轮数照用、新旧轮数的哈希都能校验、夹具交回的生产缺省不低于 20 万。
- 自测(本机,`-n 4 --dist worksteal`):unit 三片(85 / 72 / 73 秒)与 deploy 两片(125 / 167 秒)各自通过;检视返修后 unit 侧全量 3653 passed / 1 skipped、deploy 侧全量 225 passed,`backend-guards` 的同款命令(不分片、不并行)177 passed / 38 秒(复检后再加 6 条突变,共 183 例);`scripts/check_docs.py` 0 个问题。CI:PR #294 首次推送全绿(数字见 §2.2)。

## 5. 取舍与不做

- **片数**:unit 3 片、deploy 2 片。再多,每片的固定开销(检出、装依赖、装 ffmpeg、收集,约 45 秒)占比上升,收益递减;片数写在 `ci.yml` 的两处(矩阵与命令分母,守卫保证两者一致),守卫与突变都按当前片数生成,以后调整不用改测试。
- **不按耗时做装箱分片**(pytest-split 一类):要入库一份耗时表并持续更新,哈希分片实测已经够匀(本机三片 85 / 72 / 73 秒)。
- **不拆 `-n 4`**:每片仍是 4 个 worker,和不分片时一样吃满一台 runner。
- **不做建库模板**:§3.3。
- **不把临时目录放 tmpfs**:§3.2。
- **不去核对矩阵各片的逐片结果**:汇总门只读 `needs.<job>.result` 的汇总值。社区有未经官方确认的报告称「某一片因分不到 runner 被取消」时汇总仍可能是 `success`;要防它得让汇总门去调 API 数各片的结论,给合入门禁加一个网络依赖,为一个没复现的现象不值——记观察期。
- **不动 Alembic 迁移类用例**(75 次 `upgrade`,每次 631 ms):它们测的就是迁移本身。
