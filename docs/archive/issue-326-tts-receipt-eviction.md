# issue #326 精品导读语音的回执缓存:满了以后自己腾地方

> **归档于 2026-11-23(issue #326,开发版 3.70.3-alpha,版本号以实际发版为准)**:现状以 `docs/architecture/podcast.md`「精品导读语音的回执缓存」与代码为准,文中路径与状态为当时记录。
> 状态:归档(2026-11-23 立项并实现,单 PR)。
> 实现方 Claude Code(Fable 5.2),检视方 Codex(`gpt-6-astra`,ultra)。

## 1. 现象与取证

v3.70.2(#322)上线后,因语音预算满而停住的精品导读被候选巡检自动拉起。18 分钟内 9 期合成完成,另外 14 期停在 `retry_wait / tts_receipt_cache_full`。容量等待最多 8 次(5 分钟、30 分钟、2 小时、之后每 6 小时),用完转终态失败。

这不是 #322 引入的:9、10 月那批「回执存储满」的失败是同一个原因,之前预算卡在前面,合成走不到这一步。

生产只读核对(2026-11-23):回执目录 980MB,上限 1024MB(`tts_cache_max_bytes`),一次合成按最长口播预留约 51MB,放不下。

| 占用 | 是什么 |
|---|---|
| 574MB | 37 期**已发布**导读的压缩归档(`.wav.zlib`) |
| 322MB | 13 期**已发布**导读的未压缩 WAV,这些节目名下还留着 `reserved` 行 |
| 约 42MB | 刚合成的两期 |
| 约 43MB | 几期未发布(失败)节目已合成的分段 |

## 2. 根因

`services/bailian_tts.py` 的 `_reclaim_completed_receipts_unlocked`:

1. **归档只增不减。** 回收只做一件事:把已发布节目的 WAV 换成更小的 zlib 归档。没有任何路径删除归档,每期约 15MB,1GB 大约六十期就满,此后每一次合成都过不了容量检查。唯一会删音频的分支是「压不小的 WAV」,语音 PCM 总能压小,实际走不到。
2. **已解除占用的预留仍被当成「在途」。** 名下有 `reserved` / `authorized` / `generated` 行的节目整期跳过。#322 之后,从未发出的预留保留行、只把 `cost_minor` 记 0,状态仍是 `reserved`——这些节目的音频连压缩都轮不到。#322 的修复没有顾到这一处。

## 3. 方案

### 3.1 「在途」只看还有意义的调用

`_in_flight(row)`:`authorized`(已发出、结果未知)、`generated`(已计费、音频未落盘),以及仍占着额度的 `reserved`(`cost_minor > 0`)。占用额为 0 的 `reserved` 从未发出、也不再等着发出,没有要保护的东西。价格配置校验为正数,所以仍占额度的预留不可能是 0。

### 3.2 容量不足时逐出已有成品的音频

容量路径(合成前的预检 `_capacity_after_one_reclaim`、下载后的落盘检查 `_require_bytes_locked`)把「要放下多少字节」传给回收(`make_room_bytes`)。回收先照旧压缩;压完仍放不下,就把**已有成品的节目**的回执音频按账本创建时间从旧到新删除,删到够用为止。

- **只删够用的量。** 缓存是「同一份口播稿不重复付费」的保障,能多留就多留。
- **全有或全无。** 可逐出的总量盖不住缺口时一份都不删:这次请求反正要失败,留着的音频还能重放。缺口取缓存缺口与磁盘缺口中较大的一个。
- **账本行与供应商回执(`.json`)不动。** 行仍是 `succeeded`,同一段口播不会因此再发请求、再计费。沿用 #268 / #322「不删账」的口径。

**什么叫「已有成品」(`_reclaim_scope`):**

- 播客导读:这期节目有 `published` 的 `digest_audio_zh`。数据库保证这个状态只属于**当前**口播稿——口播稿指针一换,触发器 `podcast_script_audio_invalidate_*` 就把旧音频撤回。而导读流程在当前口播稿已有完好成品时直接复用成品、不调合成(`_reusable_published_audio`)。所以这些回执音频不会再被读到。新口播稿合成完、还没发布的那段时间里,节目不算有成品,它的重试照常从缓存重放。
- 文章朗读:`listen_guide` 已就绪。它每次运行都重新写旁白,不会重放旧回执。

这个判据就是回收一直在用的那一个(压缩也是它),本波没有放宽;变的只是在它之上允许删除。

### 3.3 正在合成的这一次不动自己的分段

合成前的预检发生在重新预留之前。上一次没走完的同一份口播稿,名下可能只剩「已成功」和「占用已解除」的行,账本上看不出在途;若这期节目同时有成品(比如成品文件损坏后对同一份口播稿重新合成),预检触发的回收就会动到它自己已有的分段。`_synthesize` 因此把本次的分段 id 明确传进去(`protect`),回收一律跳过。

下载后的落盘检查不需要:此刻正在落盘的那一段是 `generated`,整期节目在途。

### 3.4 逐出要留标记,备份认标记

每日备份(`services/storage_backup.py`)要求每一条 `succeeded` 的账本行在回执目录里有哈希相符的音频,否则整份备份失败(`backup_paid_audio_missing_or_corrupt`)——回执目录里可能有别处没有的付费音频。直接删归档会让备份从第一次逐出起每天失败(2026-10 的 #231 就是备份不认新形态、连续失败三周)。

所以有意删除音频的三处(逐出、压不小的 WAV、超过缓存上限的 WAV)统一走 `_drop_audio`:先原子写一个空的 `<行 id>.evicted`,再删音频。中途崩溃留下的是「两者都在」,无害。备份与合成共用回执目录锁,不会看到「两者都不在」。

备份把标记当作回执目录的第四种文件收进归档;`succeeded` 行有标记即不要求音频,**没有音频也没有标记仍按缺失失败**(误删、磁盘损坏照旧报出来)。恢复侧的文件名白名单同步放行。

「压不小的 WAV」「超上限的 WAV」这两个旧分支此前删完不留痕,同样会让备份失败,只是实际走不到;本波一并补上。

### 3.5 管理面的「缓存缺口」按可逐出的量折算

缓存从此常态接近上限。`receipt_cache_overview` 新增 `evictable_bytes`,两个缺口都减去它:页面上的「缺口」是逐出之后仍然不够的部分,也就是需要人处理的部分。前端不改。

## 4. 与既有口径的关系

- #268 / #322「保留原账本,不通过删账扩大预算」:本波不碰账本行,不改预算。
- #268「暂停的 120 期不自动恢复」、历史上因容量等待用完而终态失败的那批:本波不重新排队。
- `storage-backups.md`「禁止将回执目录作为普通缓存清理」仍然成立:手工删除不留标记,备份会失败;没有成品的音频删掉后同一份口播稿无法重放。

## 5. 部署顺序与混版本

- 无迁移,不涉及 Archive Sync(回执与语音账本都是节点本地的)。
- **回滚**:一旦发生过逐出,回退到 v3.70.2 及更早版本后,旧备份代码不认 `.evicted`,每日备份会失败,直到再次升级。需要回滚时备份以升级后的首次成功为准。旧版本的恢复工具也不接受含 `.evicted` 条目的归档(恢复本来就要求用与备份匹配的版本)。
- 上线后:等待中的导读下次重试时,先把 13 期被「已解除的预留」挡住的 WAV 压掉(一次性,约 322MB,持回执目录锁十几秒),不够再逐出最旧的归档。

## 6. 有意不做

- **未发布节目已合成的分段不逐出**(目前约 43MB)。它们没有成品,删掉后同一份口播稿只能靠供应商的临时地址重放,地址过期即失败。它们会缓慢累积,占到缓存的可观比例时再定过期策略。
- **逐出后同一份口播稿重放不了,不重新付费合成。** 已有成品的节目,若成品之后被管理端撤回或文件损坏,而它的回执音频已被逐出,再合成同一份口播稿会报 `tts_cached_audio_missing`(供应商地址已过期)。此前归档永久保留,这条路径总能重放。「缺音频的已成功分段允许重新付费合成」是计费语义的变化,等真的遇到再定。
- **已转终态的容量失败不自动重新排队。**
- **不改生产配置**(`tts_cache_max_bytes`)。
- **每日回收不逐出。** 它只压缩;逐出只发生在真的放不下的时候。
