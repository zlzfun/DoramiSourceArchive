# 社交流「显示更多」点了没有展开任何内容(issue #346)

> **归档于 2026-11-25(issue #346,PR #347,开发版 3.70.5-alpha,纯前端;Codex 两轮检视)**:现状以 `frontend/src/utils/socialClamp.js`、`frontend/src/hooks/useClampCut.js` 与 `frontend/src/components/SocialFlow.jsx` 为准,文中路径与状态为当时记录。
> 状态:已落地待发布(2026-11-25 开工并当日收口)。
> 实现方:Claude Code(Fable 5.2);检视方:Codex(见 §6)。分支 `feat/issue-346-social-more-toggle`。
> 关联:[issue #346](https://github.com/zlzfun/DoramiSourceArchive/issues/346)。

## 1. 现象与根因

读者面「社交媒体」里,部分推文正文下方的「显示更多」点一下变成「收起」,正文没有多出任何内容;再点变回「显示更多」,同样没有变化。

按钮出不出现和正文是否被截断,原先是两套互不相干的判定:

- 按钮:正文超过 360 字就出现(`SocialFlow.jsx` 的 `CLAMP_CHARS`);
- 截断:样式按行数截——桌面 `-webkit-line-clamp: 7`,手机壳 `max-height` 6 行。

一行能放多少字取决于栏宽、字号和正文里的换行,字数说明不了。字数过线、排出来却不满 7 行(手机壳 6 行)的推文,折叠态本来就是全文,按钮只切换了字样。

沙箱实测(本机开发库副本,94 条推文,其中 30 条超过 360 字;修复前):

| 版式 | 正文栏宽 | 带按钮 | 点了正文高度不变 |
|---|---|---|---|
| 桌面 1440 × 900(1920 宽相同,栏宽封顶) | 596 | 30 | 4(384 / 401 / 460 / 482 字) |
| 手机壳 390 × 844 | 334 | 30 | 0 |
| 手机壳 700 × 1000(平板档 / 横屏) | 644 | 30 | 2(384 / 401 字) |

手机壳另有一处连带表现:折叠态给正文最后一行加了自上而下的渐隐遮罩,这层遮罩同样只跟着字数走——上表 700 宽的那 2 条没被截断,最后一行照样被淡掉。

## 2. 修法

- **字数门槛保留,只决定「进不进折叠态」**(`utils/socialClamp.socialClampCandidate`),不再决定按钮。
- **按钮只在折叠态确实截掉了内容时出现**:量正文盒子的内容高与可见高(`clampCuts`,留 1px 给小数行高取整),结果记作 `cut`;`socialMoreVisible` = 进了折叠态 ∧(已展开 ∨ `cut`)。展开之后不再限高、量不出截断,「收起」靠展开状态留着。
- **手机壳的末行渐隐只在确实截断时出现**:限高规则不再自带遮罩,遮罩挂在新增的 `.is-cut` 上(`mobile.css`)。
- **量的时机**(`hooks/useClampCut`):
  - 挂载、回到折叠态、正文换了,各在画出来之前量一次(`useLayoutEffect`),按钮不会先出现再消失;
  - 之后盒子尺寸变了再量(`ResizeObserver`),但不在观察器回调里当场读高度,推到下一帧——见 §4;
  - 盒子没排版时高度读出来是 0(卡片滚出视口后浏览器跳过排版、所在面板收起),这不算结论,留着上一次的结果。

没有动的:哪些推文进折叠态(仍是 360 字)、折叠的行数、按钮的文案与位置、桌面的省略号。

## 3. 同类盘点

- **手机壳长按预览卡**(`SocialPeek`):正文限 3 行,渐隐遮罩常开——只有一行的短推文整行被淡成灰色,看着像被截断。同一条规则、同一个钩子一并修:三行确实装不下才挂 `.is-cut`。
- **其它「展开 / 收起」入口**(管理面的登录记录、反馈处理、自定义节点高级设置):都是按条数或固定区块开合,不涉及截断判定,不动。
- **条目摘要的末行行尾渐隐**(`.reader-entry-excerpt` 及手机壳、早报里的同款):同样不看是否截断,但只淡最后一行行尾 40px,摘要没排到行尾时看不出来;逐行去量要给长列表的每一行加测量,代价与收益要另算。记入 backlog,本波不动。

## 4. 为什么尺寸变化要推到下一帧再量

首版在 `ResizeObserver` 回调里直接读 `scrollHeight` / `clientHeight`。Chromium 下一切正常;WebKit 下「改窗口宽度后再滚动列表」会在控制台报 `ResizeObserver loop completed with undelivered notifications`。

社交卡带 `content-visibility: auto`,滚出视口的卡片不排版。改宽度后往下滚,卡片陆续回到视口、尺寸变化、观察器回调触发;回调里读高度会逼浏览器当场重排,正在进入视口的其它卡片跟着排出来,又产生一批同一层的尺寸变化,这一帧送不完。在未改动的主干页面上注入观察器做对照(WebKit,1440 → 1060 后把列表滚一遍):

| 观察对象 | 回调里做什么 | 报错次数 |
|---|---|---|
| 不注入 | — | 0 |
| 正文 | 空回调 | 0 |
| 卡片 | 空回调 | 0 |
| 正文 | 当场读高度 | 3–4 |
| 卡片 | 当场读正文高度 | 4 |
| 列表栏 | 当场读全部正文高度 | 2 |
| 正文 | 推到下一帧再读 | 0 |

所以回调里只排一帧(`requestAnimationFrame`),量放到下一帧做。代价是改宽度引起的按钮出现 / 消失要晚几帧(尺寸通知 → 下一帧量 → 再渲染;实测见 §5);首次出现仍是画之前量完,没有闪动。

## 5. 边界(有意接受)

- **屏外卡片改宽度后要滚回视口才重判**:跳过排版的卡片不会收到尺寸通知。逐帧实测(1440 → 1060,两张由「排得下」变成「被截断」的卡片,全程不读正文几何以免逼出屏外排版):Chromium 用滚轮滚动时,卡片进入视口前约 15 帧按钮就已改对(浏览器会提前排版视口附近的卡片);Chromium 直接跳到该卡片、WebKit 的两种滚法,都是卡片进入视口后第 3 帧按钮才改对(60 帧下约 50 毫秒)。按钮在正文下方,卡片从底部滚进来时它多半还没进视口。没有为这 3 帧再加同步渲染。
- **展开后把窗口拉宽到「折叠也排得下」**:「收起」还在,点一下收起、按钮随即消失,正文不变。要消掉这一次空点,得在展开态另算「限高是多少」,不值得。
- **不足 360 字但超过 7 行的推文不折叠**(正文里换行很多,或手机壳上的中文推文):这是门槛按字数定带来的另一面,修复前后一样。把门槛也改成按行数,手机壳上会有更多推文被折起来,属于版式取舍,没有在这次修复里顺手改。

## 6. 自测与检视

**自测**

- 沙箱(隔离栈,真实库副本)带断言的走查,Chromium 与 WebKit 各三组(桌面 1440 → 1060 → 1440、手机壳 390 → 700 → 390、手机壳 700 → 390 → 700):折叠态「按钮 ⇔ 确实截断 ⇔ `.is-cut`」,手机壳「遮罩 ⇔ 确实截断」;逐个展开正文都变长、字样变「收起」;全部收起后高度、按钮与原先逐卡一致;首屏不滚动时屏外卡片也判对;改宽度并滚一遍后按钮与新宽度下的截断事实一致、改回原宽度后数量复原;控制台零报错。六组全过。Firefox 在本机沙箱里起不来,没有跑。
- 修复后带按钮的条数:桌面 26(原 30,少掉的正是那 4 条)、手机壳 700 宽 28、390 宽 30,点开全部变长。
- 独立核对(不用钩子的量法,临时去掉限高比较正文高度):两种内核 × 三种宽度,「有按钮 ⇔ 去掉限高后变高」零出入。
- 长按预览卡:28 字的单行推文不再带遮罩;401 字的仍是 3 行 + 渐隐。
- 单元与守卫 `frontend/test/socialClamp.test.mjs` 6 例;反向对照改回 6 处(按钮绑回字数、限高规则自带遮罩、观察器回调当场量、没排版也下结论、取整差也算截断、预览卡不挂 `.is-cut`),6 处都红。首轮有 1 处没拦住——解析样式时没去注释,规则上方说明里的 `.is-cut` 被当成了选择器——已改。
- `npm test` 457 passed;`npm run lint`、`npm run build` 通过。

**检视**

Codex(`gpt-6-astra`,最高推理档;`gpt-6.2-astra` 当天仍不可用)两轮,往返文件在 worktree 的 `.review/`。

- **首轮**:结论「可合入」,没有 P1 / P2 / P3。逐项核对了钩子的清理与依赖切换、屏外卡片与 WebKit 的处理、按钮真值表与 1px 容差、搜索高亮(查询变化会清空列表、卡片重挂,不会沿用旧测量)、手机壳选择器的优先级、桌面规则不受影响。它的只读沙箱里全量前端测试有 5 项因写不了临时文件失败,与改动无关;浏览器排版依据的是提供的走查日志。
- **一条疑问,接受**:§5 原写「读者看到它时已经重判完,最多晚一帧」,它指出走查脚本在滚动前读了全部正文的几何、可能逼出屏外排版,不能当时延的证据。补了一个全程不读正文几何的逐帧脚本,实测下来原话是错的——约 3 帧,Chromium 滚轮滚动时才是提前改对。§4、§5 与 version-history 按实测改写。没有为这 3 帧加同步渲染。
- **复检**:四处改写与证据一致,维持「可合入」。两条观察:帧数是这组样本的观测值,不是跨设备的上限;独立核对的六组输出它没有复现,只确认了方法。
- 它另外提醒的两点同意、不在这次补:94 张卡的走查不能当数百张候选卡片的性能基准;读源码的守卫代替不了清理、依赖切换这类行为测试(本仓前端测试没有 DOM 环境,行为由沙箱走查承担)。
