# 收录推送:推文结构的保真与补全(issue #341)

> **归档于 2026-11-25(issue #341,PR #342,开发版 3.70.5-alpha,纯后端;Codex 两轮检视)**:现状以 `docs/contracts/ingest_push.md`、`src/services/social_ingest.py`、`src/services/social_merge.py` 与 `tests/test_ingest_social_fidelity.py` 为准,文中路径与状态为当时记录。
> 状态:已落地待发布(2026-11-25 开工并当日收口;不改前端、不加迁移、不动同步流)。
> 实现方:Claude Code(Fable 5.2);检视方:Codex(见 §8)。分支 `feat/issue-341-ingest-social-fidelity`。
> 关联:[issue #341](https://github.com/zlzfun/DoramiSourceArchive/issues/341);前情是统一收录入口的 [issue #262](../plans/issue-262-agent-ingest-sources.md)(PR #271)。

## 1. 现象与原因

用户的出发点:Agent 或自定义流程主动把内容推进平台,首个场景是 X 的推文。实际用下来,带引用或带图的推文在读者面还原不全。

用真实接口实测(2026-11-25,主干 `9d4c2eea`):

| 推法 | 回执 | 入库 |
|---|---|---|
| `quoted`、`media_urls` 放在条目顶层 | `created` | 两样都没有 |
| 放进 `extensions` | `created` | 配图留下,`quoted` / `reposted` 没有 |
| 同一条补上配图后重推 | `duplicate` | 没有补上 |
| 先推一条不完整的,抓取器随后抓到完整版 | 抓取侧按重复处理 | 一直是不完整的那条 |

读者面的推文卡片(`frontend/src/components/SocialFlow.jsx`)按 `quoted` / `reposted` / `media_urls` 画;缺了就只剩一段文字,转推显示成转推者本人说了一句「RT @xxx: …」。

三处原因:

1. **载荷收窄**。统一收录入口时(#262,PR #271),社交帖只留了正文、作者和三个扩展键(`lang` / `tags` / `media_urls`)。被它取代的 `POST /api/import/social-posts` 原本接受 `quoted` / `reposted` / 顶层 `media_urls`,没有带过来;#262 的方案与测试都没有覆盖带配图或引用的推文。
2. **静默丢弃**。请求模型忽略不认识的字段,扩展键白名单丢掉其余的键,回执没有任何体现。
3. **同一条再来时一律按重复处理**。存储层对「已有正文」的条目只有两条极窄的元数据自愈路径,扩展字段不会更新——重推补不上,抓取器的完整版也进不来。

本机开发库(旧副本,样本小)里 94 条抓取的推文:带配图 38 条、转推 25 条、引用 14 条,三样都没有的 22 条。

## 2. 范围

1. 接口补回推文的结构化字段,另给「X API 原始 JSON」一种推法;没有被采用的内容写进逐条回执的 `warnings`。
2. 同一条社交帖再次到达时能补全。

只动外网 authority 的后端。不在范围内的见 §7。

## 3. 载荷

### 3.1 两种给法,一个入库形状

`services/social_ingest.prepare` 把一条 `social_post` 载荷整理成社交扩展字段(键与 `SocialPostContent` 一致),并把出处解析要用的 `post_id` / `author` 写回条目。批处理在出处解析之前调用它——作者可能在帖子链接或原始 JSON 里。

- **结构化字段**:顶层 `media_urls` / `lang` / `quoted` / `reposted`。引用帖与原帖用与外层帖子同名的字段描述(`post_id` / `url` / `content` / `lang` / `author` / `media_urls`),入库时转成抓取器归一化的那个形状(`author_name` / `author_handle` / `author_avatar_url(_large)` / `text` / `url` / `media_urls` / `lang`)。没有沿用旧导入入口的扁平形状:一套字段名描述外层与内层,调用方只学一遍。
- **`raw`**:X API v2 的 `{"data", "includes"}`,直接交给 `x_social_normalizer.normalize_x_post_extensions`——时间线抓取器用的同一个函数。

与抓取器保持一致的几处细节:头像派生 `_400x400` 大图;转推时原帖的图并进顶层 `media_urls`、引用帖的图只留在 `quoted` 里;`x.com/<账号>/status/<id>` 链接里能读出的账号与帖子 id 不必再给。

纯转推没有自己的正文时,结构化给法按平台惯例补成「RT @原作者: 原文」:否则这一条 `has_content` 为假,进不了分析评分,也检索不到。

### 3.2 不落库的

- **`raw` 只用来归一化**。`raw_data` 会被社交回填(`services/social_backfill`)当成平台事实重放,连带重写该源的 X 账号缓存——对只登记了 handle 的源,缓存里的 `user_id` 决定抓取器去拉谁的时间线。调用方给的 JSON 不能进这条路。
- **互动数字不收**(结构化给法没有这个字段,`raw` 里的 `public_metrics` 丢弃)。目前没有消费方,但它是「调用方声称的平台事实」,与 #262 剥离系统键是同一条原则。

代价:将来若从 `raw_data` 重放出新的派生字段(短链展开、视频标记),推送来的条目跟不上,除非被抓取版替换(§4)。

### 3.3 校验

- 链接只认 http(s):配图、头像、引用对象的链接不合格的丢弃并提示(`quoted.url` 会被卡片当作 `href`)。
- 引用对象的正文上限 25,000 字(X 长帖上限),超过拒收该条——它随扩展字段一起发给读者列表。
- `raw` 形状不对、缺帖子 id、与顶层 `post_id` 不一致、作者对象的字段不是字符串 → 拒收该条,不影响同批其它条目。
- 账号名清洗后为空(`!!!` 之类)→ 拒收该条。此前身份派生抛出的 `ValueError` 没有被出处解析接住,整批 500;主干上用结构化字段就能触发(检视 R1-1)。

### 3.4 `warnings`

回执逐条带 `warnings`(有才出现),四类:

| 来源 | 例 |
|---|---|
| 模型不认识的字段(含嵌套) | `未识别的字段:likes、quoted.text(已忽略)` |
| 认识、但这一类条目不用的字段 | `文章不使用的字段:author、media_urls(已忽略)` |
| 白名单之外的扩展键 | `这些字段要放在条目顶层,不在 extensions 里:quoted` / `extensions 里未采用的键:metrics(已忽略)` |
| 值不可用 | `media_urls 里有 2 项不是 http(s) 链接,已忽略`、`quoted 需为对象,已忽略`、`已给 raw,这些字段以 raw 为准:content`、`raw.includes.media 里有 1 项的链接不是 http(s),已忽略` |

三种内容类型都有前三类。没有改成拒收:已有调用方多带的字段不该让推送失败。

新增的五个顶层字段(`lang` / `media_urls` / `quoted` / `reposted` / `raw`)在请求模型里故意不收紧类型。它们此前不在模型里、被整个忽略,旧调用方带着形状不对的值也一直能推成功;收紧会让整批 422。形状逐条核对,不对的进 `warnings`。

## 4. 同一条再次到达

`DatabaseStorage._complete_social_post`,规则在 `services/social_merge`:

| 已有的条目 | 再次到达的 | 规则 |
|---|---|---|
| 收录条目(`ingest_channel` 为 push / manual / import),还没有平台原始数据 | 再次收录 | `fill_missing`:只补已有行为空的键;已有行没有正文时补上正文与标题 |
| 同上 | 抓取器抓到同一条 | `adopt_fetched`:正文、标题、发布时间、链接与社交键整体换成抓取版 |
| 抓取入库的条目;已换成抓取版的条目(带 `raw_data.data`) | 任何 | 不动 |

- **只补不覆盖**是提方案时就定下、用户确认的口径。可补的键:作者展示信息、帖子关系 id、语言、标签、配图、引用帖、原帖。引用帖 / 原帖按整个对象补——已有的对象不替换,也不逐项拼合(两次推送描述的未必是同一条)。已有的正文不动:收录时把引用内容拼进正文的,补全后正文里那段还在。已有行没有正文时,正文按同一口径补上,标题随之按新正文取。
- **收录来路的社交帖都先走社交补全,不走通用的补正文**(检视 R1-2)。通用路径整体替换扩展字段并重置到达时间——此前社交帖没有结构可丢,加了结构之后,「先推结构、后补正文」会把引用帖与配图冲掉。抓取入库的社交帖不进这个分支,行为不变。
- **抓取版为准**:抓取版是平台原样。换成抓取版之后条目带 `raw_data.data`,此后不再被任何一条规则改写;再抓一次(互动数字变了)按重复处理,不会每次都改写。
- 服务端写在扩展字段里的键(译文、摘要缓存)不在社交键里,正文没变时两条规则都保留。**正文变了**(补上正文、换成抓取版的正文)就去掉与正文绑定的缓存键(`summary_zh` / `translation_zh` / `translation_zh_social` 及其指纹),与 `paper_fulltext` 换正文时同一做法:读者列表直接取 `summary_zh`、不看指纹,没有新的分析结果时旧摘要会一直显示(检视 R1-3)。标题译文回执按新标题判定。
- 到达时间 `fetched_date` 不动(补全不该让条目重新冒成新到的),修订号 `archive_updated_at` 前进,来路与收录记录保留。
- 保存结果新增 `structure_filled`,归入「已入库」一类:抓取管线据此入队分析(正文变了才真的重算)并预取配图;推送侧回执 `refreshed`,同样触发。推送侧的钩子原来只在新建时触发,现在补正文 / 修元数据 / 补结构都触发——两个钩子对已处理过的条目都是空操作。
- 取锁重读后重新判定一次,与补正文 / 修元数据同一做法(#263)。

只补结构不重算分析:分析输入只读正文(§7 第 2 条),补上的配图也不会回头进配图识别。正文变了(换成抓取版、给无正文的条目补上正文)才重算。

## 5. 被否的做法

- **把 `quoted` / `reposted` 加进扩展键白名单了事**:顶层 `media_urls` 仍然丢、仍然没有提示、形状仍然要调用方自己对齐抓取器的内部键名。
- **未识别字段直接拒收**:最容易被发现,但会让已有调用方的推送失败。
- **重推时覆盖**:Agent 反复推送略有出入的版本会让条目来回变,每次正文变化还要重算分析。
- **存下调用方的 `raw`**:见 §3.2。
- **推送能补抓取入库的条目**:抓取版是平台原样,推送说的引用关系未必对。

## 6. 部署顺序与混版本

只改外网 authority 的收录与入库;内网 replica 的推送入口本来就是 409,这次不变。

- **新外网 + 旧内网**:推送来的推文开始带 `quoted` / `reposted` / `media_urls`——抓取的推文一直带着这些键同步,旧内网的卡片已经会画。补全让条目修订号前进,文章流按修订号重新导出,旧内网按「来者修订号更新就接管」处理,与补正文同一机制。配图经外网预取后走媒体流。没有新的流、字段或枚举值。
- **旧外网 + 新内网**:内网不接受推送,新代码在内网没有触发点。
- **外网回滚**:已补全的条目留在库里,形状与抓取的推文相同,旧代码照常读;回滚后再推的推文回到只留正文的老样子。

## 7. 没做的

1. **服务端按帖子 id 向 X 取全**:Agent 只给链接,平台用自己的 X API 取完整推文。每条约 $0.005 起(引用帖、每张图、作者另计),占 X 月预算;待用户定。
2. **下游只读主推文字**(抓取的推文同样如此):分析评分、全文检索、问答、对外交付的正文都只读 `content`。引用推只按评论那一句打分,转推按「RT @…」打分。改分析输入会让存量推文的分析结果过期,要不要重算是成本问题。
3. **卡片**:引用帖里的图不显示(数据有,没画);视频只有一张静态封面,没有标记;`t.co` 短链是纯文本。
4. **管理面「单条收录」表单**没有引用 / 配图的输入(要目检)。
5. **文章类推送**:正文只认 Markdown,推 HTML 不转换;只给链接、认不出源的文章落在临时源,正文永远是空的;先推后抓时,带正文的推送版胜出(抓取版被当作重复)。
6. 结构化给法不能表达回复关系(`in_reply_to` / `conversation`);时间线抓取本来就排除回复。
7. 引用对象不能由后一次推送升级(已有一个只有链接的引用对象时,带正文的不会替换它)。

## 8. 自测与检视

**自测**

- `tests/test_ingest_social_fidelity.py`(18 例):
  - 保真——原始 JSON 推送与抓取器对同一条帖子的产出逐字段对拍(条目 id、标题、正文、链接、发布时间与全部社交键,只差不落库的 `raw_data` / `metrics`;引用与转推各一例);结构化推送在卡片读的键上与抓取器一致;
  - 回执——未识别的字段(顶层与嵌套)、别的类型的字段、扩展键、非 http(s) 链接、`raw` 与结构化字段并给,各有提示;没问题的条目没有 `warnings`;形状不对的新字段不让整批 422;
