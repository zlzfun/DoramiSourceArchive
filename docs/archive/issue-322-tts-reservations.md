# issue #322 精品导读语音的预留泄漏与预算等待

> **归档于 2026-11-23(issue #322,开发版 3.70.2-alpha,版本号以实际发版为准)**:现状以 `docs/architecture/podcast.md`「精品导读语音的预算记账」与代码为准,文中路径与状态为当时记录。
> 状态:归档(2026-11-23 立项并实现,单 PR)。
> 实现方 Claude Code(Fable 5.2),检视方 Codex(`gpt-6-astra`,ultra)。

## 1. 现象与取证

外网节点自 2026-11-14 起精品导读的语音合成全部失败,错误 `tts_monthly_budget_exceeded`;到 11-23 有二十多期节目的导读停在「合成失败」。当月真实花费 7.52 元,月度预算 20 元。

2026-11-23 生产只读核对(用户授权):

| 项 | 数 |
|---|---|
| 月度预算 / 单次合成预算 | 2000 分 / 200 分 |
| 11 月真实花费(`succeeded` 122 条) | 752 分 |
| 停在 `reserved` 的行 | 140 条:10 月 72 条 624 分 + 11 月 68 条 609 分,共 1233 分 |
| 这些行所属的节目 | 27 期,**每一期都另有一条 `rejected`** |
| 预算合计 | 1985 分——离 2000 分只差 15 分,任何新合成都过不了 |
| `authorized` / `generated`(结果未知) | 0 条 |

`rejected` 集中在 10-13 至 11-09:当时生产配置还指着已退役的模型快照、Key 的模型白名单也没更新,供应商返回 404 / 403(#268,11-09 修复)。那 30 次拒绝留下了这 140 条 `reserved`。11-09 之后合成恢复,成功了 122 段,随后预算就被这些预留顶满。

## 2. 根因

`src/services/bailian_tts.py`:

1. **预留泄漏。** `_reserve` 在合成开始前为这次合成的**全部分段**各写一条 `reserved`;`_synthesize` 再逐段推进 `reserved → authorized →(调用供应商)→ generated → succeeded`。某一段被供应商明确拒绝(→ `rejected`,费用记 0)后抛错退出,**后面还没发出去的分段永远停在 `reserved`**。同一份口播稿再试会先撞 `tts_previously_rejected`,这些行再也没有人碰。
2. **泄漏的预留跨月占预算。** 月度预算合计 = 当期全部行 + **任何月份**里处于 `reserved / authorized / generated` 的行。把跨月的未结算行算进来,本意是保护「结果未知、可能已计费」的调用;但 `reserved` 不属于这一类——它写在 `authorized` 之前,而 `authorized` 写在 POST 之前,**停在 `reserved` 的分段一定没有发出去过**。预留额还按 UTF-8 字节数计(中文约为实际字符数的 3 倍),占得特别多。
3. **预算满即终态。** `fail_premium_guide` 只把两类回执容量不足当作「等待后重试」,`tts_monthly_budget_exceeded` 落为 `failed`;候选巡检不碰 `failed` 的单集。预算不够是暂时的(换月、调额、别的合成结算后都会回来),但这些单集之后不会再被自动拉起。

## 3. 方案

### 3.1 从未发出的预留不占预算

- **本次合成没走完时**:`_synthesize` 在任何异常出口调用 `_release_unsent`,把本次合成里仍是 `reserved` 的行的占用额记 0。这一步尽力而为,写不进库只记日志,不盖住合成本身的错误。
- **预留时顺带清理**:`_reserve` 在同一事务里,把同账号(`account_scope`)下不属于本次合成的 `reserved` 行的占用额记 0。调用方此刻持有回执目录锁,整个合成过程都在这把锁里,别的合成不可能在途,所以这些行一定是被丢下的——覆盖进程被杀等没走到清理的情况,也覆盖生产上历史遗留的 140 条(上线后第一次成功预留时落库,不需要手工改库)。
- **行不删、状态不改**:只把 `cost_minor` 记 0。账本逐行保留,`ck_bailian_tts_status` 不变,无迁移。
- **`authorized` / `generated` 不动**:结果未知或已计费的调用仍按原规则保守计入,并继续拦住同一期节目的后续合成直到对账。

### 3.2 再次合成同一份口播稿时重新计价

`_reserve` 遇到本次合成自己的旧 `reserved` 行(被解除过的,或者进程被杀留下的),按**现在**的账期与价格重新占用:`budget_period`、`cost_minor`、价格快照一并更新。钱是现在花的,记在现在的账期;不这样做的话,占用额为 0 的行会让单次预算与月度预算的检查少算。已经付过费的分段(`generated` / `succeeded`)保持原账期。

### 3.3 月度预算满改为等待重试

`fail_premium_guide` 新增一类 `BUDGET_WAIT_CODES`(目前只有 `tts_monthly_budget_exceeded`):进 `retry_wait`,6 小时后由候选巡检重新拉起,**没有次数上限**。重试时导读博文与口播稿直接复用(`_reusable_guide_text`),预算仍不够就只是再读几行账本,不产生文本费用,也不发出任何供应商请求。

单次合成预算 `tts_per_run_budget_exceeded` 取决于这份口播稿本身,重试不会变,仍是终态。

读者面在等待期间把这类导读显示为「生成中」,与回执容量等待一致(`retry_wait` 归在进行中的状态里)。

### 3.4 已经因预算满失败的那批

旧代码留下的终态:`status=failed`、`failed_stage=synthesizing`、`error` 以 `tts_monthly_budget_exceeded` 结尾。候选巡检用 `is_legacy_budget_failure` 认出它们,各再拉起一次:成功就是 `ready`;预算仍不够就落成 3.3 的等待(换成可读的错误文案,不再匹配),不会被反复拉起。别的终态一律不碰。

## 4. 与既有口径的关系

- **「保留原账本和预占,不通过删账扩大预算」(#268,2026-11-09)**:那是一次运维补生成里的口径——不能为了腾额度去删账。本波没有删任何行,也没有动结果未知的调用;改的是记账语义本身:从未发出的分段没有花过钱,不应该占预算。11-12 的方案里「历史预留不清账」一句由本波取代,原文处加了指针。
- **「#268 暂停的 120 期不自动恢复」**:不受影响。那 120 期的失败原因是旧的回执存储满(109 期)与供应商 404 / 403(11 期),不匹配 3.4 的条件;其中被拒过的口播稿还有 `tts_previously_rejected` 挡着。恢复仍须用户明确指示。
- **预算额度**:本波不动(2000 分 / 200 分)。11-12 授权过的生产月上限 30 元调额仍是另一件事。

## 5. 部署顺序与混版本

`bailian_tts_calls` 是节点私有的计费状态,不随 Archive Sync 传;不涉及同步流字段、枚举、导出范围或删除语义,无迁移。外网按 tag 先上;内网不跑语音合成。新外网 + 旧内网、旧外网 + 新内网都不受影响。导读状态写在文章的 `extensions_json.premium_guide` 里、随文章同步:`retry_wait` 及其 `error_code` 字段是既有取值(回执容量等待早已在用),旧内网认识。

上线后的预期(外网):

1. 第一次成功预留时,140 条历史 `reserved` 的占用额落为 0,预算合计从 1985 分回到当月真实花费 752 分。
2. 候选巡检把因预算满失败的二十多期各拉起一次。文字已发布,只做合成;每期实际几十分,合计在剩余额度之内。合成由回执目录锁串行。
3. 若中途额度再次用完,剩下的落为等待,每 6 小时看一次,换月后自然恢复。

要看的:`bailian_tts_calls` 按 `status` 汇总的 `cost_minor`(`reserved` 应为 0)、日志里 `Podcast 精品导读因语音预算等待重试`、导读状态里 `failed` 且以 `tts_monthly_budget_exceeded` 结尾的应清零。

## 6. 有意不做

- 被供应商明确拒绝过的口播稿(`tts_previously_rejected`)不自动重试。10-13 至 11-09 那批拒绝事后看是配置问题,但「明确拒绝」与「配置修好了」程序分不出来;要重试得换稿或由运维处理。
- 9、10 月因回执存储满失败的一百多期不补做(#268 的暂停批次)。
- 不加管理面的预算占用视图(#178 方案 §9 的建议,仍在那边)。
- 预留额仍按 UTF-8 字节数的保守上界计,结算时按供应商返回的字符数。
