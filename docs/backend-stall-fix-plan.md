# 生产间歇停顿修复（issue #194）

Issue: https://github.com/zlzfun/DoramiSourceArchive/issues/194

草稿 PR: https://github.com/zlzfun/DoramiSourceArchive/pull/195

实现：Codex（GPT-6）；诊断讨论与本地交叉检视：Claude Code，
`claude-opus-5-5`，`--effort max`。基线为 `742326f`（v3.65.1）。
依用户要求，本 PR 不改版本号。

## 证据与归因边界

2026-10-16 生产同机回环请求中，静态首页约 1–3 ms 时，后端健康检查多次超过
12 秒超时；同一进程也有正常窗口，属于间歇停顿。慢窗口线程栈同时捕获到：

- 主线程在 `run_analysis_cycle → scan_analysis_backfill → load_people_page` 同步查库。
- 工作线程在 `pending_premium_guide_candidates → fetchall` 读取全文，持有 GIL。

10 月 15 日旧版本样本中，343 个候选的逐字稿约 286 MiB UTF-8、483 MiB Python
字符串；这是历史样本体积，不能充当 16 日重新测量。运维面板存在同类全文加载，
但不是已捕获慢窗口中的已证实触发者。堆保留、换页会放大停顿，不能把 VmData 与
VmSwap 相加。当前证据不能排除线程池排队或磁盘影响，也尚无生产修复前后对照。

## 实现边界

1. 精品导读候选仅读取选集所需字段，关联博客同样排除正文；`raiseload` 防隐式补读。
   保留权威分析、发布指针、authority、当前 RSS locator、语言、时长、抑制、重试和
   ready 模式判定。
2. 运维面板单集/分析排除正文，逐字稿就绪校验仅查询 id、episode_id、kind。
3. 分析轮次的扫描、领任务、回填对账，以及单项输入/结果/失败持久化，使用
   `asyncio.to_thread`。每个同步函数拥有自己的 Session，只返回 DTO/标量；模型请求、
   semaphore 和并发控制留在原事件循环。调度器配置读取/自动晋级及播客门槛读取同理。
4. 默认识图 provider 的配置/输入/缓存/单图复查和结果持久化同样离开事件循环；
   `get_or_fetch` 链路中的媒体查询、状态提交和 OSS 位置读取同理。单图与 URL 的
   asyncio 锁、semaphore、后台任务集合、视觉请求保留在原 loop。取消识图提交时等待
   工作线程落库完成后才释放单图锁，防止后继请求重复付费。
5. 不改表、提示词、评分、连接池策略、分配器或生产配置。

SQLite 3.40.1 下元数据投影仍可能访问 overflow 页；本次可直接验证的是避免正文解码
和 Python 字符串驻留，不预先承诺磁盘 I/O 收益。若后续仍慢，再测覆盖索引/元数据表
或有界不可变元数据缓存，另行决策。

## 验证与检视

- 回归：候选与 ready/重试/locator/语言分支、面板状态、分析租约/权限/回填与并发。
- 新增 SQL 载荷守卫，保证扫描/面板及关联博客不会 SELECT 正文。
- 新增事件循环响应与 Session 线程归属测试，模拟慢 DB，模型调用保留原 loop。
- 使用独立合成数据库比较候选扫描的内存峰值，避免生产正文与巨型 CI 样本。
- 实现后进行 Claude Code 本地检视，逐条协商并记录结论；用户本地 E2E 与目检放行后
  才可合入。生产复测需要后续正式发布，当前修复不代表已上线。

### 本地实测（2026-10-16）

- 补修后 CI 同范围后端单元回归 `2499 passed`（四个 worker，123 秒）；仅有一条已有的
  Pydantic `dict()` 弃用警告。SQL/事件循环回归模块共
  32 项，包含 locator 变化和没有发布行的反例；另外新增默认视觉 provider 的 8 个
  慢 DB 阶段用例及取消提交期间不重复识图的用例。
- 另补四篇文章同时完成分析并写入相同候选标签的回归，通过；证据数与 7/30 天聚合
  均为 4，未丢更新或出现标签写入失败。
- 合成库：96 个高分、英文、40 分钟的已分析候选，每个逐字稿为
  `"逐字稿内容" * 200000`，总正文 274.66 MiB UTF-8。两版各用独立进程调用同一库，
  只在候选函数期间开启 `tracemalloc`；旧版直接取基线源码，修复版取工作树源码。

| 指标 | 基线 | 修复 |
|---|---:|---:|
| 返回候选数 | 96 | 96 |
| Python 对象分配峰值（tracemalloc） | 194.74 MiB | 5.45 MiB |
| 进程最大 RSS | 316.11 MiB | 126.48 MiB |
| 本次单次调用耗时 | 0.259 s | 0.154 s |

实验环境为本机 macOS / Python 3.12 / SQLite 3.47.1，与生产 SQLite 3.40.1 不同。
耗时包含不同缓存状态，不能用来推断生产 I/O 加速比例；本次结论限于移除约 97% 的
扫描 Python 对象分配峰值。`tracemalloc` 不包含 SQLite 原生分配和 glibc arena 留存。
无真实用户资料或生产正文参与该实验。可复现脚本只创建临时合成库：

```sh
.venv/bin/python scripts/benchmark_podcast_candidate_scan.py --baseline-ref 742326f --episodes 96 --characters 1000000
```

### 本地交叉检视记录

Claude Code（Opus 5.5 / max）核对字段投影、全部面板消费者、事务搬移、回填与候选
聚合后，未发现这些改动的语义或并发回归。候选统计的查询发生在分析记录 flush
取得写锁之后，没有新的同候选丢更新。两项必要意见已逐条接受并与检视方达成一致：

1. 默认识图链路还有同步 SQL，可能与新的分析工作线程争锁阻塞 loop：同批补齐识图
   和媒体供给 DB 边界，保持单图锁内完成提交。使用真实默认 provider、同一测试
   engine、本地图片和桩视觉模型验证 loop 上实际有模型调用、数据库产生识图结果。
2. 检视首次读取方案时实验尚未完成：补齐实测及仓库内可复现脚本，明确对象分配
   与原生内存/I/O 的边界。未把大样本实验放进 CI。

非阻断观察：分析最多四路提交可能加重 SQLite 写锁竞争；生产 2 核默认执行器约
6 个线程，与播客长任务共用，线程阶段可能排队。上线后观察 `database is locked`
失败数、吞吐与健康检查延迟，再决定独立执行器或进程内串行持久化，本 PR 不改这些策略。

定向复检确认上述清单全部闭合，唯一待确认项是完整回归当时尚未打印的一个失败。
该项随后定位为 `test_pending_upload_survives_restart_and_short_cooldown_without_refetch`：
旧断言禁止所有 `to_thread`，把新增的元数据查库线程也判为上传重试。断言调整为
冷却期禁止上传、磁盘上传重试与重新下载（包含 `force=True`），继续验证没有多余源站
请求和云上传。媒体上传重试与对象存储共 21 项通过，满足检视方给出的放行条件；
最终完整单元回归 2499 项全部通过，唯一阻断已解除，补修清单检视完成。
