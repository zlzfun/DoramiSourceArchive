# 推送绑定:登记过的推送是源的一种获取方式(issue #344)

> 状态:进行中(2026-11-25 立项;方向已拍板,§9 的几项待拍板;尚未实现)。
> 实现方:Claude Code(Fable 5.2);检视方:Codex(合入前,见 §11)。分支 `feat/issue-344-push-binding`。
> 关联:[issue #344](https://github.com/zlzfun/DoramiSourceArchive/issues/344);前情是收录推送 [issue #262](./issue-262-agent-ingest-sources.md) 与三层源模型 [重构方案](./issue-262-source-model-refactor.md);上一波 [#341](../archive/issue-341-ingest-social-fidelity.md)。

## 1. 起因

收录推送(#262 波 1)的做法是「平台认出出处,认不出就自动建临时源」。用下来有三个问题:

1. **推进来的内容读者看不到。** 认不出的账号建成临时源:不进发现页、没人订阅,谁的「全部订阅」里都没有;社交帖又不进榜单和兴趣轴。
2. **令牌不分源。** 任何一个 `ding_` 令牌都能带 `source.source_id` 往任何公共源写,包括平台自己抓取的官号源(`x_openai`),也不核对作者是不是这个账号(`ingest_push._check_target` 只查保留 id、形态、私有、退役、下架)。
3. **没有登记的地方。** 「谁在往这个源送内容」只能从条目来路倒推,源管理里看不出一个源有没有 Agent 在推。

## 2. 拍板(2026-11-25,用户)

| | 结论 |
|---|---|
| 抽象 | 抓取还是推送不是源的属性,是源的**获取方式**:推送作为源的一种绑定,与抓取绑定并列,一个源可以两种都有 |
| 落地 | **方案 A**:推送绑定单独一张表,抓取绑定仍在源行上(0 或 1 个);以后需要时再并成统一的绑定表(方案 B,即重构方案 E2) |
| 未登记 | **拒收**:令牌只能往已登记并绑定的源推,不再自动建临时源 |
| 读者面 | 社交媒体等页面与逻辑不变;登记并列入的推送源与抓取源同等对待 |
| Agent 自助登记 | 可以考虑(§8,第二个 PR) |

这改了 2026-11-06 的一条口径。当时定的是「推送 / 手工 / 同步是通道,不是绑定」。现在是:

- **一次性送进来的仍是通道。** 管理员「单条收录」遇到未知出处照旧建临时源,临时源没有任何绑定。
- **登记过、持续送的是绑定。** 当时不设绑定的理由是「平台不知道怎么定期拿到它」;登记之后平台知道了:由这个令牌送来。

条目来路(`ingest_channel` = fetch / push / manual / sync)不变,它记的是这一条经哪条路进来,与绑定是两件事。

## 3. 模型

```
源 1 ──── 0..1 ──── 抓取绑定(源行上的 fetcher_id + params_json)──── 1 抓取器
源 1 ──── 0..N ──── 推送绑定(新表 ingest_bindings)──── 1 收录令牌
```

| | 抓取绑定 | 推送绑定 |
|---|---|---|
| 谁触发 | 平台的采集任务 | 外部调用方 |
| 能否试抓、编进采集任务 | 能 | 不能 |
| 凭据 | 平台持有 | 调用方持有的收录令牌 |
| 记在哪 | 源行 | `ingest_bindings`,只在收录入口所在的节点 |
| 运行记录 | `fetch_runs` / `source_states` | 绑定行上的「最近一批」 |

**为什么不把推送做成注册表里的一个抓取器类**:仓内「有绑定」等于「平台能自己去跑」(重构方案不变量 5)。推送如果是抓取器类,它能被编进采集任务,每次空跑都记成功;而且源行上只有一个绑定位,推送占了,这个源就不能再挂抓取。

**为什么最近一批不写进 `source_states`**:那张表一个源一行。一个源又抓又推时,推送成功会把抓取失败盖住。

### 3.1 表

`ingest_bindings`(迁移一支,纯新增):

| 列 | 含义 |
|---|---|
| `id` | 主键 |
| `source_id` | 绑定的源(索引) |
| `token_id` | 收录令牌 `ingest_tokens.id`(索引);`(source_id, token_id)` 唯一 |
| `created_by` / `created_at` | 谁在什么时候绑定的 |
| `last_pushed_at` | 这个令牌最近一次有条目被这个源接受的时间 |

解绑是物理删除(管理写操作本来就入审计)。吊销令牌不删绑定行,吊销后的令牌鉴权就过不了。

### 3.2 定向源与不限出处的源

- **定向源**:有身份的源。社交源有 X 账号(预设、配置行的 `handle` / `user_id`、身份键表),文章源有站点或 feed,播客源有 feed。定向的社交源只收这个账号的帖子(转推时顶层 `author` 是转推者,即这个账号)。
- **不限出处的源**:没有身份的源,例如「某 Agent 的推荐」。一个源里可以有很多账号的推文。读者面的推文卡片本来就按帖子自己的作者画(`SocialFlow.jsx::postAuthorOf`),不取源的名字和头像。

不加新列:有没有身份由已有的数据推出(X 身份索引 `source_identity.x_identity_index`、身份键表、源行的地址)。

这与「一个 X 账号一个源」不冲突:那条不变量说的是账号源;不限出处的源不是任何账号。

## 4. 推送入口的规则

只改令牌推送(`channel=push`)。管理员会话的「单条收录」(`channel=manual`)完全不变。

设 B = 这个令牌绑定的源。

1. **B 为空**:整批逐条拒收,「这个令牌还没有绑定来源」。
2. **带了 `source.source_id`**:必须在 B 里,否则拒收「这个令牌没有绑定来源 X」。之后是现有的目标校验(形态相符、未下架等)。
3. **没带 `source_id`**:
   - 先按现有的身份解析(作者账号 / feed / 链接)找已有的源,只认 B 里的;
   - 认不出时,B 里恰好有一个形态相符、不限出处的源,就进它;
   - 否则拒收「认不出这一条的出处;请给 source.source_id」。
4. **定向的社交源核对作者**:帖子作者的 `user_id` 或账号名要与这个源的身份对得上,否则拒收「这条帖子的作者不是来源 X 的账号」。
5. 不再自动建源。回执里的 `source_created` 对令牌推送恒为 `false`。

其余不变:条目 id 公式、查重(`duplicate` / `duplicate_url` / `duplicate_content`)、#341 的补全规则、日额度、审计。

条目 id 仍是 `{source_id}_{post_id}`,不限出处的源里帖子 id 在平台上全局唯一,不会撞。

## 5. 登记与绑定(管理面)

### 5.1 登记一个不带抓取的源

`POST /api/admin/ingest/sources`:

| 字段 | 含义 |
|---|---|
| `kind` | `social_post` / `article` / `podcast_episode`,决定源的形态 |
| `name` | 展示名 |
| 出处(可选) | 社交:`handle` / `user_id`;文章:`url` 或 `feed_url`;播客:`feed_url`(必填) |
| `source_id_suffix` | 不给出处(不限出处的源)时必填,源 id 是 `push_<后缀>`(`[a-z0-9_]`,3–40 位) |
| `avatar_url` / `homepage_url` / `description` | 呈现 |
| `listed` | `true`(默认):观察期,进发现页;`false`:待列入(临时源状态) |
| `token_id` | 可选,登记的同时绑定到这个令牌 |

- 给了出处的,源 id 沿用现有派生(`x_<账号>`、`web_<站点>`、`podcast_<主机>_<hash6>`),与抓取器的 id 公式一致;这个出处已经有源时回 409 并给出已有的源 id(直接绑定它即可)。
- 源行 `origin=ingest`、没有抓取绑定(`collection_nodes._UNBOUND_ORIGINS` 已保证这类行不推导默认抓取器)、`legacy_export=false`。
- 已有的临时源不用重新登记:直接绑定令牌,需要进发现页就点「列入」。

### 5.2 绑定与解绑

- `POST /api/admin/ingest/tokens/{id}/bindings` `{source_id}`;`DELETE /api/admin/ingest/tokens/{id}/bindings/{source_id}`。
- 签发令牌时可带 `source_ids`,一步绑好。
- 可绑定的源:存在、不是读者自定源、不是抓取模板、不是公共日报、未退役、不是同步来的行。已下架的源可以绑(推送会被「已下架」拒收,恢复后生效)。
- 平台抓取的源也可以绑(一个源又抓又推):同一条两条路都到时按现有规则合流,推文以抓取版为准(#341)。

### 5.3 界面(运维 → 自定源与收录 → 收录;运维 → 源管理)

待样页拍板(§9-5)。要表达的内容:

- 令牌表每行列出它绑定的源;行内可加、可解。
- 「登记来源」表单(§5.1 的字段)。
- 源管理里,有推送绑定的源在获取方式一列并排显示抓取器与「推送 · 调用方名」,以及最近一批的时间。

## 6. 读者面

页面与逻辑不变。一处文字要改:转推卡片顶上那行现在写「源名 转推」(`SocialFlow.jsx`),在不限出处的源里会变成「某 Agent 的推荐 转推」。改为取转推者本人(`ext.author_name`),没有时才退回源名。这一处对账号源的显示也有影响(源名「X · Sam Altman」变成帖子里的显示名「Sam Altman」),随样页一起目检。

## 7. 部署顺序与混版本

- **不触及同步流**的字段、枚举、导出范围与删除语义。`ingest_bindings` 与 `ingest_tokens`、`article_picks`、`source_identity_keys` 一样只在收录入口所在的节点,不进 Archive Sync。
- 登记的源是普通源行:声明了 `source-catalog-v1` 的内网收到完整源行,与别的源同等;旧版内网收不到这些行(`legacy_export=false`),条目照常同步,表现与今天的临时源相同。
- 内网不接受推送(409),这些规则在内网不生效;两端任意顺序部署。
- 迁移是纯新增的一张表,外网回滚到旧版时多出来的表不被读取。
- **外网部署后现有令牌都没有绑定,推送会被逐条拒收**,直到管理员登记来源并绑定。发版说明要写:部署后先在运维「自定源与收录」给令牌绑定来源,再让 Agent 恢复推送;Agent 的载荷同时要改(带 `source.source_id`,或依赖 §4-3 的规则)。
- 读者面的那一处文字只在前端,随外网与内网各自的版本生效。

## 8. Agent 自助登记(第二个 PR,待拍板)

`POST /api/public/ingest/v1/sources`,字段同 §5.1(没有 `listed` 与 `token_id`)。

- **是令牌的一项权限**(`ingest_tokens` 加一列,签发时勾选,默认不给)。
- **登记的源先是待列入**(临时源状态):内容照收,不进发现页、不算独立信源、不进公共日报;管理员「列入」后与抓取源等同。现有的列入 / 下架 / 改名直接可用。
- **自动绑定到登记它的令牌**。只能新建:出处已经是平台的源时回 409 并给出已有的源 id,由管理员绑定。
- 每个令牌每天登记数量有上限(默认 20)。

## 10. 不做

- 统一的绑定表(方案 B)、把推送登记成注册表里的抓取器类。
- 绑定级的字段要求(例如「这个源的帖子必须带作者头像」)。能由服务端强制的只有内容类型、令牌许可和 §4-4 的作者核对;「原推有引用但没带过来」服务端看不出来,仍然靠回执的 `warnings`(#341)。
- 推送的批次写进 `fetch_runs` / `source_states`。
- 给老读者批量加订阅。默认订阅名单只对新账号生效,这一点不变。
