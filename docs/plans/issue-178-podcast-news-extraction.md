# 从播客提炼文字新闻：设计与评测初稿

> 状态:进行中。2026-11-12，设计初稿，尚未实施或发布；候选规则、版式与验收指标待讨论。上接 [#178 推荐口径修订](issue-178-content-classification.md#6-推荐口径修订2026-11-11实施中)。
> 用户本轮要求：核对本地与现网 TTS 预算；设计播客文字新闻的提炼与布局。配套 [可交互 HTML 样稿](../design/issue-178-podcast-news/index.html)，个人早报、公共日报、候选审核和预算核对四个视图。

## 1. 建议：按事件推荐短新闻，按内容推荐整期节目

读者想迅速知道发生了什么，可以先读一条有依据的短消息；想理解原因、方法或观点，再进入完整节目。音频形式本身既不保证深度，也不排除新闻价值。

提议沿用既有新闻分区，不另设长期的“播客新闻”专栏。新闻属于哪个主题，就进入哪个分区，在出处处标明“来自播客”。整期节目仍在“播客精选”按全文内容价值推荐，两条记录各评各的，不把新闻分写回整期播客，也不拿整期内容分替代事件新闻分。

| 情况 | 文字新闻 | 整期播客推荐 |
|---|---|---|
| 嘉宾披露一个可核验的新发布，其余内容一般 | 事件通过核验后，可按新闻价值入选 | 仍须达到全文内容门槛 |
| 教程、研究方法、复盘深入，但没有新事件 | 可以零条新闻，不能为凑数改写成“发布” | 可按内容价值入选 |
| 热点评论或对未来的预测 | 留作观点，不把预测写成已发生事实 | 根据论证和信息增量评价 |
| 一期同时有新事件与深入讨论 | 新闻正文优先，附整期入口；避免同版双份大卡 | 达到内容门槛才标记“本期也值得听” |

## 2. 初稿案例：Cisco 这期能提炼什么（核验前）

样本为 2026-11-12 本地真实快照中的 The Cognitive Revolution 单集 **Agents That Think Together: Cisco's Vijoy Pandey on Semantic Alignment, Scope, Accord & Concord**，即早报实际选中的一期。

初稿阶段仅核对了当前已发布 ASR 原稿及相邻片段，尚未核验外部发布公告或首发日期。后续已完成外部核验：Accord / Concord 有 10 月版本，不能作为 11 月首次发布，见 §11。因此它现在是**待审核候选**，不是已经成立的“今日新闻”。HTML 的读者视图为假设核验通过后的排版预览，页面持续标明该限制。

| 原稿位置 | 可以支撑的表述（中文转述） | 不能据此声称 |
|---|---|---|
| 42:33.620–42:38.180 | 受访者称已推出两个协议，分别为 Accord 与 Concord | 两者今天才发布；已被独立证实 |

## 3. 读者布局

**个人早报。** 新闻继续按现有版面编排。标题下 100–180 字说清“谁做了什么、为何有关”，元信息保留节目名、节目日期、兴趣命中，补一项“来自播客”。动作是“查看依据”“阅读整期”；音频有无及播放/生成入口继续读当前真实状态，不随早报快照冻结。

**公共日报。** 候选通过相同证据规则，按事件主题进入现有分区，遵守公共来源准入。去掉个人兴趣理由；优先选官方报道作代表，播客提供补充说明。若没有可确认的新事件，公共日报不展示这条候选。

**依据阅读。** 点击“查看依据”打开可返回的原文阅读面，展示中文转述、对应原稿、前后文、节目出处。只有真实 ASR 时间戳才显示时间；只有段落的发布方原稿用段落定位。点击原稿定位不等于播放原音频；“播放导读”播放的是 AI 导读，也不能充当嘉宾原声证据。首版不新增原音频下载、代理或自动跳播能力。

**同版去重。** 同一事件最多一张新闻主卡。同一期若同时满足整期推荐条件，在新闻尾部折叠一个整期入口，不再占一个播客精选大卡名额，空位从下一候选补齐；统计仍分别保留新闻入选和整期推荐资格。单纯提供出处链接不等于推荐整期质量。本规则为本初稿建议，现行代码尚未实现。

**候选审核。** 首版提供独立管理列表：候选标题、事件状态、日期核验、证据、重复事件、发布资格。查看详情后才能决定保留、修订或拒绝；待核验、来源私有、原稿撤回的候选不得进入公共日报。样稿只演示阅读和切换，不提供真实发布操作。

## 4. 输入、提炼与核验

1. 只复用**当前发布指针**对应的完整原稿：发布方全文或 ASR 全文。节目简介、中文导读、翻译稿和历史失效原稿均不能充当唯一证据。没有全文就跳过，本功能不自动触发付费 ASR。
2. 全文按自然段/原生 segments 分块，带相邻上下文；每块输出零到若干候选，再跨块合并。一期最多保留 **3 个待审事件**，允许最终为零。不能只读开头，也不能把同一发布拆成三条凑量。
3. 每条候选绑定主体、行为、对象、已发布/计划/预测/回顾等状态，区分节目日期、录制日期（若有）与事件发生日期。ASR 发言者不可靠时不得仅凭自动 speaker 标签归名。
4. 逐条校验重要断言是否由引用及前后文支持；否定词、条件、数字单位和“第三个”等指代单列检查。稿中含糊时标待核验，不让模型自行补全。
5. 查已有新闻与第一方发布依据，确认新信息、时间和重复关系。可归因的首次当事人披露，也须审核其身份与录制时效，标“某人在访谈中表示”，不冒充独立证实。无法确认时间的候选不进今日新闻。
6. 审核通过后才调用现行新闻评分与主题归类。父播客的全文分 **不作为文字新闻提炼门槛**；已有全文但内容分低于 7.5，也可能含有重要的新事件。

文字提炼不消耗 TTS 预算，但新 LLM 请求并非免费。首轮先人工标注冻结样本，再议有明确次数和费用上限的模型试验；初稿阶段只做离线设计与原稿核对，未调用付费模型；后续用户授权的真实样稿调用见 §11。上线时每期提炼一次、复用候选；不能每位读者编早报时重新调用模型。

## 5. 结构与当前代码的衔接

建议先建立独立候选表，审核发布后再创建有明确派生身份的新闻记录。以下均为提案，不是已存在字段：

| 层次 | 最小字段 / 约束 |
|---|---|
| 候选 | candidate_id、parent_episode_id、parent_source_id、artifact_id/hash、extraction_version、status、event_state、event_time、time_certainty、headline、summary、review_reason |
| 证据 | claim_id、原稿片段定位、必要邻文、归因可靠性、外部第一方 URL/核验时间；原生 segments 用 segment_index/start_ms/end_ms |
| 文本定位 | 若复用 QA 的 range，则同时绑定 projection_version 与投影文本哈希；不能把投影字符偏移直接当原始 JSON 偏移 |
| 发布 | derived_article_id、event_id、reviewer/reviewed_at、新闻评分与版本、继承的来源可见性、withdrawal_reason |
| 幂等 | `(episode_id, artifact_hash, extraction_version)` 唯一任务；同一输入重跑复用结果，改稿产生新候选版本，不静默覆盖已引用内容 |

现有 `EventMemberRecord` 以 `article_id` 关联普通记录，`personal_digest*`、`daily_brief` 和 feed 也消费文章形状。推荐通过新增明确的 `content_type=podcast_news`（暂名）接入，而非假装普通 RSS 文章。其文字形状必须显式优先于父来源的 podcast 形状；`source_id` 仍继承节目来源，避免造一个“AI 新闻源”绕过订阅与来源上限。记录 URL 应指向自己的稳定站内派生页，原节目 URL 单列出处，防止被 canonical URL 去重误并回整期。

仅加一个枚举并不能完成接入。实现前需扫描分类、阅读、检索、评分、事件资格、公共/个人早报、导出与同步的所有消费方，补上新类型的显式行为；建表需 Alembic 迁移。直接把候选对象塞进早报的备选方案虽少写一条文章记录，却会绕开现有事件外键、阅读与订阅契约，不建议首版采用。

代码落点（现有能力与拟新增能力分开）：

| 当前代码 | 可复用 / 所需变化 |
|---|---|
| `podcast_qa.py`、`podcast_text_reader.py` | 当前发布原稿、分块与相邻证据、签名定位；提炼任务和审核候选需新增 |
| `models/db.py` 的 podcast text / event 模型 | 原稿身份与事件外键可复用；候选表、派生身份与撤回关联需新增 |
| `content_recommendations.py`、`public_content_recommendations.py` | 继续控制整期内容推荐；不把派生新闻混成播客推荐 |
| `personal_digest*`、`daily_brief*`、事件层 | 接入审核后的文字新闻；增加父节目血缘去重与可见性检查 |
| 现有早报播客导读组件 | 保留真实生成/播放状态；新新闻卡附整期入口时需要适配，不能直接传新闻 ID 去生成播客音频 |

## 6. 去重、权限与撤回

- 同一官方发布、访谈转述、派生新闻是**同一个事件**。官方稿优先代表；同一节目多个衍生条目、嘉宾跨节目重复讲述不增加独立发布主体数或热度。
- 事件窗口和跨期抑制沿用现行事件层/早报规则，不因“刚提炼”刷新旧新闻时效；新闻发布时间不能取生成时间冒充事件时间。已有事件追加播客解释时不重复推送无变化的事件。
- 首版同一父节目每期早报最多一个文字新闻席位；仍按父 source 计算来源上限。其它已核验事件可在节目详情查看，避免一集拆三条挤占版面。
- 公共发布仅接受公开、准入、当前可见的父节目；个人候选继承原节目订阅与访问范围。**首版不发布私有来源派生新闻**，以后若支持，必须有读者隔离的候选、缓存、检索与交付。
- 原稿撤回/替换、来源隐藏、权限收紧后，重新检查派生内容；失去依据即暂停新分发并撤回当前派生页。早报选篇快照不重排，但读取时执行动态权限遮蔽和失效提示，不允许缓存正文绕过撤回。
- 失败任务不阻塞早报，早报只读取审核通过的已发布产物；关闭功能即停止新提炼/新分发，保留审计、原稿与原有播客。

## 7. 部署顺序与混版本

设计阶段只生成本地样稿，无协议改变。实施分两步：

1. **候选内测**：新增表/任务/管理阅读面，发布开关默认关闭；候选不进入文章流、事件层或 Archive Sync，因此旧节点行为不变。
2. **审核发布**：为派生类型和证据/撤回关联设计显式同步能力，例如 `podcast-news-v1`（暂名）。接收端先具备类型识别、权限和撤回处理；生产端只对声明能力的接收方导出该类型及其必要关联。能力缺失时连同相关分析、事件成员、正文和删除引用一起过滤；不得发普通文章伪装值。

| 组合 | 必须保证 |
|---|---|
| 新外网 + 旧内网 | 默认关闭发布；若面向新读者端开放，也须按接收能力排除旧端相关流，不能只给未知 JSON 键就称兼容 |
| 旧外网 + 新内网 | 无派生记录，原新闻/播客照常，前端缺字段不显示新动作 |
| 新版回滚 | 先关发布；若已分发，先完成接收端撤回或采用已验证的保留读取方案；未经跨版本测试不允许直接回滚成忽略撤回的版本 |

新增分析字段应同步提升既有分析 payload generation。只有全链路混版本回放和撤回验收通过后才开公共发布。现行 #178 推荐增强仍保持原新闻导出契约；此方案是独立后续波次。

## 8. 首轮评测方案

先冻结 **24 期全文**，按首次发布、旧事回顾、深度无新闻、计划/预测/否定、ASR 歧义、跨源重复各选 4 期。中文/英文、长短节目和两种全文来源交叉覆盖；再加权限/撤回的工程固定用例。16 期用于改进，8 期封存后验，不能用同一批反复调优后宣称泛化。

标注者先不看模型答案，写出每期“可以零条”的事件金标、证据、实际日期/不确定性及排除理由。两人独立核对有争议的事实与日期，再定金标；模型输出逐条与金标匹配。候选召回、人工修改率、最终新闻准确率分开报告，零输出也统计，不以多产为成绩。

首轮拟定门槛（不是已达结果）：

| 维度 | 建议验收门槛 |
|---|---|
| 重要断言依据 | 发布候选 100% 有可定位的证据，观测到的无依据重要断言为 0 |
| 状态/日期/归因 | “已发布/未发布”“计划/事实”错误为 0；日期无法确认的候选不发布 |
| 新闻适格性 | 审核前候选精确率目标 ≥95%；同时报漏掉哪些事件与召回率，不能用全不提炼过关 |
| 重复与来源 | 同事件重复主卡为 0；同一血缘不增加独立主体数 |
| 原文阅读 | 所有引用能定位当前版本；虚构时间码为 0；原稿更新后旧定位不误指新文本 |
| 权限与回滚 | 隐藏/私有/撤回全路径泄漏为 0；两种混版本及回滚固定场景通过 |
| 读者体验 | 桌面/390px 手机可读、键盘可操作、查看依据可返回原位置；记录理解耗时与阅读整期意愿，不把点击率当唯一价值 |
| 成本 | 报每期/每条有效新闻的实际 token、费用及审核时间；异常/未知请求不自动重复提交 |

24 期只能给首轮风险信号，不能证明生产错误率低于某个统计上限。通过后先人工审核试运行，再按后验数据决定是否扩大自动化；不预先承诺无人审核发布。

11 月 9 日 17:14 审计记录：历史预留 ¥12.09 + 本批次本地计量 ¥5.33 = 占用 ¥17.42 / ¥20，剩余 ¥2.58；完成 14/134 期，余下 120 期按用户要求暂停。**这些余额与批次数字有时间戳，不是今天实时值；本地计量也不是供应商最终账单。** 仓库/GitHub 搜索未找到更晚的预算变更记录，尚未从现网有效配置及账本实时回读金额。
