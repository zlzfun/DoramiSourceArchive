> 状态:进行中(2026-11-27 样页与 §10 的十二项都已拍板;第一批已实现,见 §14;第二批未动工)。
> 实现方:Claude Code(Fable 5.2);检视方:Codex(合入前,见 §13)。分支 `feat/issue-72-product-registry`。
> 关联:[issue #72](https://github.com/zlzfun/DoramiSourceArchive/issues/72);样页 [`design/issue-72-product-registry/`](../design/issue-72-product-registry/README.md);相邻的两波是三层源模型 [重构方案](./issue-262-source-model-refactor.md)(系统源登记在 `system.toml`)与 [推送绑定](../archive/issue-344-push-binding.md)(源的「获取方式」)。

## 1. 起因

公共日报是平台里唯一一个「定时把站内已有的内容加工成一份新内容」的东西,它在代码和管理面里都是专属的:`services/daily_brief.py` 一个模块、`/api/daily-brief/*` 一组端点、调度里一个固定的 job id、`daily_brief_*` 一组 KV 键、「AI 日报」一个页签,以及散在二十多处的 `source_id == "dorami_daily_brief"`。

想加第二个同类的东西(第一个是「GitHub Trending 精读」:读当天的 GitHub Trending 日榜,挑几个值得看的仓库写成中文)就没有地方放。本波做两件事:

1. 把「登记、开关、定时、手动触发、进度、上次结果」这一层做成共用的外壳,日报成为其中一个**流程**;各流程内部怎么取材、怎么加工仍然各写各的,不抽共用的管道。
2. 加第一个新流程「GitHub Trending 精读」。

issue 是 2026-09-14 开的,正文里的几条前提到 2026-11 已经变了,见 §3。

## 4. 概念

- **流程**:一段登记在代码里的 Python。外壳只认它的几样东西(§6.1);内部各写各的。加一个流程 = 加一个模块 + 在 `system.toml` 加一条系统源,与加一个抓取器同一种纪律(代码即记录,不给读者面开自定义入口)。
- **流程的产出是一个系统源的条目**。日报写 `dorami_daily_brief`,精读写 `dorami_trending_picks`。读者订阅、阅读、feed / MCP 交付都按源走,分发侧不为流程另写代码。
- **系统源的条目不回流**:平台自己加工出来的东西不再当素材——不进公共日报候选、个人早报、榜单、兴趣与 Taxonomy 的取证。现在这条规则只对日报一个 id 成立。

## 6. 第二批:外壳、泳道页、精读

### 6.1 外壳认的东西

一个流程向外壳登记:

| | 含义 |
|---|---|
| `id` | 流程 id,也是调度里的 job id 与后台任务类型(`daily_brief`、`trending_picks`) |
| `name` / `source_id` | 名称;产出写进哪个系统源 |
| `phases` | 一组**有序的阶段**(泳道「加工」一格里那几块:日报是 收集 / 评分 / 精选 / 点评 / 成稿),建议不超过 6 个。它是内部过程的粗粒度投影,不是步骤图:日报的评分与点评是逐条并行、论文走单独名额、推荐是旁路,都在阶段里面。以后有并行或分支的流程,往阶段上加字段(并行路数、可否跳过、节点与连线),已有流程不用改 |
| `default_cron` / `default_enabled` | 缺省定时;新流程缺省关 |
| `knobs` | 旋钮的声明(字段、名称、类型、上下限、缺省值),界面据此画参数行 |
| `read_config` / `write_config` | 读写本流程的配置(带校验);日报的取材范围也在这里 |
| `input_summary` | 「取材」一格的一句话与小字(日报:全部来源 / 自定名单 · N 个来源;精读:日榜的名字 + 最新一条的入库时间,没有新榜单时带警示) |
| `generate` | 跑一次,返回 `status`(`success` / `skipped` / `failed`)与原因 |
| `progress` | 当前阶段 + 阶段内的完成数 / 总数(内存态,只供轮询;日报现有的 `set_progress` 就是这个形状) |

外壳自己管:开关与 cron 的存取、调度的增删、把手动触发交给 `services/jobs.launch`、记上次结果、列表接口。模块放 `services/generation_flows.py`(登记表与外壳),日报的适配写在同一处,精读是 `services/trending_picks.py`。

### 6.2 端点

都在采集侧门控之内(加进 `COLLECTOR_API_PREFIXES`),仅管理员;写操作进审计(前缀加进 `admin_audit.AUDIT_PATH_PREFIXES`,摘要规则 `AUDIT_SUMMARY_RULES` 给配置与生成各加一条);游客白名单不加。

| 端点 | 作用 |
|---|---|
| `GET /api/generation-flows` | 泳道页一次取全:每个流程的名称、源 id、阶段、取材一句话、开关、cron、下次运行时刻、今天这一期(时刻、概况,或失败 / 跳过的原因)、近 7 日每天有没有产出、总期数、旋钮的声明与取值、是否在跑 |
| `POST /api/generation-flows/{id}/config` | 部分更新:`enabled` / `cron` / 本流程的配置。改了开关或 cron 即重排调度 |
| `POST /api/generation-flows/{id}/generate` | 手动触发,返回 `job_id`,终态轮询 `GET /api/jobs/{job_id}` |
| `GET /api/generation-flows/{id}/progress` | 阶段进度 |

往期列表沿用 `GET /api/articles?source_id=…`(现网日报就是这么取的)。

`/api/daily-brief/*` **原样保留**:神灯流水线与 skill 模板指向它;日报的增量游标重置、「取材与去重口径」、流水线说明仍走它。

近 7 日的圆点只分「那天有一期 / 没有」,从条目是否存在推出来;今天的失败与跳过来自上次结果。过去某天的失败不留痕(现网也不留),所以本波**没有新表、没有迁移**。

### 6.3 调度与存储

- 调度:`reload_daily_brief_schedule` 泛化成按流程 id 的一个函数,启动时逐个流程登记;一律经 `add_cron_job`(宽限 300 秒 + 合并,硬规则 8)。日报的 job id 仍是 `daily_brief`。
- 存储:日报的 KV 键(`daily_brief_enabled`、`daily_brief_cron`、`daily_brief_last_run` …)**不改名**;新流程用 `flow:<id>:enabled|cron|config|last_run`。
- 同一个流程同时只跑一次(日报已有的生成锁照旧;精读照做)。
- 用量:精读的调用记在新用途 `trending_picks` 上(登记进 `ai_usage.VALID_PURPOSES`,否则落账会被静默丢掉),定时归 system,手动归触发的管理员,不进读者预算。

### 6.4 日报怎么接进来

薄适配,`services/daily_brief.py` 内部不动:配置读写、生成、进度分别转给现有函数;`extensions.items` 的形状(神灯在用)、三层去重、确定性渲染都不碰。开关即时生效、cron 与取材范围和旋钮一起随「保存配置」提交,都与现网相同。

### 6.5 精读

- **取材**:最新一条 `github_trending_daily` 记录的 `items_json`(仓库、描述、语言、星数、今日新增)。如果这条已经写过精读(精读记录的扩展字段里记着它用的日榜 id),本轮 `skipped`,原因「没有新榜单」。不触发抓取。
- **加工**:辅助模型一次调用,从榜单里挑 `pick_count` 个(缺省 6,1–10),每个给一句中文说明与为什么值得看;`ai_only`(缺省开)时只在 AI 相关的仓库里挑。模型只返回结构化条目,正文由代码渲染(与日报同一个思路:条目是枢纽,Markdown 是渲染)。空返回或解析失败算 `failed`,不落库。
- **产出**:一条 `content_type="trending_picks"`、`source_id="dorami_trending_picks"` 的条目,标题「GitHub Trending 精读 · YYYY-MM-DD」(北京时间的日期),同一天重跑覆盖。扩展字段:`items`(仓库、说明、分组)、`trending_article_id`、`repo_count`、`llm_model`、`generated_at`。
- **不回流**:目录条目 `analysis = false`,源行建出来就不送分析(不评分、不打标);即使管理员在源管理里把分析打开,§5 的名单排除仍然挡住日报候选、个人早报、榜单与取证。内容类型另加进榜单与同源判重的排除名单,默认类型记「汇编」。
- **读者面**:是一个可订阅的源,形态与日报相同(文章)。不进新账号的默认订阅。有了第一期才出现在发现页与源目录里(§10 第 8 项);个人早报的订阅范围不算它。

### 6.6 界面

以样页 `lane.html` 为准,刻度写进 `frontend/src/index.css` 时注「取自 docs/design/issue-72-product-registry/」。

- `App.jsx`:页签 `brief` 的名称改「生成流程」、短名改「生成」;页签 id 与 `#/brief` 不变。
- 新页面取代 `DailyBriefTab` / `DailyBriefPanel`。泳道的一行:名称与源 id、取材的一句话、阶段条、今天这一期与近 7 日、cron 与距下次(只读)、开关、立即生成。行高固定,每格内容以行的中线为准。
- 行上能直接动的只有开关与立即生成。点一行从右侧打开这个流程的抽屉(现成的外壳 `components/layer/Drawer` + `.ledger-scrim` / `.ledger-drawer`):题条是名称、源 id、立即生成、关闭;正文是「配置」框(定时、取材范围、旋钮、增量游标、保存配置)与「往期」框(现有的近期日报列表,生成中时阶段条在它顶上),框沿用 #350 的 `.acq-panel`。「配置」框里参数按 取材 → 定时 → 旋钮 → 游标 一行一个,输入框同宽、字居中、数字框去掉浏览器自带的增减钮。抽屉宽度不改(现网的 470)。

- 零说明句:现网面板里「开关即时生效」「还没有生成过日报。配置好模型后点…」这类句子不带过来(守卫 `explanatorySlots`)。
- 源管理里系统源的获取方式一格从「无抓取」改成「生成」(`utils/sourceAcquisition.js` 加一种取值),检视器里给一个去本页的入口。
- 数据总览的台账现在按 id 排除日报(`DataTab.jsx` 三处 `exclude_source_ids: 'dorami_daily_brief'`),改成排除全部系统源(第一批没有碰前端)。
- 源管理列表里系统源的图标、简介读的是源行,不是目录条目的展示元数据(第一批检视时指出):精读那一行要么建行时把 `icon` / `description` 写进去,要么源管理改读目录条目,第二批定。

- 用户手册里提到「AI 日报」页签的地方(`docs-site/features/integrations.md`)跟着改名。

### 6.7 没有做成通用的

往期每行的概况(日报「收录 33 条 · 模型」、精读「选 6 个 · 榜单 25 个」)由前端按流程 id 各写一个小函数,读各自的扩展字段;不为此给日报记录加字段。

## 7. 部署顺序与混版本

同步流的字段没有变,`ANALYSIS_PAYLOAD_GENERATION` 不动。新出现的只有三样**取值**:一个新的系统源行、这个源的条目、条目上新的 `content_type="trending_picks"`。要分开看两件事:**源行**在升级那一刻就有了——第二批把精读加进 `[[system]]`,启动对账立即建一行,它经源流的目录投影传到接收端,与生成开关无关;**条目**要等管理员打开精读才开始生成。下面表里说的都是「打开精读之后」;只有源行、没有条目时,新旧两端的读者目录都不列它(系统行不是目录元数据的来源),源管理里会多一行。

| 组合 | 会怎样 |
|---|---|
| 新外网 + 旧内网 | 精读的条目会同步到内网。旧内网把它当普通文章:没有分析行(外网不送分析),进不了榜单与早报候选。**但订阅了这个源的内网读者,个人早报会每天等到截止时刻**——旧代码把所有带同步印记的公共源都算作「当天该到货」(`calculate_due_source_ids`),而系统源没有源状态行,永远等不到。源行经目录投影下发;走旧投影的接收端收不到源行,这个源只会以「归档里出现过的来源」出现,名字是原始 id |
| 旧外网 + 新内网 | 内网多一条本机建的系统源行,没有任何条目;按「有了第一期才出现」读者看不到。生成流程页上精读那一行是关着的 |
| 外网回滚到本波之前 | 库里已有的精读条目留着。旧代码的日报候选池只排除日报自己,**会把精读的期当普通文章收进候选并就地评分** |

对应的做法:

1. **打开精读之前,内网先升到含本波的版本**。写进发版说明。
2. 外网要回滚时,先关精读的开关,并在源管理里把这个源设成读者面隐藏(旧代码的候选池认隐藏源)。
3. 合入前做一次跨版本实测,分两步:**精读关着时**,旧接收端收到 `origin=system` 的未知 id 源行,同步不报错、读者目录不多出空源;**打开之后**,收到未知 `content_type` 的条目,同步不报错、阅读器能当文章显示(目前都只是读代码的推断)。

接入了上游的节点不该在本机生成公共内容。日报的定时在接入时已被关掉(#263);精读缺省关,本波不另加围栏。
