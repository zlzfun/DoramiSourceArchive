# issue #318 播客处理的内存与读盘根治

> 状态:进行中(PR-1 读路径瘦身已实现;PR-2 租约路径与去重待做)
> 开发版 3.70.1-alpha,版本号以实际发版为准。实现方 Claude Code(Fable 5.2),检视方 Codex(`gpt-6-astra`,ultra)。

## 1. 现象与取证

2026-11-20 发版核对时发现外网节点长期内存与磁盘压力,当天只读排查(Claude Code 与 Codex 各自独立排查后交叉核对,三轮;原始证据、探针与复现脚本留在排查方本机,不入库):

- 后端进程约 3.4GB(常驻约 0.5GB + 换出约 2.9GB),机器 1.6GB 内存;同一进程 10 分钟稳定在 3.36–3.42GB,不重启不归还(一周内交换区的三次骤降都对上部署重建容器的时间)。
- 一周 7×24 小时磁盘等待 50% 以上,换页很低时也有 40MB/s 以上读盘。
- 下游:`/api/health` 每隔几分钟卡 10–12 秒、空闲翻译 worker 报 `database is locked`、每分钟的周期任务 `was missed`。
- 11-20 当天同一期节目的全文分析连续 100 次租约到期后才成功,随后同一期节目的第二个处理单又循环。

都不是 v3.70.0 引入的。当天 16:55 起外网暂停了播客处理(`DORAMI_PODCAST_PROCESSING_ENABLED=false`)止血:15 分钟内后端回到 143–219MB、磁盘等待 0.33%、健康检查 3–7 毫秒。

## 2. 根因

| # | 位置 | 机制 | 量级 |
|---|---|---|---|
| 1 | `article_analysis.build_topic_heat_context` | 只算近 7 天的标签热度,但三表连接没有时间条件、整行取回,`.all()` 后才在 Python 里按 7 天过滤;开头还整行加载全部公共日报。内存用完释放,但被 glibc 留在各工作线程的堆里(默认线程池 6 个线程各留一份) | 卡住的那期节目召回 32 个标签,连接 23,987 行 / 11,407 篇(全库 17,447 篇),原始文本约 306MB / 次 |
| 2 | `podcast_full_analysis.run_full_analysis_worker_step` | 租约 120 秒,上面的重查询排在「认领之后、第一次续租之前」;用步骤开始时的旧时间检查租约;续租失败不取消分段调用;失败出口无日志、无上限、无退避 | `lease_expired_local_attempt`:9 月 0 次、10 月 11 次、11 月 359 次 |
| 3 | `podcast_premium_guides.pending_premium_guide_candidates` | `load_only` 取的列排在大文本列之后(转写平均 378KB),SQLite 要沿溢出页链走完整段大文本才读得到;每拍 worker 结束都跑 | 实测一次请求读取 339.5MB、实际读盘 780MB、22.6 秒;只取大文本之前的列是 8.9MB、2.1 秒 |

同类隐患:`bailian_tts` 回执回收 `select(ArticleRecord).all()` 整表加载;interval 类周期任务没有迟到宽限(默认 1 秒)。另:第一个处理单产出转写后,自动入队把这份转写当成新输入又建了第二个处理单,重做一份已发布的相同分析。

**一条值得记住的 SQLite 事实**:只取小列不等于不读大文本。列在行里排在大文本列之后时,SQLite 要走完那段大文本的溢出页链才读得到它;`load_only` / 列投影省的是内存,不是读盘。`articles` 里 `extensions_json`、`analysis_authority_id` 等排在 `content` 之后,`podcast_text_artifacts` 里除 `id / episode_id / kind / version / content_hash` 外都排在 `inline_text` 之后。

## 3. PR-1 读路径瘦身

### 3.1 热度查询

- 连接查询只取聚合要用的六列:`tag_id`、文章 `id / source_id / publish_date / fetched_date`、分析 `quality_score`(都排在大文本之前)。
- 公共日报只取 `publish_date / fetched_date / extensions_json`,不再整行。
- SQL 侧加「只多不少」的日期粗筛 `_may_be_seen_since`,与 Python 侧 `parse(publish) or parse(fetched)` 的判定配套:只挡掉两种确定在窗口外的行——
  1. 发布时间是早于窗口的 `YYYY-MM-DD…`,且抓取时间也是早于窗口的 `YYYY-MM-DD…` 或为空;
  2. 发布时间为空,抓取时间是早于窗口的 `YYYY-MM-DD…`。
  其余(紧凑写法、周历写法、脏数据、带前导空白)一律放行,交给 Python 精确判定。
- 为什么是「只多不少」:`parse_article_time` 认的是 `datetime.fromisoformat`,偏移量绝对值小于 24 小时,所以落在窗口内的时刻,其自身时区下的日期不早于「窗口起点再往前一天」;能被解析又匹配 `____-__-__%` 形状的只能是 `YYYY-MM-DD…`,前 10 位就是那个日期。发布时间解析失败时 Python 回退抓取时间,所以条件 1 要求抓取时间同样确定在窗口外。空值先折成空串,粗筛不会因为 NULL 悄悄丢行。
- 没有改的:7 天窗口、来源去重、日报命中、分数取最大、信号按标签代码排序。

### 3.2 精品导读候选巡检

- 主查询的转写只取 `id / kind / content_hash`(排在 `inline_text` 之前)。
- 排在正文之后的 `language / authority_id / source_artifact_id / source_content_hash / provenance_json` 走进程内缓存 `_artifact_tails`:`podcast_text_artifacts` 的行不可变(库里有 BEFORE UPDATE 触发器),每份产物只为它走一次溢出页链。缓存按数据库引擎分开、上限 8192 条。已就绪单集核对导读博文时读的也是这几列,同样走缓存。
- 缓存键是 (产物 id, `authority_id`),`authority_id` 每拍现取。「不可变」只管 UPDATE:单集删除时产物随之删除,之后经 Archive Sync 原样导回会得到同一个 id、不同的 `authority_id`(接收端写成生产者),只按 id 做键会一直给出旧值、把候选漏掉(检视 P2,见 §7)。现取走唯一索引 `uq_podcast_text_artifacts_authority_slot (id, episode_id, kind, authority_id)`,只读索引、不回表;必须用 `INDEXED BY` 点名——按 id 查时 SQLite 默认走主键索引再回表,回表就要走完整段逐字稿(本机 3.47.1 与生产 3.40.1 的查询计划都如此)。SQLAlchemy 不为 SQLite 渲染表提示,这一句写成文本 SQL;索引不可用时退回回表读取并告警(宁可慢,不可错)。
- 巡检降频:`_podcast_premium_scan_due`,每 60 秒一次;本拍 worker 确实推进了工作(有非 `idle` 动作)时立即巡检,所以一次分析落定后不会多等。降频状态是进程级的:`reload_podcast_asr_worker_schedule`(启动时注册 worker)会把它清零,所以重启后的第一拍即使空转也巡检,接续重启前已落定的候选。测试侧 `tests/conftest.py` 有自动夹具让每个用例从未降频的状态开始——第一次全量套件里「重启后恢复已提交的候选」那条用例正是因为前一个用例留下的时间戳而失败。
- 代价:进程启动后的第一次巡检仍要把每份转写走一遍(一次性);`articles.extensions_json` 排在简介之后,每次巡检仍会走单集简介的溢出页(简介是 KB 级)。
- 没有采用的:调整表的列顺序(要重建 324MB 的表)、给尾部列建覆盖索引(依赖规划器选它,且 `provenance_json` 不适合进索引)。

### 3.3 语音回执回收

回收只关心「本账号有成功回执」的文章是否有就绪的 `listen_guide`。改为先取回执,再只查这些文章的 `id / extensions_json`(200 个一批)。判定逻辑逐行未变。

### 3.4 interval 类周期任务的迟到宽限

`interval_job_options`:宽限 = 一个周期,积压合并成一拍。`_ensure_interval_job`、存储巡检、播客 worker、用户自定源刷新四处注册都走它;守卫测试用 AST 检查 `app.py` 里每处 `"interval"` 注册都带统一选项。cron 类仍是 `add_cron_job` 的 300 秒。

### 3.5 验证

- 热度上下文新旧对拍:`tests/test_topic_heat_context.py` 保留改写前的实现作基准,三组随机数据(各 1300 余篇,发布 / 抓取时间遍历 11 种写法 × 53 个时刻 + 12 种脏值,含窗口边界 ±1 秒、±24 小时偏移、日报收录名单的坏 JSON)× 3 种排除对象 × 4 种标签子集,结果逐例相等。造数分两种:每篇文章自成一个来源(来源数 = 计入的文章数,多算少算一行都看得出来)与来源共享(守聚合语义)。第一版只有后一种,反向对照发现它对「少算几行」不敏感(来源数早已饱和),三个改坏的变体照样全绿,补了前一种才守住。
- 合成数据复现(与生产同等体量:17,606 篇、连接 36,623 行、原始文本 325.6MB;glibc 2.36 / Python 3.12 / SQLite 3.40.1,6 个工作线程轮流调用):

  | | 12 次调用 + 一轮 4 路并发后驻留 | 峰值 |
  |---|---|---|
  | v3.70.0 | 2,608MB(其中已释放未归还 2,293MB) | 2,719MB |
  | 修复后 | 113MB | 113MB |

- 候选巡检合成实测(423 份转写、合计 145MB):v3.70.0 每次请求读取 156.1MB;修复后第一次 157.0MB,此后每次 3.7MB(含每拍现取 `authority_id`)。生产库只读核对:该索引存在,点名后查询计划为 `USING COVERING INDEX`,对全部 896 份产物现取一遍读量不到 0.01MB。
- 守卫:取列守卫(语句捕获)、粗筛有效性(窗口外 595 篇不回 Python)、回执回收只点名有回执的文章、宽限与降频。反向对照 23 个改坏的变体全部变红(含检视修复后的 3 个:缓存只按 id 做键、所属方不点名索引、索引缺失时不退回),5 个不该红的对照(缓存上限调大、两处分批改小、巡检间隔改 90 秒、粗筛多留一天)保持全绿。

## 4. PR-2 租约路径与去重(待做)

- 认领后立刻建 attempt,之后的一切耗时都记在这次 attempt 名下;重活在独立会话的线程里做,期间续租照常跑。
- 续租:租约确实失效时立即取消分段调用;一时写不进库(锁)只记日志、下一拍再试。
- 各失败出口有日志。
- 租约到期的本地 attempt:连续次数有界退避、到上限转终态;由重领路径(持有新租约的一方)记账,不放松 fence。
- 自动入队不为「在途处理单自己产出的转写」再建一单。

## 5. 部署顺序与混版本

不涉及 Archive Sync 的流字段、枚举、导出范围或删除语义,无迁移。外网按 tag 先上;上线后把 `DORAMI_PODCAST_PROCESSING_ENABLED=false` 那一行删掉并重建后端容器,恢复播客处理——**预期 PR-1 上线即可恢复**(重查询变轻后,那一期应能在租约内跑完;恢复后先盯这一单),PR-2 是防复发。内网不跑播客付费处理;热度查询只在本机分析播客时才走。新外网 + 旧内网、旧外网 + 新内网都不受影响。

上线后观察一个早间播客批次:进程占用、读盘、`lease_expired_local_attempt` 计数、健康检查耗时。

## 6. 有意不做

- #196 的文章首页类型分面慢查询、列表整行取回。
- 每分钟的分析回填扫描(有界读;页缓存恢复后可缓存)。
- `MALLOC_ARENA_MAX` / 定时 `malloc_trim`:复现里限到 2 个 arena 后顺序调用平台 0.95GB,但 4 路并发仍到 1.8GB;治标。
- 机器扩容:由用户定。修完后 1.6GB 仍装不下 1GB 的库做页缓存。

## 7. 检视记录

### PR-1 首轮(Codex `gpt-6-astra`,ultra)

结论:1 条 P2,其余关注面未发现问题。

- **P2(接受)**:单集删除后原样重导同 id 产物,缓存持续遗漏导读候选。检视方用真实的 `export_page` / `import_page` 与完整触发器做了实证:重导后接收端把 `authority_id` 从空串写成生产者,缓存仍返回旧空串,与新发布指针的所属方不一致,候选被跳过,直到缓存淘汰或进程重启。「UPDATE 不可变」不足以保证 id 跨删除、重建后仍对应同样的尾部元数据。**修法**:缓存键改为 (id, `authority_id`),`authority_id` 每拍经覆盖索引现取(见 §3.2);回归测试 `test_reimported_artifact_with_the_same_id_is_not_served_from_the_cache`。
- 日期粗筛:未发现漏算。检视方另在 Python 3.12.10 下核了 7,523 种日期值、135,398 对组合,没有 SQL 误排除。
- 巡检降频、interval 宽限、回执回收:未发现问题(回执回收 430 个候选新旧对拍一致)。
- 检视方的反向对照:去掉一天余量、不同引擎共用缓存、删除 reload 清零,三处对应测试均变红。

实现方补充的发现:`with_hint` 对 SQLite 不生效(第一版修复的点名没有渲染进 SQL,靠语句捕获的守卫测试发现);`dorami.*` 日志不向根记录器传播,测试里要把捕获器直接挂到该记录器上。
