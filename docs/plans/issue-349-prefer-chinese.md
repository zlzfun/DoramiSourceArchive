# 「优先显示中文」:中文偏好从标题扩到推文,推文入库即译(issue #349)

> 状态:进行中——实现、沙箱自查与交叉检视首轮返修完成,待复检与用户目检。实现方 Claude Code(`claude-fable-5-2`),检视方 Codex(`gpt-6-astra`,本地协商式检视)。

## 1. 背景

设置 → 阅读里的「默认显示中文标题」(issue #218)只管标题:标题在入库时由后台自动翻译,开关只决定显示哪一个。
推文要读者逐条点「✦ 译为中文」(issue #84),每条一次模型调用、计入读者个人 `translate` 日额度(50 次),
译文接在原文下面。社交流里的推文几乎全是英文,开着中文偏好的读者进到社交流看到的仍是整屏英文。

用户 2026-11-26 提出:把这枚开关扩成中文偏好,开着时读者看到的推文直接是中文。

## 2. 拍板(2026-11-26)

| 项 | 结论 | 被取代 / 被否的 |
|---|---|---|
| 译文来源 | **入库即译**:新推文入库后由后台自动翻译,走系统预算,不扣读者额度;抓取入库与推送入库都要覆盖 | 读者看到时再译(第一次看到要等,且要么扣个人额度、要么另设额度);#84「不自动翻译」、#218 R2「社交正文仍手动」 |
| 呈现 | **中文替换原文**:正文与引用推直接显示中文,卡片底栏标明是译文并可一键切回原文 | 原文与译文都显示(卡片高度接近翻倍);#84「原文下追加、不替换」 |
| 开关文案 | 「优先显示中文」;沿用现有账号偏好(默认开,游客存本机),字段名仍是 `prefer_chinese_titles`、不加迁移 | 「中文偏好」「默认显示中文」 |

文章正文、播客简介与逐字稿仍由阅读页手动切换,不在这枚开关的范围里。

## 3. 后端

### 3.1 入队:挂在写入层,不分入库方式

`services/social_translation.py`,做法对齐标题自动翻译(`title_translation`):

- SQLAlchemy `before_flush` 钩子:新的 `social_post` 记录,或 `content` / `extensions_json` 有改动的 `social_post` 记录,
  在**它自己的事务里**写一行待办 `social_translation_jobs`(回滚即一起消失,提交后才可领取)。
- 待办按「需要翻译的那几段原文」的指纹(`source_fp`,与译文缓存 `translation_zh_social.fp` 同一口径:主推——转推取原推全文——
  与引用推)去重。指纹没变的写入(译文缓存、标题回执、配图、阅读数)不重排;原文变了才换指纹、尝试次数清零。
- 初始状态:没有要译的文字(中文 / 纯链接 / 纯表情)→ `skipped`;同一份原文的译文已在缓存里 → `succeeded`;
  两段原文合计超过 6000 字(个别超长 note tweet)→ `skipped`,留给读者手动翻译;其余 `pending`。
- 指纹没变也重排的唯一情形:待办记着已完成、译文却被别的写入冲掉了。
- **不回填存量**:首次启动记水位 `auto_social_translation_started_at`,之后只处理新记录与原文的后续变化。存量推文(没有待办行)
  上的无关写入不入队;只有能从属性历史里读出旧值、且需要翻译的原文确实变了才入队。
- 同步来的条目(`analysis_authority_id` 非空)、归档导入事务(`session.info` 的抑制标记)、不可外送的来源不建待办——与标题同一套围栏。

### 3.2 各入库方式(用户点名要兼容的部分)

抓取、推送、手工收录、导入,以及 issue #341 的两条补全规则,最终都是经 ORM 写 `ArticleRecord`,所以钩子不需要认识它们:

| 入库方式 | 发生了什么 | 待办 |
|---|---|---|
| 抓取器抓到新推文 | 新记录 | 入队 |
| 推送 / 手工收录一条新推文 | 新记录 | 入队 |
| 同一条再次被推送,补上引用帖 / 原帖(`fill_missing`) | 扩展字段变,需要翻译的原文多了一段 | 换指纹重排;旧译文指纹对不上,读侧不再给 |
| 同一条再次被推送,只补配图等 | 扩展字段变,原文没变 | 不动 |
| 抓取器抓到已被推送的同一条(`adopt_fetched`) | 正文与社交键整体换成抓取版 | 原文不同则换指纹重排;只是顶层「RT @…」包装文字不同、原帖全文没变时,已有译文保留(`_complete_social_post` 丢弃与正文绑定的缓存后,把仍对得上新原文的推文译文放回去) |
| Archive Sync 拉来的推文 | 带上游印记 | 不入队(上游已译的随扩展字段一起到) |

对应用例在 `tests/test_auto_social_translation.py` 末尾两条(走真实的收录接口与抓取管线)。

### 3.3 派发、预算与门控

- 后台 worker(`worker_loop`,随应用生命周期起停,不分运行角色):每次只派发一条,调用复用
  `reader_ai.translate_social_post`——提示词、单元协议、结构校验、「原文变了不落缓存」只有一套。译文写进既有缓存
  `extensions_json.translation_zh_social`,与读者手动翻译是同一份。
- 模型:辅助模型、明确关闭思考(与标题自动翻译同一档)。
- 计量:独立用途 `auto_social_translate`,归 system;预留 / 核销表 `social_translation_calls`,每日上限
  `auto_social_translation_daily_tokens`(默认 300,000;`0` = 暂停),总闸 `auto_social_translation_enabled`(缺省开)。
  不扣读者额度,不占标题自动翻译的预算。核销按**实际发出的请求**:一个请求都没发(缓存命中、原文已变)即释放;发出的请求里
  有任何一个没有回执,到的回执照记、整笔预留留到当天结束。自动路径不让客户端内部重试(`max_retries=1`)。
- 门控:AI 全局总闸、模型已配置、来源可外送、条目属于本机;读者自己发起的正文翻译任务在跑时让路。领取时、**落缓存前**各判一次
  (途中被上游接管、开关被关掉的结果不发布)。
- 占用:待办带占用期与占用者 token(`lease_until` / `lease_token`),占用期 180 秒、在途每 30 秒续租。多个应用进程同时只放行
  一个自动请求(看的是「有没有未过期的占用」);续租、发布前复核与收尾都认 token,失去占用即取消在途调用;进程中途退出后到期
  自动回到可领取。
- 一次领取只为它领的那份原文付费:请求带着领取时的指纹(`translate_social_post(expected_fingerprint=…)`),读到的原文对不上
  就不调模型。原文在途中变了,钩子按新指纹重排但不动占用;在途方收尾时交还占用,新指纹的待办随即可领。
- 失败:每条最多 3 次,指数退避;闸门 / 预算 / 让路不计尝试次数。
- 读者先手动译了某条:worker 领到时发现译文已在,直接记完成,不调用、不建预留。

### 3.4 列表带回译文

带正文的推文条目(`serialize_article_list_item`,社交流列表、收藏、单条)多一个字段 `social_zh: {text, quoted} | null`——
与 `title_zh` 同一做法:服务端只在缓存指纹仍对得上**当前**原文、流程版本一致时才给,不需要翻译的一侧为 `null`
(`reader_ai.cached_social_translation`;「哪份缓存算数」与归档同步的本机缓存保留共用一个校验函数 `social_translation_entry_valid`)。前端不自己校验缓存。显示已有译文不要求账号开通 AI(与标题一致)。

## 4. 前端

- 设置 → 阅读:行名与 `aria-label` 改为「优先显示中文」(桌面设置柜与手机设置栈同一组件)。
- 推文卡(`SocialFlow.jsx`,桌面与手机壳共用):译文**原位替换**原文,一次只显示一种语言——
  - 有译文 + 偏好开 → 正文与引用推显示中文,底栏「✦ 已译为中文 · 原文」;点「原文」整卡换回原文,底栏变回「✦ 译为中文」;
  - 有译文 + 偏好关 → 显示原文,底栏「✦ 译为中文」,点了直接换上(不发请求、不需要 AI);
  - 没有译文 → 显示原文;AI 可用时底栏「✦ 译为中文」(行为同 #84,译好后同样原位替换),不可用时不出底栏;
  - 读者在某张卡上切过,这张卡就不再跟偏好走,直到原文变了或页面重载。
- 判定是一处纯函数 `utils/socialTranslate.socialCardView`,卡片、长按预览卡、右键 / 长按菜单(「显示原文」/「译为中文」)
  都从它推导,各自带上所在列表的搜索词(订阅推入页是另一个列表实例、没有搜索)。换语言的开关不重新推导,只认调用方
  交给它的那份视图——同一条推文在搜索结果与推入页里的默认语言可以不同。
- 搜索时的例外:搜的词只在原文里、译文里没有,这张卡默认显示原文(否则看不出它为什么被搜到)。
- 「原文下追加」的译文块(`.social-tr` / `.social-quote-tr`)整体退役;换语言的那一下,换上来的文字淡入(遵守应用内减少动效开关)。
- 手机壳上「原文」只有两个字,点击区横向扩到 44 宽。

## 5. 部署顺序与混版本

1. **跨节点契约**:没有新增或改动。译文缓存沿用 `translation_zh_social`(格式不变),随现有 `articles` 流同步,也照旧随 feed
   交付的 `metadata.extensions` 外传——只是带着它的推文变多。每条预译会让那条推文多一次修订。新增的两张表只在本机,不参与同步。
   内网神灯流水线只读日报 `extensions.items`,不受影响。
2. **两个窗口**:
   - 新外网 + 旧内网:内网照常收到译文缓存,旧前端不主动显示;读者点「译为中文」命中缓存,不调模型、不扣额度。
   - 旧外网 + 新内网(或外网回滚):没有预译到达,推文显示原文与「译为中文」,与现状一致。内网不会替上游的条目翻译;
     内网自己采集 / 被推送的推文由内网的 worker 翻译(需内网配置了模型)。
   - **同步协议上的兼容不等于数据库可以直接回滚。** 本波带一条迁移(`e349b6d2a8c1`),升级后的库不能直接配旧代码启动;
     回滚按既定流程([`ops/release-process.md`](../ops/release-process.md)「回滚」):切回上一 tag **并**恢复部署前的库备份,升级之后
     入库的内容与译文缓存随之丢失(外网之后重新采集;已同步到内网的那部分缓存不受影响)。这与任何带迁移的版本相同。
3. **两个方向都兼容,对部署顺序没有要求。** 因为内网晚于外网升级,这段时间差里外网已把最近几天的推文译好,内网升级当天
   读者看到的就是中文——等于免费的存量回填。
4. **验证**:没有改同步流的字段 / 枚举 / 导出范围 / 删除语义,未做跨版本实测;围栏(同步条目不入队、导入事务不入队、
   入队后被上游接管即作罢)有单测。

**一个时序上的观察点**:预译是逐条串行的(一条数秒)。内网每天同步一轮,如果外网的 X 采集任务正好排在内网同步之前几分钟,
这一批里没译完的推文会晚一轮(次日)才带上译文,期间内网读者看到的是原文与「译为中文」;预算用完或积压较大时不保证只晚一轮。
发版后看一眼外网 X 采集的时刻与内网同步时刻的间隔,不够就把采集任务往前挪。

## 6. 成本

每条推文一次调用(超长的两次):提示词约 550 字 + 原文 + 等量译文。本机开发库 94 条推文平均 277 字,估每条不到 1000 token;
生产上每天的条数未查(需要授权读库)。默认每日上限 300,000 token,超出后当天暂停、待办保留、次日继续;用量在
管理面「AI 用量」里以「自动推文」单列。

## 7. 不做 / 遗留

- 存量回填(见 §5 第 3 点的时间差);管理面的预算 / 开关界面(与标题自动翻译一致,走 AppSetting);
- 文章正文、播客简介 / 逐字稿的默认中文;
- 超长推文(> 6000 字)的自动翻译;
- 读者手动翻译与 worker 恰好同时翻同一条时可能各付一次(手动路径没有租约,窗口是一次调用的时长);
- 管理员的社交元数据回填如果改变了某条存量推文「要不要翻译」的判定,那一条会入队——量小、受每日上限约束,不另拦;
- 停服恰好落在「领取」提交的那一刻:留下一笔当天的预留(约 3k token)与一个最长 180 秒的占用,下次启动自动回收(标题自动翻译有同类窗口)。
