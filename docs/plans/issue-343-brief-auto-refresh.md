# 个人早报：新内容落地后自动补编（#343）

> 状态:排队中。方案待拍板(2026-11-25),尚未开始实现。实现方 Claude Code(Claude Fable 5.2);检视方待定(按流程交 Codex)。
> 待拍板项在 §9;§4–§8 按 §9 的推荐项写,拍板有变再回改。

## 1. 问题

在从上游同步内容的节点上,个人早报常年显示「部分来源更新尚未完成，按当时已有内容编排」;点「重新编排」后提示「已开始重新编排今日早报」,而请求返回时新一版已经换上页面。

2026-11-25 用上游节点的访问日志与后端日志核实的时间线(接收节点每天同步一轮):

| 时刻 | 发生了什么 |
|---|---|
| 07:00–08:00 | 上游六个每日采集任务陆续启动 |
| 08:30 | 上游公共日报生成;**接收节点个人早报定时编排**(`personal_digest_schedule`,时刻写死) |
| 09:05 | 接收节点开始同步;文章、分析、事件在第 1 分钟内落地 |
| 09:06 起 | 图片(3–15 分钟)、播客文本、播客音频(近两天 26–51 分钟) |
| 09:08–10:20 | 源状态最后落地(近 7 天的范围) |

由此得到三件事:

1. 08:30 那版用的是前一天同步进来的内容,并且必带提示。读者不在内容落地后手动重编,全天看到的都是前一天的内容。
2. 提示看的是「每个订阅源今天是否完成过一次采集」(`_source_readiness`),这份状态是每轮同步的最后一条流。内容落地到状态落地之间重编,内容是新的,提示仍在。用户当天在状态落地后重编,提示消失,说明没有个别源常年不就绪的问题。
3. `handleRebuild` 不看返回状态,固定弹「已开始」;而 `POST /api/reader/briefs/today/rebuild` 是同步生成的。

「重新编排」按钮现在替系统干活,而读者无从知道什么时候该按。

## 2. 目标与不做

目标:

- 新内容落地后,系统自动把当天早报补编到位,读者不需要操作。
- 读者面去掉常驻的「重新编排」按钮和「部分来源更新尚未完成」提示行。
- 重编完成后的提示按返回状态说话。

不做:

- 不改 Archive Sync 的流、字段、枚举与拉取顺序(把源状态挪到图片之前能让标记更早变准,但本方案不依赖它,记 backlog)。
- 不改 08:30 定时与「打开即生成」(v3.48 去等待的口径不变)。
- 不恢复「改兴趣 / 订阅就自动重编」(v3.51.1 的口径不变);「立即重编」「重试生成」两处保留。
- 不让早报变成全天滚动更新:自动补编以上午为限(§9-2)。

## 3. 现状要点(实现依据)

- 两个标记 `sync_stale` / `analysis_incomplete` 是生成时刻的事实,任一为真版面状态即 `degraded`;v3.48 起不再等待,只记录。
- 重编原因属于 `REBUILD_REASON_VALUES` 才会开同日新版本;`ensure_first_personal_digest_edition` 遇到已有版本直接复用,所以早于 08:30 打开过的读者,08:30 定时不会给他换版。
- 跨期抑制(`_recent_edition_article_ids`)只看更早日期的 ready / degraded 版,同日前一版不影响补编选篇。
- `superseded` 版本已被「最新版」查询、往期列表、跨期抑制排除;按日期 + 版本号精确读取仍能读到。
- `first_open_at` 目前只在「这次打开创建了版本」或机器人接口 ensure 时写入;读者打开一个已存在的定时版不会写。
- 接收节点在 `remote_sync:state` 里按流记本机时钟的 `completed_at`。同步进来的分析行带的是上游时间,不能拿来和本机的编排时刻比。
- 早报页挂载时 `ensure` 一次;只有版本处于 pending / generating 时才每 8 秒轮询。
- 机器人接口(`docs/contracts/admin_reader_briefs.md`)线上不带编排原因;`degraded_reason` 在没有显式原因时由两个标记派生。

## 4. 设计

### 4.1 系统侧:补编规则

在既有的 30 秒任务 `execute_personal_digest_pending_job` 里,恢复卡住版本之后加一步「补编巡检」。

**落地信号 L**(本机时钟,取两者较晚):

- 同步:`analyses` 流的本机完成时刻;协商了 `events` 且本机没有跳过它时,取两者较晚者。
- 本机分析:最近一次本机分析成功的完成时刻(同步进来的分析行不算)。取分析表的本机时间列还是由分析 worker 记一条 KV,实现时定。

**一轮巡检:**

1. 当前时刻已过当天 12:00 → 结束。
2. L 不存在,或不晚于已处理水位(KV,记上一轮处理到的 L)→ 结束。这是全局短路,平时每轮只有两三次小查询。
3. 距 L 不足 3 分钟 → 结束,等内容到齐再动(同步的几条流、相邻的采集任务会连着来)。
4. 对每个启用账号(含游客保留账号)取今天最新一版 E。以下情况跳过:没有版本;E 不是 ready / degraded;E 上挂着排队的重编意向;E 两个标记都为假;E 的生成时刻不早于 L。
5. 其余的按当时的订阅、兴趣与就绪事实重新选篇:
   - 条目(文章与分区顺序)与 E 完全相同 → 什么都不写。
   - 不同 → 落成新版本,原因 `content_arrived`,两个标记按当时事实重算;随后补中文标题(同现有流程)。
6. 全部账号处理完,把水位写成 L。中途失败不写水位,下一轮重来;已补过的账号因生成时刻晚于 L 自然跳过。

**终止性:** 补编版的生成时刻晚于 L,只有再来一批新内容才会再动;12:00 之后不再动。每天一轮同步的节点,每人每天最多补编一次。

**为什么用落地信号而不用「就绪」:** 就绪要等源状态,而源状态排在图片和播客音频之后,2026-11-25 比内容晚 74 分钟;个别源当天没被上游采到时就绪永远不成立。落地信号两种情况都不受影响。

**标记仍然有用:** 标记为假的版是在内容齐备时编的,当天不再动,早报不会变成滚动更新。接收节点上标记通常为真(状态晚到),所以实际效果是「上午每轮同步落地后补编一次」。

**成本:** 补编那一轮相当于再跑一次 08:30 的全员编排(选篇只读库,标题中文化有缓存)。本机分析信号要先按读者范围过滤,避免某个读者的自定义源每小时更新一次就让全员重算。

**并发:** 与读者同时点「立即重编」撞版本号时,以唯一约束失败的一方放弃,下一轮再评估。

### 4.2 被顶替的那版怎么处理

- 读者没打开过 E → E 标 `superseded`,不进往期。读者当天只看到一版。
- 读者打开过 E → E 留作上一版,读者能从往期看到两版。

「打开过」用 `first_open_at` 判断,为此读者打开一个已存在的版本时也要写它(现有 `_reuse_edition` 就是这个行为,让 `ensure_first_personal_digest_edition` 的复用分支走它)。机器人接口 ensure 写的 `first_open_at` 同样算打开过:那一版已经推给人了。

版次显示改为「当天可见版本里的第几个」,不直接用库里的 revision,否则隐藏一版后会出现只有「第 2 版」「第 3 版」的情况。

### 4.3 读者面

- 去掉页头「重新编排」按钮(桌面 `bp-lbtn`、手机页头两处)。
- 去掉「部分来源 / 文章分析尚未完成，按当时已有内容编排」提示行。
- 保留「你的兴趣 / 订阅已更新，下次编排生效 · 立即重编」与失败态的「重试生成」。
- 今日端点的版本载荷加一位 `refresh_pending`(今天这版还可能被系统补编:带标记且未过 12:00)。为真时页面每 60 秒取一次今日版本;发现比页面上更新的版本时,在眉头下出一行「今日早报已更新 · 查看」,点了才切换,不在读者眼前换内容。
- 游客同样适用(游客没有重编入口,这次起能自动拿到当天内容)。

不出样页:改动是删两处、加一行,新增的一行沿用现有提示行的样式;目检在沙箱里做。

### 4.4 提示文案

`handleRebuild` 按返回状态提示,文案放进 `frontend/src/utils/briefRebuild.js`:

| 返回状态 | 提示 |
|---|---|
| ready / degraded | 今日早报已重新编排 |
| pending / generating | 不弹(页面已有「新的编排请求已记录」或生成中状态) |
| failed | 重新编排失败，请重试(错误样式) |
| empty_subscriptions | 不弹(页面自会说明) |

### 4.5 编排原因值

新增 `DigestGenerationReason.CONTENT_ARRIVED = "content_arrived"`,加入 `REBUILD_REASON_VALUES`;配一条 Alembic 迁移改 `ck_personal_digest_editions_generation_reason`。枚举里有一个没被使用的 `recovery`,不借用:原因值是给排查看的,借用会让「为什么多了一版」查不清。

## 5. 消费方盘点

| 被动到的东西 | 消费方 | 影响 |
|---|---|---|
| `sync_stale` / `analysis_incomplete` | 早报页提示行;机器人接口的 `degraded_reason`;版面状态 | 语义不变。提示行删除;机器人接口取值不变;新增「系统据此决定是否还补编」 |
| `first_open_at` | 读者端点透出;`deadline_at` 的历史计算(已不门控生成);机器人接口 ensure | 含义从「创建该版的那次打开」扩为「第一次被取走的时刻」。实现时再 grep 一遍前端与测试 |
| `superseded` 的新来源 | 最新版查询、往期列表、跨期抑制 | 既有过滤都已排除它;带旧版本号的精确读取不受影响 |
| `generation_reason` 新取值 | CHECK 约束;服务层枚举 | 迁移同波;线上契约不带这个字段 |
| 今日端点新字段 `refresh_pending` | 早报页 | 只加不改;旧前端忽略 |
| 页头按钮与提示行 | 用户手册 `docs-site/features/brief.md`、`guide/quick-start.md`、`reference/markers.md`;`docs/frontend/conventions.md`;登录页文案里提到「重新编排」的一处 | 同波改 |

机器人接口另有一点要告知对方(只走文档):接收节点上 08:30–内容落地之间取到的是前一天内容编的版,落地后几分钟内会换成新版;推送时刻放在同步之后更合适。契约本身不变。

## 6. 部署顺序与混版本

个人早报的版本不随 Archive Sync 传,本方案不改任何同步流、字段、枚举、导出范围与删除语义。

- **新上游 + 旧接收端:** 上游节点上规则同样生效(上游的定时版在采集与分析没跑完时也带标记),只影响上游自己的读者与游客版。接收端无变化。
- **旧上游 + 新接收端:** 接收端只读本机的同步进度,不要求上游任何新能力;对任何能完成 v2 同步的上游都成立。
- **回滚:** 接收端回滚到旧版本前要先降迁移(CHECK 约束),否则旧代码读到 `content_arrived` 的 pending 行会报错——补编不产生 pending 行(直接落成终态),风险只在迁移本身。回滚后自动补编停止,旧前端的按钮与提示行都还在,行为回到现状。
- **先后端后前端(同一节点内):** 第一批只上后端时,旧前端的提示行与按钮照常工作,只是读者不必再按;没有中间态问题。

## 7. 分批

- **第一批(后端):** §4.1、§4.2 的后端部分、§4.5、今日端点的 `refresh_pending`。没有可目检界面,按纯后端口径走检视 + 全量套件 + CI。合入后接收节点升级即可拿到「自动补编」。
- **第二批(前端 + 手册):** §4.3、§4.4、版次显示、`docs-site` 三处。沙箱目检后合入。

## 8. 测试与文档

后端(造数据一律相对时间):

- 落地信号:同步完成时刻晚于版本生成时刻才触发;不足 3 分钟不触发;过 12:00 不触发;水位未变不重算。
- 同步进来的分析行(上游时间早于本机编排时刻)不影响判断——用本机完成时刻。
- 条目相同不落新版本;不同才落,原因为 `content_arrived`。
- 标记都为假的版不补编;failed / pending / generating / 挂着排队意向的不补编。
- 被顶替版:没打开过 → superseded;打开过 → 保留;机器人 ensure 过的算打开过。
- 游客版、仅兴趣(无订阅)版、订阅为空的账号。
- 中途失败不写水位,下一轮续上且不重复补已补过的账号。
- 迁移:`upgrade heads` 与 `create_all()` 一致;降级可回。
- 既有的 `sync_stale` 相关用例与机器人契约基线原样通过。

前端:`briefRebuild` 提示映射的单测;说明文字守卫(explanatorySlots)过;沙箱里用两版数据目检「已更新 · 查看」与版次显示,亮暗与手机壳各一遍。

文档同波:`docs/architecture/analysis-and-briefs.md`(补编规则写进不变量)、`docs/decisions.md`(改写「读者可感知的重编入口只剩手动与次日 08:30」一行,新增本方案的拍板 / 不做 / 触发)、`docs/backlog.md`(源状态拉取顺序、12:00 与 3 分钟两个常数是否做成配置)、`docs/version-history.md`、`docs-site` 三处。

## 9. 待拍板
