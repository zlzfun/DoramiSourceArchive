# 个人早报：全自动编排，读者面不留重编入口（#343）

> 状态:排队中。方案待拍板(2026-11-25),尚未开始实现。实现方 Claude Code(Claude Fable 5.2);检视方待定(按流程交 Codex)。
> 2026-11-25 用户口径:读者不需要做任何操作,一切自动——「立即重编」「重试生成」也取消。待拍板项在 §9;§4–§8 按 §9 的推荐项写,拍板有变再回改。

## 1. 问题

在从上游同步内容的节点上,个人早报常年显示「部分来源更新尚未完成，按当时已有内容编排」;点「重新编排」后提示「已开始重新编排今日早报」,而请求返回时新一版已经换上页面。

2026-11-25 用上游节点的访问日志与后端日志核实的时间线(接收节点每天同步一轮):

| 时刻 | 发生了什么 |
|---|---|
| 07:00–08:00 | 上游六个每日采集任务陆续启动 |
| 08:30 | 上游公共日报生成;**接收节点个人早报定时编排**(`personal_digest_schedule`,时刻写死) |
| 09:05 | 接收节点开始同步;文章、分析、事件在第 1 分钟内落地 |
| 09:06 起 | 图片(3–15 分钟)、播客文本、播客音频(近两天 26–51 分钟) |
| 09:08–10:20 | 源状态最后落地(近 7 天的范围) |

由此得到三件事:

1. 08:30 那版用的是前一天同步进来的内容,并且必带提示。读者不在内容落地后手动重编,全天看到的都是前一天的内容。
2. 提示看的是「每个订阅源今天是否完成过一次采集」(`_source_readiness`),这份状态是每轮同步的最后一条流。内容落地到状态落地之间重编,内容是新的,提示仍在。用户当天在状态落地后重编,提示消失,说明没有个别源常年不就绪的问题。
3. `handleRebuild` 不看返回状态,固定弹「已开始」;而 `POST /api/reader/briefs/today/rebuild` 是同步生成的。

读者面现在有四个要读者自己判断的重编入口:页头常驻的「重新编排」、未就绪提示后的「重新编排」、改了兴趣 / 订阅后的「立即重编」、失败后的「重试生成」。前两个读者无从知道什么时候该按;后两个系统自己就知道该不该做。

## 2. 目标与不做

目标:**读者面不留任何重编入口,今天的早报由系统在三种情况下自动换版。**

- 新内容落地。
- 读者改了兴趣或订阅。
- 生成失败。

不做:

- 不改 Archive Sync 的流、字段、枚举与拉取顺序(把源状态挪到图片之前能让标记更早变准,但本方案不依赖它,记 backlog)。
- 不改 08:30 定时与「打开即生成」(v3.48 去等待的口径不变)。
- 不让早报变成全天滚动更新:因新内容而换版以上午为限(§9-2)。

推翻的旧口径:v3.51.1「兴趣与订阅变更只记录不重编,读者可感知的重编入口只剩手动与次日 08:30」。当时要解决的是连点几个标签就连开几个版本、版本列表成了流水账;本方案用「静置合并」和「旧版不进往期」解决同样的两件事(§4.2、§4.4)。

## 3. 现状要点(实现依据)

- 两个标记 `sync_stale` / `analysis_incomplete` 是生成时刻的事实,任一为真版面状态即 `degraded`;v3.48 起不再等待,只记录。
- 重编原因属于 `REBUILD_REASON_VALUES` 才会开同日新版本;`ensure_first_personal_digest_edition` 遇到已有版本直接复用,所以早于 08:30 打开过的读者,08:30 定时不会给他换版。
- 版本行上有一组「排队意向」字段(`desired_generation_reason` / `desired_requested_at`),30 秒任务每轮扫描并落成下一版(`materialize_desired_personal_digest_revision`);终态版本上挂意向也在扫描范围内。
- 跨期抑制(`_recent_edition_article_ids`)只看更早日期的 ready / degraded 版,同日前一版不影响选篇。
- `superseded` 版本已被「最新版」查询、往期列表、跨期抑制排除;按日期 + 版本号精确读取仍能读到。
- 接收节点在 `remote_sync:state` 里按流记本机时钟的 `completed_at`。同步进来的分析行带的是上游时间,不能拿来和本机的编排时刻比。
- 失败:`BriefRuntime` 一个版本内最多尝试 2 次、20 分钟内,之后落 `failed`。只有游客版有系统重试(打开时触发、10 分钟冷却,`_retry_failed_guest_edition`)。
- 首登兴趣引导首次完成时就地重编一次(#56),结果经 `brief_rebuild_status` 回给前端弹提示。
- 早报页挂载时 `ensure` 一次;只有版本处于 pending / generating 时才每 8 秒轮询。
- 机器人接口(`docs/contracts/admin_reader_briefs.md`)线上不带编排原因;`degraded_reason` 在没有显式原因时由两个标记派生。

## 4. 设计

### 4.1 新内容落地 → 补编

在既有的 30 秒任务 `execute_personal_digest_pending_job` 里,恢复卡住版本之后加一步「补编巡检」。

**落地信号 L**(本机时钟,取两者较晚):

- 同步:`analyses` 流的本机完成时刻;协商了 `events` 且本机没有跳过它时,取两者较晚者。
- 本机分析:最近一次本机分析成功的完成时刻(同步进来的分析行不算)。取分析表的本机时间列还是由分析 worker 记一条 KV,实现时定。

**一轮巡检:**

1. 当前时刻已过当天 12:00 → 结束。
2. L 不存在,或不晚于已处理水位(KV,记上一轮处理到的 L)→ 结束。这是全局短路,平时每轮只有两三次小查询。
3. 距 L 不足 3 分钟 → 结束,等内容到齐再动(同步的几条流、相邻的采集任务会连着来)。
4. 对每个启用账号(含游客保留账号)取今天最新一版 E。以下情况跳过:没有版本;E 不是 ready / degraded;E 上挂着排队意向;E 两个标记都为假;E 的生成时刻不早于 L。
5. 其余的按当时的订阅、兴趣与就绪事实重新选篇:
   - 条目(文章与分区顺序)与 E 完全相同 → 什么都不写。
   - 不同 → 落成新版本,原因 `content_arrived`,两个标记按当时事实重算;随后补中文标题(同现有流程)。
6. 全部账号处理完,把水位写成 L。中途失败不写水位,下一轮重来;已补过的账号因生成时刻晚于 L 自然跳过。

**终止性:** 补编版的生成时刻晚于 L,只有再来一批新内容才会再动;12:00 之后不再动。每天一轮同步的节点,每人每天最多因新内容换版一次。

**为什么用落地信号而不用「就绪」:** 就绪要等源状态,而源状态排在图片和播客音频之后,2026-11-25 比内容晚 74 分钟;个别源当天没被上游采到时就绪永远不成立。落地信号两种情况都不受影响。

**标记仍然有用:** 标记为假的版是在内容齐备时编的,不再因新内容而动。接收节点上标记通常为真(状态晚到),所以实际效果是「上午每轮同步落地后补编一次」。

**成本:** 补编那一轮相当于再跑一次 08:30 的全员编排(选篇只读库,标题中文化有缓存)。本机分析信号要先按读者范围过滤,避免某个读者的自定义源每小时更新一次就让全员重算。

### 4.2 读者改了兴趣或订阅 → 跟上

- 兴趣写入、订阅 / 退订 / 合集批量 / 自定源增删这些写入点(v3.51.1 之前触发重编的同一批位置),在读者今天最新一版上记一条排队意向:原因 `interest_changed` 或 `subscription_changed`,时刻为当前。今天还没有版本就什么都不记,首版本来就按最新的编。
- 30 秒任务扫描意向时加一条静置:意向时刻距今不足 30 秒的先不动。读者连点几个标签、连订几个源,每次写入都把时刻往后推,停手后 30–60 秒落成一版。
- 落成前复核:当前兴趣版本与订阅范围和这一版冻结的是否真的不同(`edition_freshness`)。改了又改回来 → 只清意向,不出新版。
- 不受 12:00 限制:这是读者自己改的。
- 退订到一个源都不剩且没有兴趣:沿用现有重编口径,当日版本清成空订阅状态。
- 首登兴趣引导(#56)的就地重编保留不动:那是读者做完引导、马上要看结果的一步,不等静置。
- 游客版跟默认名单、管理员下架来源的全员重编:已是系统触发,不变。

### 4.3 生成失败 → 自动重试

- 今天最新一版是 `failed` 时,30 秒任务按「距上次失败 2 / 10 / 30 分钟」各重试一次,当天最多 3 次,原因用枚举里现成而没被使用的 `recovery`(加入 `REBUILD_REASON_VALUES`)。
- 游客版现有的「打开时重试、10 分钟冷却」并入这条规则,不再单列。
- 重试成功后,当天此前失败的版本标 `superseded`。
- 页面:还有重试机会时显示与「编排中」相同的状态并轮询;用尽后显示失败状态,没有按钮,往期照常可看。

### 4.4 被换下的版本

**一律标 `superseded`,不进往期;当天只有一版可见。** 被换下的版本要么是内容没到齐时编的,要么是按读者已经改掉的偏好编的,要么是失败的,都没有回看的价值。

- 条目是不可变快照这一点不变:被换下的版本不改不删,只是不再列出;阅读窗「返回我的早报」带着旧版本号回来仍能读到。
- 往期里已有的多版本日期照旧显示;新的日期不会再出现「共 N 版」。
- 机器人接口取「最新的非 superseded 版」,口径不变。

### 4.5 读者面

去掉:

- 页头「重新编排」按钮(桌面 `bp-lbtn`、手机页头两处)。
- 眉头下的三种提示行:「部分来源 / 文章分析尚未完成…」「你的兴趣 / 订阅已更新,下次编排生效 · 立即重编」「新的编排请求已记录…」。
- 失败态的「重试生成」按钮。
- `handleRebuild` 及其提示(「已开始重新编排今日早报」随之消失)。

保留:游客那一行(登录引导);「编排中」状态;失败用尽后的失败状态(无按钮);首登引导完成后的提示(它本来就按返回状态说话)。

**页面开着时换了新版:** 今日端点的版本载荷加一位 `refresh_pending`(系统接下来还可能换版:§4.1 的条件成立、挂着 §4.2 的意向、或 §4.3 还有重试机会)。为真时页面轮询今日版本——挂着意向或等重试时沿用现有的 8 秒,等新内容时 60 秒。取到更新的版本后:

- 页面停在页首,或读者刚切回这个页面 → 直接换成新版。
- 读者正在往下读 → 不打断;回到页首或下次回来时再换。

不出提示行,不需要读者点任何东西。

读者端 `POST /api/reader/briefs/today/rebuild` 保留(前端不再调用,排查与脚本可用),是否删除记 backlog。

不出样页:读者面只做删除,没有新增元素;目检在沙箱里做。

### 4.6 编排原因值

| 情况 | 原因值 | 说明 |
|---|---|---|
| 新内容落地 | `content_arrived` | 新增;配一条 Alembic 迁移改 `ck_personal_digest_editions_generation_reason` |
| 兴趣 / 订阅改动 | `interest_changed` / `subscription_changed` | 已有,已在重编原因集合里 |
| 失败重试 | `recovery` | 已有、未使用;加入重编原因集合,不需要迁移 |

## 6. 部署顺序与混版本

个人早报的版本不随 Archive Sync 传,本方案不改任何同步流、字段、枚举、导出范围与删除语义。

- **新上游 + 旧接收端:** 上游节点上规则同样生效,只影响上游自己的读者与游客版。接收端无变化。
- **旧上游 + 新接收端:** 接收端只读本机的同步进度,不要求上游任何新能力;对任何能完成 v2 同步的上游都成立。
- **回滚:** 接收端回滚到旧版本前要先降迁移(CHECK 约束)。因新内容换版不产生 pending 行(直接落成终态),失败重试与偏好改动走既有原因值,风险只在迁移本身。回滚后自动换版停止,旧前端的按钮与提示行都还在,行为回到现状。
- **先后端后前端(同一节点内):** 第一批只上后端时,旧前端的按钮与提示行照常可用;读者改兴趣后会看到「新的编排请求已记录」约半分钟到一分钟,随后自动换版、提示消失。没有卡住的中间态。
