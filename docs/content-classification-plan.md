> 状态:**第一波已合入**(#180,2026-10-12);**第一波补已合入**(#181,2026-10-12);**第二波检视通过、待用户验收**(分支 `feat/issue-178-content-value`,见 §3)。
> 结论与可视化见 [issue #178](https://github.com/zlzfun/DoramiSourceArchive/issues/178)
> 和样页 [`docs/design/dorami-classification-scores-quiet.html`](./design/dorami-classification-scores-quiet.html)

## 0. 拍板(2026-10-12)

1. **定位**扩展为「资讯 + 值得深读 / 收听」。
2. **双评分**:每条内容都打两个分。**新闻价值**(这件事有多重要)保留现有 `quality_score`,定义、数值、门槛不变;
   **内容价值**(值不值得花时间读或听)新增,标准随内容类型变化,所有类型都有领域相关性上限(与 AI 无关最高 4.9),
   播客现有附加尺迁入内容价值。这推翻了 issue #22(2026-09-07)「只留一把尺子」的拍板,理由写在 issue #178。
3. **条目级内容类型**:资讯 / 论文 / 教程 / 观点 / 版本更新 / 项目 / 汇编;体裁 `content_genre` 拆成「内容类型 + 事件类型」。
4. **公共日报**继续收少量论文:论文名额仍 3 篇,改为从内容类型为论文的条目里按内容价值挑选(第三波)。
5. **个人早报**新增「深度阅读」「播客精选」(第三波)。
6. **阅读器**:每条显示一个主分(内容类型决定默认维度,新闻价值 ≥ 8.5 时以新闻价值为主);评分卡里 AI 速读不变,
   分数下方小字标当前维度,点分数切换维度,悬停分数显示该分数的评分依据(第二波)。条目挂类型签,列表头加类型筛选(第一波)。
7. **左轨撤销「动态」并入「文章」**,版本更新用紧凑行(第一波)。
8. **维度收口**:`content_type` 只是数据结构、不再当分类展示;`category` 拆出准入状态后退役;源级 `content_tags` 退役;
   标签与映射表合一。对外说法:文章 / 播客 / 社交是「呈现形态」,「类型」专指内容类型。

## 2. 第一波

### 2.1 词表与推导

单一事实来源 `src/services/content_classification.py`:内容类型 / 事件类型 / 体裁 / 数据结构四张中文名表,
体裁 → (内容类型, 事件类型) 映射,个人早报板块与公共日报分类两张分区映射,以及判定规则。

判定序(`classify_item`):

1. **来源先验**:抓取器类属性 `default_kind`。HF Daily Papers → 论文;8 个 changelog / release notes 与 3 个
   GitHub Release 源 → 版本更新;2 个 HF 模型、1 个 GitHub 仓库、1 个 GitHub 趋势源 → 项目;日报源 → 汇编。
2. **数据结构兜底**:只对没有来源先验的源(配置源、历史 / 导入源、未设 `default_kind` 的注册源;`github_release` → 版本更新,模型卡 / 仓库 / 趋势 → 项目,`arxiv` → 论文)。
3. **链接形状**:arXiv / OpenReview / HF papers 链接 → 论文。只认 URL 开头的「协议 + 主机 + 路径」前缀(`PAPER_URL_PREFIXES`),
   查询串或片段里引用的论文地址、相似域名都不算;社交帖、播客、日报不套用,它们的链接指向自身。
4. **体裁**:`research_paper` → 资讯 + 研究成果(分析看到的是讲研究的内容,不一定是论文原文);`tutorial` → 教程;
   `opinion` → 观点;`aggregation` → 汇编;其余 → 资讯 + 对应事件类型。
5. 都没有(通常是分析未完成)→ 未判定,读者面按资讯处理(不挂签)。

事件类型只对资讯 / 版本更新 / 项目填写。

**为什么读取时推导、不落库**:所有输入(源 id、链接、数据结构、体裁)都已入库并随归档同步到接收节点,两端同一份代码
算出同一结果,零迁移、零回填、同步协议不动;分析版本不变也就不触发重跑。SQL 镜像只有一份:`kind_expr` 是按判定序排列
WHEN 的 CASE 表达式(体裁用相关标量子查询),筛选取它的 IN(`kind_condition`),分面按它 GROUP BY 一次聚合。
它与 Python 推导共用规则表,`tests/test_content_classification.py` 在由规则表生成的穷举组合(源 × 数据结构 × URL × 体裁,
含无分析行)上逐条对拍。第二波大模型给出的内容类型落库后,作为额外输入同时接进 `classify_item` 与 `kind_expr` 即可。

### 2.2 接口

- `GET /api/articles` 列表 / 详情 / 收藏的条目新增 `kind`、`kind_label`、`kind_basis`、`event_type`、`event_label`、
  `content_genre_label`、`content_type_label`(中文名由后端下发,前端不再维护映射表)。
- 新参数 `kind=paper,tutorial`(CSV,任一非法值即 400,在任何查询之前校验)与 `kind_facets=true`:附带当前范围
  (不含 kind 自身)的各类型计数 `[{kind, label, count}]`,筛选带的选项来自它(约定 §6「选项来自聚合端点」)。
  分面只随分页对象返回,所以 `kind_facets=true` 隐含 `include_total=true`;两者都不传时默认响应仍是数组。
  代价:真实库副本(7194 篇,文章容器 4307 篇)全范围请求约多 17ms,订阅范围下差异在抖动之内;合成数据 10 万篇全范围时,
  一次 GROUP BY 约 183ms(原先六次 COUNT 约 362ms)。用于筛选时 CASE 比原先的 OR 分支慢(同组合成数据计 tutorial
  89ms → 135ms),换取 SQL 镜像只有一份,检视时双方同意这一取舍。
- `GET /api/articles/facets` 的 `content_types` 每项附 `label`(数据结构中文名)。
- `GET /api/reader/sources` 每个源新增 `default_kind` / `default_kind_label`(发现页源卡、日报名单用)。
- 字段名用 `kind` 而非 issue 里写的 `content_kind`:后者已是自定源的源级字段(article|podcast),避免同一接口面二义。

### 2.3 「动态」并入「文章」

- 15 个原 bulletin 源(另 3 个模板)的 `content_shape` 回到默认 article,改设 `default_kind`。
- `api/sources.normalize_shape`:入参 `bulletin` 视同 `article`。用在 `/api/articles`、`mark-all-read`、`mark-scope-read`、
  `favorites` 四个入口——**不能把 bulletin 当未知值忽略**,否则旧客户端的 `mark-all-read?shape=bulletin` 会把全部订阅
  (含社交)标读、列表混进社交与播客(测试锁定)。其余非法值分两类处理:两个标读端点是写操作,返回 400 且不写任何读态;
  列表与收藏是只读查询,沿用既有的宽松处理(视为不过滤)。
- 未注册的历史源按数据结构兜底时,版本发布 / 模型卡也归文章容器(此前会落到不存在的容器)。
- **榜单口径不变**:`rankings._source_shapes` 把来源先验为版本更新 / 项目的源标为 excluded,继续不进文章榜与必读榜;
  配置源(如绑定 `generic_github_releases` 的公共源)按其预期数据结构求类型,同样排除。
- **批量订阅**:「订阅全部文章源」随形态合并纳入原动态源(前后端同口径),待验收确认。
- 管理面节点目录去掉「动态」页签,计数量词按来源先验(版本更新 / 项目用「条」);日报名单的「· 动态」改为类型名。

### 2.4 读者面

- 条目行:源名后挂内容类型签(`.reader-entry-kind`,沿 `.reader-entry-tag` 细线语法,墨色提一档),资讯不挂;
  与主标签同名时主标签让位。主标签兜底从体裁中文名改为事件类型。播客行同样挂签(教程 / 观点类播客的提示不因此丢失)。
- 紧凑行由内容类型决定(版本更新):`.is-bulletin` 改名 `.is-compact`,与文章混排。
- 筛选带 `.reader-kind-band`:列头下,仅文章容器;单选,再点取消;选项只列计数 > 0 的类型(选中项除外)。
  选中值绑定在当时的作用域上:切容器 / 源 / 轴 / 收藏的同一帧即失效(不先发「旧类型 × 新范围」的请求),并永久清除——
  返回原作用域不复活;按 id 打开文章(深链、引用跳转)也退出类型筛选。
- 按类型筛选时收起列头的「全部标读」:标读按源水位推进,会连同没显示的其它类型一并标掉。右键 / 长按里的「该源全部已读」
  是显式的源级动作,与兴趣透镜下同一菜单项口径一致,不随类型筛选收起(会连同该源其它类型一并标读)。
- 分析轮询:每次列表加载(首页 / 翻页 / 整窗重拉)都让列表版本 +1,轮询整次提交前核对,期间有过加载的旧轮询整体作废
  (不回滚新条目、不重复累加分面)。不筛选时,已加载条目的类型变化按增量修正分面计数。按类型或标签筛选时,在途条目
  不在本轮响应(同一窗口)里即视为窗口成员变了——可能改判出了范围,也可能被补位挤出窗口,而翻页可能已拿到服务端的新总数——
  不在本地移出或扣总数,改为静默重拉同一窗口、带总数与分面的快照整体替换。未加载条目的变化等下次列表加载。
- 阅读窗眉头「源 · ___」:非资讯写内容类型,资讯写事件类型。
- 移动端:底部 Tab 去掉「动态」;筛选带放在列表顶(顶栏须单行,e2e 有约束),横向滑动。
- 发现页:形态筛选 5 档 → 4 档;源卡「动态」签改为来源的默认类型(论文 / 版本更新 / 项目)。

## 2b. 第一波补:`category` / `content_tags` 退役

### 2b.1 拆分

源级 `category` 一个字段挤着三件事,逐个盘点消费方后拆开(注册表 69 个节点:38 个 `incubating`,7 个 `advanced`
与 `is_template` 完全重合,其余是 official_doc / official_web / product_update / primary / official / community / media 等角色值):

| 原职责 | 原表达 | 现在 |
|---|---|---|
| 准入状态(观察期) | `category = "incubating"`,注释写「转正后改回 X」 | **`admission_status`**:`admitted` 正式(默认)/ `incubating` 观察期。注册源是抓取器类属性,配置源是同名列 |
| 节点用途(通用模板) | `category = "advanced"` / `"workflow"` | 现有的 `is_template`(`workflow` 已无节点) |
| 来源角色 | official / media / community … | 不再记录;角色一直由 `services/source_naming.source_role`(前端 `sourceRoleOf`)推导 |

准入状态的消费方:每日采集脚本(排除观察期与模板)、节点管理「观察」徽记、源健康接口与节点目录。
转正:注册源让该类的有效值成为 `admitted`——类上自己声明观察期的删掉那一行,观察期继承自父类的(7 个 X 预设)在具体类上写
`admission_status = "admitted"`(删父类那一行等于整批转正);配置源 `PUT /api/source-configs/{id}` `{"admission_status": "admitted"}`。
播客精选目录新建行时设为观察期,之后的目录重导不改写(此前每次导入都把 `category` 重置为 incubating,转正无从谈起)。
规范化 `admission_status_of`:未知值按正式处理,不让拼错的值把节点悄悄挤出每日采集。

### 2b.2 退役范围

- **抓取器**:删除全部 `category` 与 `content_tags` 类属性(63 处)、三个通用模板参数表里的「业务分类」、
  RSS / 播客 / 网页模板的 `category` 运行参数;配置源调度不再把 `category` 塞进抓取参数。
- **条目标签**:不再写入源级 `category`、`content_tags` 和抓取方式字面量 `webpage`,只保留源站自带的标签(feed term、
  WordPress 分类、站点标签)。历史条目不做主动的全库或批量标签改写。正常的播客元数据刷新、空正文补齐仍沿用既有更新规则;本次重新抓取并进入这些路径的历史条目,可能按新规则更新标签,即使发布方 feed 本身未变。实际持久化字段发生变化时会推进归档同步 revision;相同输入收敛后,不会仅因本次标签退役反复产生更新。播客刷新继续保留原有的空值保护,部分旧标签可能留存。影响范围取决于实际抓取窗口、limit 和更新条件,不扫描全库(codex R1 #2 协商结论)。
- **接口**:注册表元数据、源健康、节点目录、读者源目录、配置源 CRUD 不再输出 `category` / `content_tags`,
  改输出 `admission_status`(配置源列表的 `?category=` 过滤换成 `?admission_status=`);MCP `list_sources` 去掉
  `category` 键(它把内部的 incubating 状态暴露给了外部客户端;仓库内与 IM 机器人均无消费方)。
  旧客户端提交的 `category` / `content_tags` 被接口静默忽略。
- **读者源目录 / 管理端内容看板的 `category`**:这是另一个概念(数据结构中文名),原映射表与第一波的
  `CONTENT_TYPE_LABELS` 重复且把 RSS 叫「RSS 资讯」;改用同一张词表(「RSS 条目」「网页条目」「GitHub 仓库」…),
  删除 `api/sources.CONTENT_TYPE_CATEGORY`。仓库内无消费方。
- **AI 自定义节点生成器**(前端入口关闭):提示词、启发式基线与 LLM 合并不再产出这两个字段。
- **前端**:「观察」徽记改看 `admission_status`;节点检视器去掉内容标签行(`.inspector-tags` 样式删除);生成器表单去掉两个字段。
- **每日采集脚本**:`--exclude-category` 参数删除(`--include-advanced` 语义不变:同时纳入模板与观察期节点)。

### 2b.3 数据库与同步

- 迁移 `c6413eda8931`:`source_configs` 只加列 `admission_status`(NOT NULL,默认 `admitted`),把 `category='incubating'`
  的行映射为观察期;SQLite 原生 ADD COLUMN,不重建表。降级用原生 DROP COLUMN 去掉新列。
- 旧列 `category` / `content_tags_json` **暂留、不再读写**:表上挂着 7 个归档同步触发器,SQLite 删列要重建表并重装触发器,
  留给后续结构清理一并做(见 backlog)。
- 归档同步 v2 的 sources 流:去掉 `content_tags_json`,加入 `admission_status`,并保留**线路兼容键 `category`**——由准入状态
  派生(观察期为 `"incubating"`,正式为显式的空串),不读退役列。接收端规则:payload 有 `admission_status` 键时以它为准;
  键缺失而有 `category` 时(旧版生产者)按 `category == "incubating"` 推导;两键都缺不动已有状态。这样准入语义在混部期间两个
  方向都不丢(codex R1 #1:原稿只保证报文可接收,旧接收端会把新建的观察期源记成空串、升级后变正式,且同一 revision 不会重放)。

### 3.2 提示词 v7

`ARTICLE_ANALYSIS_PROMPT_VERSION` 升到 `article-analysis-v7`;**新闻价值尺子逐字不动**,`ARTICLE_ANALYSIS_SCORING_VERSION`
保持 `news-value-v2`(公共日报照常复用存量新闻分)。内容价值另立版本号 `content-value-v2`(`content-value-v1` 是
v3.44 时代旧尺子的名字,已被占用,其记录不复用)。

**输出字段**(JSON 顺序):`score_reason`、`quality_score`、`content_kind`、`content_value_reason`、`content_value`、
`summary`、`content_genre`,其后与 v6 相同。依据先于分数,与新闻价值同一写法。

**输入新增两项**(都由服务端生成,不含 URL):

- `kind_hint`:来源先验、数据结构、链接形状能确定类型时给出(第一波 `classify_item` 的规则部分)。模型必须照用,
  保证 HF 论文、changelog 用对应类型的标准评分。规则判不出时不给,由模型判。
- `community_signals`:目前只有 HF Daily Papers 的赞数,取自条目扩展字段的 `raw_data.upvotes`(抓取器一直在写,
  存量论文也有;方案稿曾误判为「没有入库」,实现时更正,不需要改抓取器)。数值是抓取那一刻的快照。

**内容价值尺子**(拍板稿;实现时为过门禁做了四处调整,见下方「门禁调整」,提示词以
`src/llm/article_analysis_prompt.py` 的 `CONTENT_VALUE_RULER_PROMPT` 为准):

```text
【内容价值】content_value 是第二个分，与新闻价值相互独立，衡量「这篇值不值得 AI 从业者花时间读完或听完」：
读完能带走多少可核对、可复用的东西（方法、数据、判断、可执行步骤）。一件大事的媒体转述新闻价值高，
内容价值可以低；一篇窄而扎实的教程正相反。不评文笔，不按篇幅给分，不因来源是大厂加分。

先确定 content_kind，只能取 news、paper、tutorial、opinion、release、project、digest。
输入给出 kind_hint 时，content_kind 必须等于它。没有时按正文判断：
- paper：论文原文、技术报告、带实验与结论的研究长文。媒体或博主对论文的报道、解读算 news；
- tutorial：可以照着做的实践指南、操作手册、工程复盘。介绍产品功能的发布稿、营销式「最佳实践」算 news；
- opinion：评论、立场声明、访谈、对谈、个人分析；
- digest：周刊、日报、多条目合集；
- release：版本说明、changelog；
- project：代码仓库、模型卡、工具或数据集的介绍页；
- news：其余对事件的报道、公告、发布稿、推文。

再按该类型的标准评分：
- paper：贡献是否新而具体（新问题、新方法、新结论，而不是换个数据集刷几个点）；证据是否扎实（对比基线、
  消融、规模、复现细节）；是否开放权重、代码或数据；
- tutorial：能否照着做（步骤、代码、配置是否完整）；是否讲清原理与取舍；离开特定厂商的产品是否仍成立；
  是否有实测数据或踩坑经验；
- opinion：是否带来新事实或新框架；论证是否成立；讲述者是否一手（亲历者、决策者、研究者本人）。
  复述他人观点的二手评论低分；
- digest：取舍是否有判断、是否去重；覆盖面；每条是否附有效点评与出处。纯链接堆砌低分；
- news：信息密度（具体数字、机制、对比）；一手程度（官方原文、当事人 vs 转述）；
- release：使用者需要知道的改动是否写清（新能力、破坏性变更、迁移方法）。只有版本号或琐碎修复的低分；
- project：能否用起来（安装、用法、示例）；要解决的问题是否明确；文档与维护情况。

内容价值使用 1.0～10.0，保留一位小数，锚点各类型通用：
- 9.0～10.0：该类型里会被反复引用或长期回看的标杆（奠基性论文、权威的深度教程、关键人物的一手长访谈）；
- 7.0～8.9：扎实，值得专门花时间读完，读完能带走具体的方法、数据或判断；
- 5.0～6.9：有可用信息，但浅、泛，或大部分是已知内容，扫一眼即可；
- 1.0～4.9：内容稀薄、纯链接或纯标题、营销稿、与 AI 无关。
【领域相关性上限】与 AI / 前沿技术无关或只是顺带提及的内容，content_value 最高 4.9，写得再好也一样。
营销通稿、软广、PR 稿落 1～2.9，与新闻价值同口径。
【只看到部分内容】正文只有摘要、标题或片段时，按能看到的内容评，不臆测全文质量；论文只有摘要时，
按摘要能确认的贡献评。
【社区信号】community_signals 是抓取时的快照：数值高可以作为佐证上调，数值低不扣分（可能只是抓取时还早），
不能代替对内容本身的判断。

content_value_reason：先于 content_value 给出，一句话、不超过 40 个汉字，说明值不值得花时间
（例如是否给出可复现细节、讲述者是否一手、是否只是转述），不复述内容。
```

**门禁调整**(第一轮评测后,只动内容价值这一段,新闻尺子未动):

1. 写明 `content_kind` 与 `content_genre` 是两个字段——模型曾把体裁取值 `social_discussion` 填进类型,一句话的帖子因此
   连续两次输出不合规;
2. 资讯一条补「看这篇文本能让读者带走什么,不是事件有多大:只宣布事情、缺机制数据的发布稿落 4～6,转述低于原文」——
   第一轮资讯整体比金标高约 1 分,模型把新闻分带进了内容价值;
3. 1.0～4.9 档拆成 3.0～4.9(转述、泛泛、推广)与 1.0～2.9(只有标题 / 元数据 / 一两句 / 纯链接,以及营销稿);
4. 营销稿明确包括「企业借论文发表、融资、获奖做的宣传稿,即使引了实验数字」。

原拍板稿末尾的 `content_value_reason` 说明挪进了输出字段说明,措辞不变。

**校验**:`content_kind` 不在七个取值内即判本次输出无效(走既有的结构修复重试);给了 `kind_hint` 而模型输出不同,
以 `kind_hint` 为准、不判失败;模型把体裁取值填进类型时按体裁映射表折回(记 warning)。公共日报的现场补评只用
新闻分,传 `require_content_value=False`:内容价值字段缺损不触发修复、不丢新闻分。体裁与类型不一致时(如类型 tutorial、体裁 product_update)不改体裁:读者面类型取
模型的 `content_kind`,事件类型只在资讯 / 版本更新 / 项目上取自体裁。

**对新闻分的影响**:提示词多了一段,新闻分可能被带偏。门禁(§3.6)要求 62 篇新闻黄金集在 v7 下的 MAE 与档位
一致率不劣于 v6;不过就改提示词,不改新闻尺子。

  照样前移,升级后那些行不会重发——外网先部署、内网晚几天升级的这段时间里,近 7 天重跑、新文章与回填产出的内容价值会
  在内网永久缺失。对策:接收端在同步状态里记下自己按哪一代分析流载荷拉过(`v2_analysis_payload_generation`,常量
  `archive_sync_v2.ANALYSIS_PAYLOAD_GENERATION = 2`);落后时,同步准备阶段在一个事务里清掉分析流 checkpoint 和该权威的
  分析流逐行应用记账,本次同步按协议既有的全量路径整流重拉分析流(逐行覆盖、重建记账、收尾只删 presence 确认不存在的行),
  其它流仍增量。效果:内网什么时候升级都能补齐,外网的回填不必等内网;代价是内网升级后第一次同步多拉一遍分析记录
  (生产约一万条、几十 MB),此后不再发生。补拉中途失败时 checkpoint 仍空,下次从头重新下载,已应用的行被记账跳过——
  应用层续上,不是网络分页断点续传(检视 R4-1)。
- **管理面**:文章详情抽屉同时显示两个分与依据;分数分布图仍只画新闻价值。

### 3.5 读者面

- **条目列表**:分数位显示主分,着色档位沿用新闻价值的阈值(6.0 灰线)。列表不标维度(样页待验证问题,验收时观察)。
- **评分卡**(`AiReadingCard`):分数下方加一行小字标出当前维度。有两个分时,点分数在两个维度间切换,数字、着色、
  小字一起换,AI 速读不变;切换只对当前打开的这篇有效,换篇回到主分。悬停分数浮出该维度的评分依据;键盘聚焦同样浮出,
  回车切换。现在「点分数翻面看评分依据」的交互退役,由悬停取代。浮层可以用鼠标移进去停留,Escape 收起且焦点不动;
  悬停与焦点都离开、或有新的悬停 / 聚焦进来时复位(检视 R1-6)。
- **移动端**:没有悬停,评分依据改为评分卡里常显的一行小字(≤40 字),点分数切换维度时随之更换。
  不用长按:长按在条目上已经是动作单,叠加含义容易误触(也符合「可发现优先于安静」的拍板)。
- **个人早报页**:不变(早报按新闻价值编排,第三波再加内容价值分区)。

### 3.7 回填与上线顺序

现有「历史文章完整分析」只有「全部强制」和「缺失或版本过期」两种策略;后者会把所有 v6 结果也算作过期、整篇重跑,
违反 §3.1「不覆盖已有新闻价值」。本波新增两种:

- **仅缺失**(`selection=missing`,管理面「仅从未分析」):只处理从未成功分析过的文章(给 4337 篇用),完整跑 v7。
- **补内容价值**(`selection=content_value`,管理面「补内容价值」):只处理已有当前新闻分、缺当前内容价值的文章,
  按内容类型过滤(默认论文 / 教程 / 观点 / 汇编,外加体裁为「学术论文」的资讯——这批最可能被模型改判为论文)。
  `queue_content_value_fill` 把行置为 pending + `pending_scope=content_value`(排队期间旧结果照常可读),worker 跑 v7,
  提交时**只写**内容类型、内容价值与依据,新闻分、摘要、标签、体裁、`prompt_version` 与 `analyzed_at` 都不动;
  期间正文若变化,入库钩子的完整分析把范围改回完整。表上的触发器照常推进同步版本,让内网收到。播客按 §3.3 不参与。
  补评只在 attempt 上记本次的模型与 taxonomy,结果行的来源字段保持上一次完整分析的值。选样避开近 7 天内提示词版本落后的
  文章(与版本巡检同一窗口与时间解析):巡检会整篇重跑它们并顺带产出内容价值;没赶上就出了窗口的,下一次补评选样会选中。
- **边界**(检视 R1):「仅从未分析」派发时再核一次——期间已被实时补偿扫描分析过的直接记完成、在途的关联其结果而不重新入队;
  补评失败(含终态)后管理面「重试失败项」重新排队补评,完整刷新还在重试的让它先跑;补评被撤销(源开关关闭)或被别的路径收尾而
  没写内容价值时记跳过;目标未完成而本机已无执行权(归档同步接管、接收端停写)时一律记跳过,不会让任务永远停在运行中。

上线后的顺序:

1. 部署后,既有的版本巡检会把近 7 天的 v6 结果按 v7 整篇重跑(每轮最多 16 篇,约一千篇、约 1 美元)。等它消化完再做第 3 步
   (选样已避开这批,先后顺序只为让估算数字准确)。这是提示词升级的
   既有机制:这些条目的新闻分会被同一把尺子重评一次,数值可能小幅变动,门禁第 1 条兜底。
2. 「仅缺失」先限定一个小来源试跑,再跑全部历史(约 4337 篇,按 §3.1 估算 5–10 美元、约 9 小时)。不必等内网升级:
   内网升级后第一次同步会自动整流补拉分析流(§3.4)。
3. 「补内容价值」先估算篇数与费用,确认后执行(预计一两千篇,约 1–3 美元)。
4. 回填前告知「历史高分」榜单会纳入 6–8 月内容(§3.1)。
